A fork that sends features upstream as pull requests gets a contribution mode, so graph entries about a feature are captured on that feature's branch and travel with the pull request. The mode is explicit and off by default. With it off, sdd behaves as it does without this plan.

## Mode

The mode is on in a checkout whose machine-local config sets `contribution` to an upstream ref, for example `contribution: origin/main` in that checkout's `.sdd/config.local.yaml`. `sdd config set --local contribution origin/main` writes it. The committed `config.yaml` rejects the key. The agent session starts inside the feature's worktree, so the CLI commits there and `sdd serve` started there derives the feature branch as the unbound base (20260923-233057-d-cpt-ekd). Graph writes at the upstream graph's schema follow from 20261027-092049-d-tac-7gz.

## Shared prerequisites

Entries that several pull requests need, such as an actor signal for the fork's maintainer, are captured once on a branch `contrib/base` cut from the upstream ref. Every feature worktree is cut from `contrib/base` (`git worktree add <dir> -b feat/x contrib/base`), so all pull requests carry the same commit and upstream merges it once. The fork's mainline merges `contrib/base` too.

## Guard

In contribution mode a write is refused when its target branch is `default_branch`, is the branch of the `contribution` ref, or does not contain the ref in its history (`git merge-base --is-ancestor`). The refusal names the cause, for example `feat/x is not cut from origin/main`. The engine resolves the mode per write against the target checkout, since a `bind_branch` target is another worktree with its own local config. CLI and MCP behave the same. `sdd info`, `mcp__sdd__info` and the serve banner show `Mode: contribution (<ref>)`.

Refs into entries missing from the worktree's graph are already refused as dangling refs, so a contribution entry cannot reference a fork-only entry. Fork-only decisions are captured on the fork's mainline, never in a contribution worktree.

## Skill note

The bundled sdd skill template gains a section on contribution mode: when to use it, the `contrib/base` and worktree setup, the config key, what the guard refuses, and that fork-only decisions belong on the fork's mainline. The installed renders refresh through `sdd init`.

## Decomposition

- `internal/model`: `Contribution` on the machine-local config layer, rejected by the committed layer. A pure guard function decides refusal from the target branch, `default_branch`, the ref's branch and the ancestry answer.
- `internal/query` and `internal/finders`: a contribution status read for `sdd info` and the serve banner.
- `internal/handlers`: write handlers run the guard before writing. An ancestry check (`IsAncestor`) joins the git interfaces the handlers declare, implemented in `internal/git`.
- `internal/cliapp`: the write gate resolves the mode. `sdd config set --local` accepts `contribution`. `sdd info` prints the mode.
- `pkg/application`, `pkg/local`, `pkg/mcpapp`: target acquisition resolves the mode from the acquired checkout on every write and applies the guard. The MCP `info` tool reports the mode.
- `internal/presenters`: the mode line.
- `internal/bundledskills/templates`: the skill section.

## Why

Engine captures from a session started in the base checkout land on the base checkout's branch, not on the feature branch. Entries captured on branches cut from the fork's mainline sit on fork-only graph history and cannot ride a pull request. Capturing a shared entry separately on each feature branch creates one copy per pull request with different IDs.

## Rejected alternatives

- Export at pull request time, copying entries onto the PR branch. It adds a manual step per pull request, and each entry then exists twice, which conflicts when upstream merges back into the fork.
- A binary built from upstream for PR branches. Those captures lose the fork's checks, and two sdd binaries share the PATH.
- Entries in a separate store (orphan branch, git notes, a second repository). Search and view do not see them.
- One long session that calls `bind_branch` per feature. It depends on the agent remembering, and a forgotten binding lands on the mainline.
- An environment variable switch. It is invisible in the tree and leaks into every repository the session touches.
- A bool switch guarding only `default_branch`. A branch cut from the fork's mainline would pass.
- A reserved `fork/` topic refused in contribution mode. It catches only tagged entries and adds a reserved-namespace rule for little gain over the dangling-ref refusal.
- Accepting the configured local participant without an actor signal. It changes the participant check for every graph, and entries would name a person the graph never introduces.

## Accepted costs

Each feature needs its own worktree and session. Each write in the mode costs one `git merge-base` call. Until upstream merges `contrib/base`, every pull request shows its entries. A fork-only decision captured by mistake inside a contribution worktree rides the pull request, and only review catches it.

## Acceptance criteria

- [ ] With no `contribution` key, every existing test passes unchanged.
- [ ] Each guard case (target is `default_branch`, target is the ref's branch, target not cut from the ref, ref not fetched) is refused through the CLI and through MCP, and each guard is broken once with its test failing on its own assertion.
- [ ] A capture in a worktree cut from `contrib/base` succeeds through the CLI and MCP and lands on the feature branch.
- [ ] A `bind_branch` target in another worktree resolves the mode from that worktree's config.
- [ ] `contribution` is accepted by the machine-local layer and by `sdd config set --local`, and rejected in the committed `config.yaml`.
- [ ] `sdd info`, `mcp__sdd__info` and the serve banner name the mode and the ref.
- [ ] The bundled sdd skill carries the contribution-mode section, and the Codex render validates.
