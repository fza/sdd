Git now merges a graph entry file whose title or summary both sides rewrote without a conflict: `sdd merge-entry` ships on branch `pr/feat-merge-entry` in `ba2e0675`, closing the merge-driver directive (20261030-085158-d-tac-vyt) and the summary-rewrite conflict gap (20261030-083758-s-tac-5ky).

Acceptance criteria:
- Both sides changed the summary or title: the merge keeps the value sorting first and yields the same file from either side; covered by handler tests over fixture entries.
- One side changed it: that side's value is kept; same tests.
- Both changed the same other frontmatter or body line: the driver exits non-zero and leaves git conflict markers.
- An unknown frontmatter key changed on one side survives byte for byte beside a summary change.
- `sdd init` commits `.sdd/graph/**/*.md merge=sdd-entry` to `.gitattributes` and writes the driver section into `.git/config`; a repeat init changes nothing, and restores the section when it is missing even with nothing to commit.
- Every sdd commit, merge and merge-pull in a clone lacking the section writes it, once per process.
- Without the section git text-merges entry files and conflicts on a doubly changed summary.

A smoke run with the built binary on two clones of one upstream showed the whole path: the clone that never ran init gained the driver from `sdd summarize`, and `git pull` merged two different summaries cleanly.

Noted in the doing: the root command hook runs a sync check and config warnings before every command, so `merge-entry`, which git runs mid-merge, returns from it early. On a first init the commit's own driver setup masks init's explicit one; the repeat-init case tests the explicit setup alone. A side whose frontmatter cannot be read merges the whole file as text, and a driver configured otherwise is left as it is.

As the directive accepts, hand edits to `.sdd/config.yaml` and `.sdd/meta.json` and a frontmatter only reformatted by another sdd version still conflict as before. Not yet merged into `pr/core` or `fza-fork`.
