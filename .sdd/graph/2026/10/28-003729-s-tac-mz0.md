title: Conflict notices lost on reads
summary: Merge-conflict notices from the automatic pull never reach the agent when the triggering engine call is a read call. Only a served step carries the notice, and the sync cooldown keeps later calls from raising it again until the next fetch. The signal is grounded in the conflict-notice directive (20261027-231225-d-tac-n5o), was recorded by the automatic graph sync evaluation (20261028-002921-s-tac-bb0), and leaves candidate remedies unsettled.

A merge-conflict notice raised by the automatic pull during an engine session reaches the agent only when the call that ran the sync also serves a step; a read call (show, search, view, info) runs the sync, discards the notice, and the conflict stays unreported until the next fetch after the cooldown.

Actual: every engine call refreshes the session through `RefreshWorkflow`, which runs the graph sync and keeps its notice on the refreshed session (`pkg/application/workflow.go`). Only a served step prepends the notice to its instructions, and a read call serves no step. The sync check raises the notice only on a call that fetched (`pkg/local/graph_sync.go`), and the cooldown gates fetches, so the calls that follow within the cooldown raise no notice. Observed by reading the code on `fza` at `2221b775`; recorded as a finding of the sync evaluation (20261028-002921-s-tac-bb0).

Expected: the conflict-notice directive (20261027-231225-d-tac-n5o) commits that a conflict the automatic pull finds reaches the agent as a notice, because a branch that silently stopped syncing is the failure it rejects. An agent that only reads after the notice was raised keeps working on that branch unwarned.

Candidate remedies, unsettled: keep the notice on the session until a serve carries it; raise it on every call while the conflict lasts, not only after a fetch; attach it to read responses.
