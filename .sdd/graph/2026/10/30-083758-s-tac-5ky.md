A graph held in its own repository still meets textual merge conflicts when two participants sync, because some sdd writes rewrite files that already exist instead of adding new ones.

**Expected.** The sync directive (20260817-162701-d-cpt-r8k) treats divergence between two capturing participants as the ordinary case, and a graph in its own repository as the setting where sync simply works. Entry IDs carry a timestamp and a random suffix, so added entries never share a path and merge cleanly.

**Actual.** Read from this repository's `.sdd/` history: nearly every edit to an existing file is `sdd summarize` rewriting the `summary` field in an entry's frontmatter, singly or in bulk runs over hundreds of entries. That placement comes from the frontmatter summary directive (20260414-152337-d-tac-h93), with summaries regenerated on demand. Two participants summarizing the same entry, or a bulk run overlapping any single summarize, conflict on that file. Edits to `.sdd/config.yaml` and `.sdd/meta.json` conflict the same way, rarely. Each such conflict pauses automatic sync and lands on an agent to resolve (20261028-201909-d-tac-fxp). sdd registers no merge driver; no `.gitattributes` exists.

**Candidate remedy, unsettled.** An sdd merge driver registered through `.gitattributes` that settles a conflicting `summary` field on its own, keeping the current file layout. Its costs: every clone must configure the driver in `.git/config` (`sdd init` could write it), and it covers only the conflict shapes known when it is written. Weighed beside it: an append-only layout writing each summary to a new file, which removes textual conflicts entirely but changes the layout and needs a migration.

**Out of scope.** Two participants closing or superseding the same entry merge cleanly yet leave competing outcomes; no file layout or merge driver prevents that.
