sdd ships its own git merge driver, `sdd merge-entry`, for graph entry files, so two participants rewriting the title or summary of the same entry merge without a conflict. It addresses the summary-rewrite conflicts (20261030-083758-s-tac-5ky). Title and summary are derived from an entry's body, which never changes (20260414-152337-d-tac-h93), so either side's value is valid.

**Policy.** Per field, title and summary: only one side changed from the base → that side; both changed → the value whose UTF-8 bytes sort first (Go `strings.Compare`, no locale or normalization). Every clone resolves the same pair the same way, so merges in any order converge. Rejected: keep ours (the outcome is whoever pushes last); keep theirs (silently drops a summary written and checked by hand); keep both and flag the entry for a fresh summarize (a new frontmatter field plus a follow-up step to clear it). Accepted cost: which of two valid summaries wins is arbitrary.

**Rest of the file.** The driver locates the title and summary values in each version's frontmatter, writes the chosen values into all three versions, and lets `git merge-file` merge the rest line by line: clean exits 0, otherwise it leaves conflict markers and exits 1, as git's own merge would. Body bytes and frontmatter keys the running sdd does not know stay as written. Rejected: parsing both sides into the entry model and rewriting the file (drops keys a newer sdd wrote, reformats the file); a three-way merge per YAML key (most code to own, and re-encoding restyles values). Accepted cost: a frontmatter only reformatted by another sdd version still conflicts, as today.

**Setup.** `sdd init` commits a `.gitattributes` line routing graph entry files to the driver, beside the `.gitignore` entries it already manages, and writes the `merge "sdd-entry"` section into the clone's `.git/config`. Every sdd command that touches the graph repository's git (serve, sync, commit paths) writes that section when it is missing, so existing clones need no re-init and a pull made by hand is covered once sdd has run in the clone. A clone without the section falls back to git's text merge, checked in a scratch repository. Rejected: `sdd init` alone (every existing clone must run init again); only under `sync.mode: auto` (a hand pull still conflicts, and a committed `.gitattributes` would hang on a setting each person makes for themselves, 20261027-211908-d-tac-l8j); the user-global git config (sdd editing a file outside the project); `.git/info/attributes` (nothing in the repository shows the driver exists). Accepted costs: sdd writes to `.git/config` unasked; with `sdd` missing from PATH during a merge, git stops on a conflict without markers.

**Prior art.** No existing tool settles a field both sides changed: mergiraf, suture and git-json-resolver still conflict there and would add a Rust, Python or Node runtime to every clone; chant's frontmatter driver serves only chant's own spec files.

## Acceptance criteria

- [ ] Both sides changed `summary` (or `title`) of one entry and nothing else: the merge succeeds, the result holds the value sorting first, and merging in the other direction yields the same file.
- [ ] Only one side changed `title` or `summary`: the result holds that side's value.
- [ ] Both sides changed the same other frontmatter line or body line: the driver exits non-zero and leaves git conflict markers.
- [ ] A frontmatter key unknown to the running sdd survives a driver merge byte for byte.
- [ ] `sdd init` writes the `.gitattributes` line and the `.git/config` section idempotently; a second run changes nothing.
- [ ] In a clone lacking the `.git/config` section, the next sdd command touching the graph repository's git writes it.
- [ ] Without the `.git/config` section, git merges entry files with its text merge.
