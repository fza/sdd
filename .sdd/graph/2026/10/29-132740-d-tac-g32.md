Every `sdd init` run in a work repository also runs a full init in the project holding its graph, and both repositories receive the same `.gitignore` entries, so one command keeps both current. This refines the one-step split setup (20261029-130154-d-tac-frl), which initialized the project only when setting it up: afterwards an init in the work repository refreshed that repository alone and wrote the project nothing but the participant, so the project's skills, MCP registration, `.gitignore` and `meta.json` drifted until someone ran init inside it. Felix Zandanel asked for both.

- On every run with a project at `project_dir`, the project's init runs first with its own recorded settings: skill scope and agents as the project records them, upgrades and refreshes committed in the project repository when anything changed. Its failure stops the run before the work repository is touched.
- The work repository's init follows as before: pointer config, skills and MCP registration, committed there.
- Both repositories get the full entry set a project's `.gitignore` gets today: `.sdd/tmp/`, `.sdd/config.local.yaml`, `.sdd/stats/`, `.sdd/sessions/`, `.sdd/staged-blobs/` and the graph directory's `.sdd-runtime/`. The work repository received only `.sdd/config.local.yaml`, so a `.sdd/` runtime file created there by a command run in it could get committed.
- The questions (20261029-132422-d-tac-2sn) are asked once per run and serve both repositories.

Rejected: initializing the project only on first setup. It leaves the project's skills and metadata to drift unless someone remembers to run init inside it.

Accepted costs: an init in the work repository commits in the project repository on refreshes too; a failing project init blocks the work repository's refresh until fixed; the work repository's `.gitignore` carries entries for paths it rarely holds.
