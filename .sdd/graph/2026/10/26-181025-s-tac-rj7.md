At a supersede fork the model answers which entry is current with three different rules, and `ResolveRef` follows none of the rules the graph has decided. `ResolveRef` takes the first superseder in load order and ignores closure. `ProcedureChain.Head` takes a live head, preferring a project entry over a shipped one, then the newest, as 20260702-222259-d-cpt-7iy commits. `ActorChain.Head` takes the oldest non-superseded entry.

A model-level probe shows two cases where `ResolveRef` lands on the wrong entry:

- X is superseded by Y, a directive closes Y, and Z later supersedes X, which pre-flight allows because Y's branch is settled. `ResolveRef` from X lands on the closed Y, and X's status reads superseded by Y, though Z is the live successor. The fork lint stays silent, treating the fork as settled per 20260608-134612-d-cpt-rgx. Pre-flight's fork check reads the same head, so a further entry superseding X passes it while Z is live.
- Two project overrides of one shipped procedure: `ResolveRef` from the shipped entry lands on the older override, while the chain's execution head is the newer one.

Between a shipped and a project entry, `ResolveRef` reaches the project entry only because shipped entries load after project entries.

20260608-095950-d-tac-m9b designed `ResolveRef` for linear chains and left forks to lint. Procedure forks became legitimate later, and a fork with one live branch counts as settled. The fork census in 20260810-121909-s-tac-a1g already noted the tie-break as unspecified, with no misbehaviour at the time. `ResolveRef` feeds derived status, `show`, pre-flight's ref context and fork check, and the facts the engine serves.

The expected state is that a fork with exactly one active head resolves to that head, and every code path resolves forks with the same logic. The question came up while implementing 20261026-174647-s-tac-fwo.
