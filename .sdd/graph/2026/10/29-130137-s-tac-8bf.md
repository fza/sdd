Git subprocesses that sdd starts can still reach the user's terminal: under `sdd serve`, an engine capture's commit-signing prompt read the user's keystrokes and broke the terminal, although d-tac-zhp committed every auto-commit path to run detached and fail fast with Git's error.

Observed in a Claude Code session on another project, after a reboot left the SSH signing key out of the agent. An engine capture's commit started `ssh-keygen -Y sign`, which prompted for the passphrase on the terminal Claude Code was reading. The two processes split the keystrokes: Claude Code received keyboard and mouse sequences without their escape bytes, the signer read garbage and failed with "incorrect passphrase", the write took minutes to return, and the terminal had to be reset.

Reproduced in a scratch repository with a passphrase-protected SSH signing key, no agent and an isolated pseudo-terminal, calling `git commit` from Go as the finalizer does. The prompt goes to the terminal. When the context deadline passes, git is killed, but the call returns only once the terminal input ends, because `ssh-keygen` outlives git and holds the output pipe. Detached (`Setsid`), the same commit fails immediately with Git's error and the terminal stays untouched. Setup, program and output: [reproduction](./29-130137-s-tac-8bf/signing-prompt-repro.md).

Cause in the code: engine captures commit through `GitFinalizer` in `pkg/local/git_finalizer.go`, the sole committer of a capture publication (d-tac-ugt), which runs git with plain `exec.CommandContext`. Only `CLI.Commit` in `internal/git/git.go` uses the detached runner the earlier fix shipped. Other Git calls run attached as well: `RemovalCommitter.Commit`, fetch, pull and clone in `internal/git`, and the worktree commands in `pkg/local/git_target.go`.

Expected, beyond d-tac-zhp, as Christopher stated it in this dialogue: no Git call sdd starts reaches the user's terminal; a call that needs input it cannot get fails fast; Git's own error is forwarded as is, not translated; after the user has fixed the cause, such as by loading the key, the engine's retry of the failed write (d-tac-ugt) completes it; nothing falls back to an unsigned commit; and no signing check runs before the user confirms an entry.

Signing is one known prompt. SSH passphrases, host-key confirmation and HTTPS credentials on fetch, pull and clone, GPG signing, and commit hooks can prompt too; which of these each call site can hit is not inventoried. Closing this gap means no Git subprocess can reach the terminal, not a fix to the finalizer alone. Candidate remedies, unsettled: one shared Git runner for every subprocess, detached and bounded so the timeout also ends the signer, and a guard that fails when code starts git outside it. Forwarding `SSH_AUTH_SOCK`, the mitigation for the earlier hang under Codex (s-tac-cam), does not help here: the agent was reachable, but the key was not loaded.
