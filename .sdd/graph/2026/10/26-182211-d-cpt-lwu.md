Every code path resolves a supersede fork to its current entry with one rule in the model: among the candidate heads, an active (not closed) head wins over a closed one, then an entry nearer the resolving project over a farther one, then the newest, then the entry ID. Nearness counts dependency hops: the project's own entries first, then its dependencies' entries by hops, and entries shipped with sdd always last. The candidates are the non-superseded entries reachable from the entry being resolved; for a chain, all of its heads. A fork with exactly one active head therefore resolves to that head.

`ResolveRef` and through it derived status, `show`, pre-flight's ref context and fork check, and the facts the engine serves use the rule, as do `ActorChain.Head` and `ProcedureChain.Head`. No code path keeps its own tie-break. This answers 20261026-181025-s-tac-rj7, where the resolver took the first superseder in load order and the two chain types each chose differently.

The order extends the procedure execution rule of 20260702-222259-d-cpt-7iy, a live project head first and the newest within it, to every kind and origin, so procedure execution behaves as it does today. Christopher set the origin preference as general rather than limited to facts and procedures, and ordered dependencies by hops because a dependency may serve as a base for similar projects and ship entries of any kind to them. Supersedes and closes stay within one graph under 20260529-131915-d-cpt-v8t, so only the shipped-entry part applies until lifecycle edges may cross a repo boundary. The entry ID comes last so the result never depends on load order. This replaces the linear-chain assumption of 20260608-095950-d-tac-m9b, which left forks to lint.

The rule makes resolution deterministic; it does not make a fork intended. The lint warning on a fork with more than one active head stays, and a fork in the graph is still resolved by converging forward per 20260608-134612-d-cpt-rgx.

Returning every head and letting each consumer choose was weighed and rejected: status, `show`, refs, served facts and execution would each handle a fork their own way, which is the divergence this rule removes.
