A read never fails because of a dependency-closure member it does not need: an unavailable member is read around and reported, a reference into it renders as unavailable, and only a read that names that member, or a capture referencing it, fails on it.

This answers 20260903-153224-s-cpt-ir1 with degrade per reference, and settles the expected side of 20261028-155600-s-tac-4mz, where the CLI reads around an unavailable member and serve fails the read: both surfaces follow these rules.

- A read that does not name a member never fails because of it, whether the member is a sibling met while walking the closure, a direct dependency loaded up front for `show` or a session's graph, or a member behind another. On 2026-10-28 serve failed `show` and session open when a direct dependency's graph could not be read.
- A read naming one member fails when that member is unavailable, naming the member and the reason: working in it as a project, `show <repo-id>:<entry-id>`, search or view with that repository selected. This changes the CLI, whose search skips a named unavailable repository with a warning, because an agent can miss a warning and report the repository as holding nothing. A member that is readable but whose refresh failed is read from its cache, with a warning.
- A read over all repositories returns what it can read and names every member it could not read.
- A reference into an unavailable member renders as unavailable and the read continues: a `show` chain keeps the ref line and its description with a marker in place of the target's summary and status, and view expansions and lists do the same. The `[unresolved: repo X]` marker of 20260707-175137-d-tac-i6f becomes this marker. A capture keeps blocking per reference (20260628-130400-d-cpt-uh0), only on references into the unavailable member, naming the reason.
- A member reachable only through an unavailable member is unreachable too; a read naming it names the chain to it and the unavailable member, not "not in the closure".
- Each unavailable member yields one warning, of the same kinds on every surface: not connected on this machine, not cloned, refresh failed, configuration unreadable, graph unreadable, and unavailable for a hosted refusal. Each carries who must act and the original error text (20260829-113416-d-cpt-nut). The CLI prints it to stderr; serve carries it in the read's result beside the incomplete-index notice and in session framing beside the graph-health block. The not-connected and refresh-failed kinds are the warnings the CLI refresh already reports (20261027-150208-d-tac-bg4).
- A hosted refusal stays indistinguishable from an unknown dependency (20260712-104530-d-tac-1mb) and reports as unavailable without a cause. A failure does not hide behind it: `AccessResolver.ResolveDependency` separates a refusal, a typed not-available answer, from an error, reported verbatim. Today the application treats any resolver error as a refusal, which extends the dependency-store swallow recorded in 20260723-114403-s-tac-m13 to the resolver. This changes the public API for implementers.
- Unavailability is a typed Go value carrying the member, the kind, the original error and the chain, passed from where it is detected to the presenters; only the presenters render it as text, through one rendering shared by the CLI and serve.

Why: a read should not depend on parts of the horizon it does not touch, the stance 20260723-113656-d-cpt-4y9 takes for one bad file, here taken for one unavailable dependency. The rule of 20260906-234056-d-tac-bae that nothing falls back after a source cannot be acquired holds: no other source substitutes for the member, and its failure is reported rather than dropped. The strict answer, requiring access to the whole horizon, was rejected because one broken direct dependency stops every session in the home project, and in engine mode, where no cache is refreshed, one uncloned second-level member fails every all-repos read. The closure itself stays as 20261026-194528-d-cpt-gcq sets it.

Out of scope, each kept by its gap: refreshing caches from serve (20261027-145612-s-tac-2n5) and surfacing a member's unreadable entries (the member load-issue item of 20260723-114403-s-tac-m13). The behaviour observed on 2026-10-28, the alternatives weighed and example renderings are in the [design record](./29-135448-d-cpt-olh/unavailable-closure-member.md).
