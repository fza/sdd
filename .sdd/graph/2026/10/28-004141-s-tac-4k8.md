Under `sync.mode: auto`, a command that runs the cooldown-gated sync check and then commits to the graph reports a held push twice, with the same reason both times.

Actual: the CLI sync check pulls through `PullGraph`, which publishes what the branch holds ahead whenever the pull is ready or finds nothing to merge (`internal/handlers/handler_pull_graph.go`). The command's own commit then publishes again through `commitGraph` (`internal/handlers/handler_push_graph.go`). Each publish whose push is held logs the captured-but-unpublished warning. Observed in a smoke run against a bare remote, where a capture behind a commit not written by sdd printed the warning before and after its own output, and confirmed in the code on `fza` at `2221b775`; recorded as a finding of the sync evaluation (20261028-002921-s-tac-bb0).

Expected: one command reports one held push once. The warning describes a standing condition of the branch, and repeating it within one command reads as two separate problems.

Candidate remedies, unsettled: skip the report on the commit's publish when the sync check already gave it in the same command; leave publishing to the commit when the command is about to commit anyway.
