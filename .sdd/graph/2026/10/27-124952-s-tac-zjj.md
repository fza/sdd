Commit f4982b87, merged into `fza` on branch `feat/info-json`, adds `sdd info --format text|json`: the JSON form prints the session framing as one object with `graph_schema`, `binary_schema` and a `capabilities` object, closing the info JSON plan (20261027-122627-d-tac-2cx).

The finder computes `capabilities` from the graph's recorded schema, else the binary's, and carries it on `query.InfoResult`. `model.SchemaCapabilities` carries the JSON keys itself, so a new capability field reaches the output without a second mapping.

Acceptance criteria, each covered by a test in `internal/cliapp/info_json_test.go`:

- Schema-1 graph: `graph_schema` 1, the binary's `binary_schema`, `capabilities.titles` false.
- Graph at the binary's schema: `capabilities.titles` true.
- Graph without `meta.json`: `graph_schema` absent, `capabilities` equal to the binary schema's.
- Every `SchemaCapabilities` field must carry a lower-case JSON key present under `capabilities`; adding an untagged field fails the test.
- `sdd info` without `--format` prints the same text as `--format text`, and an unknown value such as `yaml` is refused.

A graph newer than the binary has a schema this binary cannot describe. There `capabilities` is `null`: the key stays present, as the plan requires, and the write gate still refuses writes. A test covers this case too.

Each guard was broken once (format check, graph-else-binary schema choice, `graph_schema` omission, `null` for an unknown schema, the `titles` key, the JSON branch) and its test failed on its own assertion.
