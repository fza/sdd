Whenever automatic sync of the graph repository cannot proceed, every sdd response says so until the problem is fixed, and one agent works on fixing it: a stopped sync means captures stay unpublished and others' entries stop arriving, which has to be acted on fast. It covers every blocked state: a merge conflict, a held pull (commits not written by sdd, paths outside the graph, a dirty tree), a held push (a commit not written by sdd ahead), no upstream, a failing fetch, a missing graph repository. Today each is logged once per occurrence, and a conflict comes back at every fetch while a capture made meanwhile fails on its push retry (`internal/handlers/handler_push_graph.go`, as shipped in 20261028-000607-s-tac-h74).

**Record.** The marker of the timed sync plan (20261028-175735-d-tac-k4y) becomes a blocked-state record: the state, since when, its details and the owning agent's session; for a conflict also the upstream ref, the upstream commit that would not merge (source), the local commit it was to merge into (destination) and the paths. A successful round removes it.

**Pause on conflict.** While a conflict is recorded, no automatic path fetches, merges or pushes; a capture commits locally and succeeds. Each path only checks whether the source commit is now in the branch, and resumes once it is. Rejected: resuming whenever the branch moves (a capture moves it without resolving anything) or after a timeout (the same conflict again). Other blocked states keep retrying each round, since a returning network or a commit by the user clears them. An explicit `sdd sync` always runs and re-records what remains.

**Banner.** Every MCP response, step or read, from every agent, carries a short line in its `sync_notice` field naming the blocked state and since when, as plain result content, never an error or a warning the client renders red. Every CLI command prints the same line at info level. The first agent to call after the record is written owns it: its responses also carry the full steps. Served instructions tell the owner to fix it itself first (merge and resolve the conflict, commit as `sdd: merge <upstream>`), report one line once fixed, and tell the user and ask how to proceed when it cannot, such as for commits it may not rewrite, an authentication failure or a missing repository. Other agents see the banner and leave the fixing to the owner. This replaces the plan's one-time notice. Rejected: the owner alone told on every call (an idle owner leaves the user unwarned) and full steps to every agent (two agents fixing one conflict at once). Accepted costs: every response stays noisy until fixed, including during a brief offline spell; the banner's "since" needs the record even for transient states.

## Acceptance criteria

- [ ] With a conflict recorded, no timer round, per-call check or post-commit publish runs `git fetch`, `git merge` or `git push`; a capture commits locally and succeeds.
- [ ] Once the recorded source commit is in the branch, the next automatic path removes the record and syncs.
- [ ] For each blocked state, every MCP response of every server carries the banner in `sync_notice` as non-error content, and every CLI command prints it at info level, until a round succeeds.
- [ ] Only the owning agent's responses carry the fix steps; its served instructions say to fix first, report once fixed, and ask the user when it cannot.
- [ ] The conflict record holds upstream ref, source commit, destination commit, paths and time; `sdd info` and MCP `info` show the record.
- [ ] An explicit `sdd sync` runs while blocked and re-records what remains.
