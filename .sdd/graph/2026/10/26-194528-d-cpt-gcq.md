A project's horizon is its transitive declared dependency closure, and every read beyond the local graph reaches exactly that set on every surface: search and view over all or named repos, export, reading or traversing a `<repo-id>:<entry-id>` entry, its attachments, and the projects a session may work in. What a new entry may reference stays the direct declared dependencies (20260708-184318-d-cpt-6cq), and bare-ID resolution stays bounded to them (20260709-171105-d-cpt-ete), so a bare ID that resolves is still one a captured reference may point at. The user-global `repos` configuration only says how this machine reaches a repository, its clone URL and cache; it selects nothing, and repository management and cache maintenance (`sdd repo`, `sdd index gc`) are its only users.

Why: on 2026-10-26 the reachable set differed by surface. CLI search and view with `--all-repos` spanned every connected repository, the scope 20260606-003344-d-cpt-s6q set before dependencies were declared and 20260708-184318-d-cpt-6cq kept; MCP search and view spanned the direct dependencies; export spanned the closure; and the CLI resolved `<repo-id>:<entry-id>` in any connected repository while serve refused a cached second-level dependency as outside the closure. A repository the project does not declare is not part of its horizon, so reaching it is a defect, not discovery. The closure already bounds the projects a session may work in (20260903-152247-d-cpt-yjc); this makes it the bound of every read.

Whether a closure member that cannot be reached, because it is not cached on this machine or the reader may not access it, fails a read or degrades per reference stays open in 20260903-153224-s-cpt-ir1.
