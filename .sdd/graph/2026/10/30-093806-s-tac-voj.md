The `sdd merge-entry` driver shipped in `ba2e0675` (20261030-092427-s-tac-lx2) can block or skip its own setup and misreads some valid frontmatter, beyond the markerless-conflict defect the fallback decision (20261030-093341-d-tac-t6j) covers. Expected: the driver setup never stops an entry from being written and reaches every clone sdd writes in, entry files resolve their title and summary the same way from either side, and init writes a routing line that matches the graph or refuses. Actual, from an independent code review of that commit with each finding re-checked in the code (20261030-093649-s-tac-th3):

- **Setup blocks or misses commits.** `CLI.Commit` runs the driver setup before `git add`, so a failing config write fails an entry commit that needs no driver; two sdd processes writing the section at once can fail on git's config lock; `RemovalCommitter.Commit`, the WIP-removal path, skips the setup.
- **Setup errors read as absence.** The work-tree check treats any `git rev-parse` failure, such as dubious ownership or a broken repository, as no repository and installs nothing; the once-per-process cache also stores a directory that was not yet a repository, so a later `git init` there never gets the driver from that process.
- **Frontmatter edge cases.** A side that only requoted an unchanged value resolves to different bytes depending on which side merges; a leading UTF-8 BOM, a flow-style top-level mapping, or a closing `---` followed by spaces defeats region detection.
- **Init validation.** The `.gitattributes` line accepts absolute, `..` and glob graph directories, writing a pattern that matches nothing; the shared append helper ignores write and close errors, so init can report success without the line.
