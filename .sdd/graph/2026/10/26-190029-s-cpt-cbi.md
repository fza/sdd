How does a user running SDD locally find a session to continue once the agent conversation that held its handle has been closed or has crashed? The capability directive (20260828-165352-d-cpt-aen) moved session listing to the `sdd` CLI and accepted that an agent which lost its handle must ask the user; `sdd sessions` shipped with it (20260902-224832-s-tac-x8c) and shows each session's label, branch, last activity and open moves. Nothing leads the user to it, and the agent cannot: the served guidance tells it to ask the user and adds that sessions are never listed on this surface, and served text may not name the CLI (20260707-134311-d-cpt-476).

Observed 2026-10-26: asked to find a prior session behind an open pull request, the agent answered that sessions are not listed, found the handle by searching the raw session logs under `~/.local/state/sdd/sessions/`, and learned of `sdd sessions` only after the user questioned the design.

Strands that one answer settles:
- How the user learns the listing exists at the moment they need it, not from documentation read beforehand.
- Whether the agent may run the listing when the user asks, in a local setup where the OS user is the principal and an agent with a shell can read the session store anyway, or whether that brings back the handle publishing the directive removed.
- What host-neutral wording a serve could carry that points the user to their client's session listing without naming a command.
