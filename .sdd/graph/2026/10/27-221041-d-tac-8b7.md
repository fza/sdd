When the push after a graph commit is rejected because the upstream moved, sdd fetches, merges the upstream graph commits by the automatic pull's rules, and pushes once more; the command fails only if that second attempt fails. This refines the automatic sync plan (20261027-194536-d-tac-190), whose failed-push rule made every rejected push fail its command.

A push sends what this checkout knows, and sdd fetches only on the cooldown-gated background check, 15 minutes by default. In an active team a participant's graph commit often lands upstream inside that window, so the next capture elsewhere is rejected through no fault of the person capturing. Under the plan's rule that capture fails, and the entry reaches others only on the next background check, up to a cooldown late.

The retry merges only when the pull's rules hold: every incoming commit matches `^sdd:`, the working tree is clean, and no path conflicts. Otherwise, and when the fetch or the second push fails, the command fails as the plan states, with the entry and its commit kept. The accepted cost: one more code path, and a capture can bring other participants' entries into the checkout mid-command.

Rejected: failing as planned, for the frequent failed captures and delayed publication above; fetching and merging before every push, which costs a network round trip on every capture although nobody else pushed, and is still rejected when a participant pushes in between.

## Acceptance criteria

- [ ] With `auto`, a graph commit whose push is rejected because the upstream holds new graph commits is merged with them, with a merge message matching `^sdd:`, and reaches the upstream before the command returns.
- [ ] With `auto`, when the retry cannot merge (an incoming commit not matching `^sdd:`, a dirty working tree, a conflict) or its push fails, the command fails and the entry and its commit remain.
