`sdd merge-entry` signals a written conflict with its own exit code, 10, which the driver command maps to git's 1, so every other non-zero status, 1 included, takes the text-merge fallback. The fallback directive (20261030-093341-d-tac-t6j) reserved exit 1 for a written conflict, but `sdd` also exits 1 for any failure before a command runs, such as a malformed flag or environment value, so the driver reads that failure as a conflict and git keeps our side without markers (20261030-104530-s-tac-bz1, item 1).

**Command.** The configured driver becomes `sdd merge-entry %O %A %B %L %P; s=$?; [ $s -eq 0 ] && exit 0; [ $s -eq 10 ] && exit 1; git merge-file -L ours -L base -L theirs --marker-size=%L %A %O %B`. The upkeep rule of the fallback directive replaces the earlier value, since it starts with `sdd merge-entry`.

**Exit codes.** 0 merged, 10 conflict with markers written, 2 any other failure inside the command. Code 10 lies clear of 1, of 2 and 3, which argument errors and an older `sdd` answering an unknown command return, and of the shell's 126, 127 and signal statuses.

Rejected: keeping exit 1 and mapping errors in `main` to 2 when the subcommand is `merge-entry` (main must recognise the subcommand from raw arguments, and any later path that exits 1 on its own reopens the hole); accepting the risk (when it fires, the other side's change is silently gone). Accepted cost: the driver line carries one more test.

## Acceptance criteria

- [ ] With a malformed root flag or environment value, an entry whose summary both sides changed merges to a conflict with git's markers.
- [ ] `sdd merge-entry` exits 10 for a written conflict, 2 for any other failure inside the command, 0 when merged; git sees 1 for a conflict.
- [ ] A clone holding the earlier driver value gets the new one from the next sdd commit, merge, merge-pull or init.
