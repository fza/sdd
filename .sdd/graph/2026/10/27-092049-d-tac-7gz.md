The sdd binary and its MCP server work on a graph whose schema is older than the binary's. They read and write it at the graph's own schema, and only an explicit, user-confirmed `sdd migrate` upgrades it. A graph newer than the binary is still refused.

## Behaviour

1. For a graph at schema N and a binary at schema M with N < M, every write produces N's shape. A typed per-version capability table in `internal/model` (`SchemaCapabilities`, looked up by version) replaces the prose `schemaChanges` map. Every schema-gated producer asks it what version N supports.
2. At schema 1 this means no title model call and no `title` key. An explicit `--title` or `ExplicitTitle` is an error naming the graph's schema, never a silent drop. `sdd summarize --all` never writes a field the graph's version lacks. `actor_kind` is not schema-gated.
3. `sdd serve` and the write commands behind `withWriteGate` (`sdd new`, `sdd summarize`, `sdd wip start`, `sdd wip done`, sessions) no longer refuse an older graph. The engine resolves the graph's schema per write against the target checkout, since a `bind_branch` target is another checkout.
4. `sdd migrate` stays the only path that raises `graph_schema_version`, and it asks `Proceed? [y/N]` or takes `--yes` as today. No other command upgrades a graph or backfills fields of a newer schema.
5. `sdd info`, `mcp__sdd__info` and the serve banner show the graph's schema and the binary's, and say that writes happen at the graph's schema when they differ.
6. A graph newer than the binary and a binary below `minimum_version` are refused, as today.

## Decomposition

- `internal/model`: `SchemaCapabilities` by version. `CheckCompatibility` returns compatible with a write schema for an older graph instead of refusing.
- `internal/query` and `internal/finders`: `SchemaStatusQuery` returns the write schema.
- `internal/command` and `internal/handlers`: the new-entry, summarize and WIP commands carry the write schema, and their handlers consult the capability table.
- `internal/cliapp`: the write gate passes the write schema on instead of refusing. `sdd info` prints both schemas.
- `pkg/application`, `pkg/local`, `pkg/mcpapp`: target acquisition resolves the write schema from the acquired checkout per write, and the MCP `info` tool reports it.
- `internal/presenters`: the schema lines for `sdd info` and the serve banner.

## Why

`model.CheckCompatibility` refuses every write when the graph's schema is older than the binary's, and `sdd serve` sits behind the same gate, so a newer binary cannot capture in an older graph or serve it over MCP. A user on a newer binary is then forced to migrate a graph that other contributors still use with older binaries, or to stop working in it. Graphs kept on an older schema on purpose and upstream branches of a fork are the cases where a forced upgrade is wrong. An upgrade rewrites every entry and is a decision for the graph's owners, so it stays an explicit, confirmed act.

## Rejected alternatives

- Keeping the refusal. It blocks all work, including MCP, on graphs the user may not upgrade.
- Writing the binary's newest shape into an older graph. Older binaries and other contributors then meet fields their schema does not define, and the graph holds two shapes under one version number.
- Upgrading automatically on first write. It rewrites every entry without the owners' consent.
- Special-casing schema 1 and 2. The next schema bump would need the same work again; the capability table covers any pair.

## Accepted costs

The binary carries one write shape per schema version, and a producer missing from the capability table is a defect only tests catch. Entries written at an older schema lack the newer fields until the graph is migrated.

## Acceptance criteria

- [ ] On a schema-1 graph, `sdd new`, `sdd summarize`, `sdd wip start` and an MCP capture write entries without `title`, and no title model call happens. A test with a model stub that fails on any title prompt proves it.
- [ ] An explicit `--title` on a schema-1 graph fails with a message naming the graph's schema.
- [ ] A test enumerates the capability table and proves each schema-gated producer omits or refuses a feature the graph's version lacks.
- [ ] `sdd serve` starts on a schema-1 graph and an MCP capture there succeeds at schema 1.
- [ ] A graph newer than the binary, and a binary below `minimum_version`, are still refused through the CLI and MCP.
- [ ] No command other than `sdd migrate` changes `graph_schema_version`, and `sdd migrate` still asks for confirmation without `--yes`.
- [ ] `sdd info`, `mcp__sdd__info` and the serve banner show both schemas and the write schema.
- [ ] Each new guard is broken once and its test fails on its own assertion.
