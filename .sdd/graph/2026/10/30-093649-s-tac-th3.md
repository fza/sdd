An evaluation of the `sdd merge-entry` driver (20261030-092427-s-tac-lx2) on both lenses finds it working for two participants on one upstream but not ready to ship: an older `sdd` first on PATH turns an entry merge into a conflict that hides the other side, and a code review confirmed a set of robustness defects.

**Inner.** An independent read-only review of `ba2e0675` against `AGENTS.md`, each finding re-checked in the code, beside the passing test suite, clean lint and 16 caught guard breaks. Layering, error handling and external tests follow the project's rules, and every acceptance criterion holds on its tested path. The review confirmed one high defect: the driver writes git's file before the merge finishes, and every error exits 1, which git reads as a conflict, so a failure leaves a conflicted file without markers. It also confirmed medium defects: the driver setup runs before an entry commit and can block it, races on the config lock, is skipped by the WIP-removal commit, reads git errors as no repository, and caches a directory that was not yet a repository; frontmatter detection mishandles a requote-only side, a leading BOM and a flow-style mapping; init accepts absolute or glob graph directories and ignores write errors.

**Outer.** A smoke run on two clones of one bare upstream with the built binary: the clone that never ran init gained the driver from `sdd summarize`, and `git pull` merged two different summaries cleanly. A probe called the installed release, which lacks `merge-entry`, as the driver: it exits 3 and leaves git's file as our side alone. On a machine running a dev build beside a release, PATH order decides which runs, so this is the ordinary mixed-version state, and it is worse than git's own text merge. The fallback decision (20261030-093341-d-tac-t6j) removes it and covers the high inner defect.

Uncovered: Windows, a merge driven by automatic sync (`sync.mode: auto`, the `sdd serve` timer), and a live engine session over MCP.
