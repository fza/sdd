A capture can take its body from a staged file: the report names the staged handle instead of carrying the body, while every field still travels in the report. An agent drafting an entry in a file that a person reviews stops re-sending the text: in one graph-only project's 18 drafts the body runs about 1.7k tokens at the median and costs 3.5k to 7k output tokens per capture once adjust rounds re-send it, against 400 to 600 when the file is staged by path. On this graph the fields are about a fifth of a report (median 400 against 1,800 characters over 119 entries), so the body carries most of the saving.

**Header.** A staged body file may open with a block between two lines equal to `---`; the body is everything after the second. sdd compares only the block's keys whose name and value shape equal a report field: `entryKind`, `layer`, `confidence`, `intent`, `refs` as a list of id, kind and desc, `topics` as a list of strings, `closes` and `supersedes` as lists of full IDs. Such a key whose value differs from the report refuses the report, naming the key. Every other key is ignored, a block that is no valid YAML is ignored, and nothing is filled from the block.

**Hash and confirm.** Staging returns the body's sha256 beside the handle, and playback shows it beside the usual excerpt. A confirm binds to that hash: when the handle is re-staged after playback, the write refuses and playback runs again. Comparing the hash with the person's own file is the job of a client-side capture hook, which hashes its file and blocks the confirm on a mismatch. Which bytes the hash covers, and how they are normalized, is still open and needs its own decision. Body edits on a file body go to the staged file through staging patches, giving a new hash and a fresh playback; a body patch to the drafted body is refused for it. sdd never writes to the source file.

**Remote.** Staging by path needs a server that can read the path; a remote server takes the body once as content and edits through staging patches.

Rejected:
- The draft supplying the fields too: the last fifth of the saving, bought with a header-to-field path, a collision rule and edits that must land in the file; rewriting the header changes bytes a hook hashes.
- A strict header check: refuses every capture whose header uses its own key names and shapes.
- Skipping the header: a report drifting from the reviewed file goes unnoticed even for keys that could be compared.
- Refusing a header: forces a second, body-only file beside the reviewed draft, which can drift.
- sdd re-reading the path at confirm: runs only when the server shares the filesystem, reads outside staging a second time, and adds nothing over a hook.
- A reviewed-digest field on the confirm: one more field and an injected argument for a check the hook makes before the confirm is sent.
- Playback by hash alone, without the excerpt: breaks the rule that the user sees what they confirm.

Accepted costs: without a hook, an edit to the local file after staging goes unnoticed; the header check covers only keys a project writes in report form; playback still carries the excerpt.

## Acceptance criteria

- [ ] A report naming a staged handle and no body writes an entry whose body is the staged file's text after its header, with every field from the report.
- [ ] A report naming a staged handle and also carrying a body is refused.
- [ ] A header key equal in name and shape to a report field but different in value refuses the report, naming the key; other keys and a block that is no valid YAML are ignored.
- [ ] The staging result and playback both carry the body's sha256.
- [ ] Re-staging the handle after playback makes the write refuse and serves playback again.
- [ ] A body patch to a file body is refused; a staging patch to the handle gives a new hash and a fresh playback.
- [ ] A body staged as content works on a server that cannot read the client's paths.
- [ ] The source file is never written.
