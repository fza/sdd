When the commit at the end of `sdd init` fails, a re-run reports success while the files the first run wrote stay uncommitted. Init stages and commits only the paths the current run touched; the first run's files are already on disk, so the re-run touches nothing new and commits nothing. A code review in the split-init evaluation (20261029-142339-s-tac-yw8) found it by reading the handler's commit path, and the setup of a separate graph repository inherits it: a rejected commit there leaves that repository's config, meta and skills untracked while later runs succeed.

Expected, from the project's fail-loud rule (AGENTS.md): a failed commit is not swallowed, and a later run either completes the setup's commit or reports that it cannot. Actual: the first run fails loud, but every later run hides the state behind a success.

Candidate remedies, unsettled: commit init's whole managed path set when any of it is untracked or modified; or refuse while init's own files sit uncommitted, naming them.
