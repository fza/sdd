Up to release v0.18.0-alpha.2, sdd's LLM path lacks five pieces that running it on OpenAI-compatible services and reasoning models calls for: a system role those services accept, a response schema on structured checks, a JSON mode for services that refuse a schema, a configurable output cap, and a usage record a host can meter from.

Expected, from the commitment to reach any OpenAI-compatible service through a configured base URL (20260921-181638-d-cpt-cnu) and the structured-output directive (20261004-134853-d-cpt-sw8): requests to a configured endpoint use roles and parameters that service accepts, and structured checks carry a response schema where the provider takes one. Further, as natural expectations: a user can raise the output cap when a reasoning model spends its thinking against it, an answer cut at the cap reads as cut, and a host running sdd can meter each call's usage outside the repository.

Actual, read from the code at tag v0.18.0-alpha.2:
- The `openai` provider sends the system prompt under role `developer` to every endpoint (pinned `networkteam/gollm` fork, `PrepareRequest`). OpenAI-compatible services commonly know only `system`, `user` and `assistant` and answer 400.
- Pre-flight and the writing guide send no `response_format` on `openai` and no `format` on `ollama`, and one unparseable response fails the check.
- No setting chooses how a structured request asks for JSON. Felix Zandanel reports that some OpenAI-compatible services serve a model in `json_object` mode only and refuse a `json_schema` request for it, while another service accepts `json_schema` for the same model.
- The output cap is fixed at 4096 tokens in `internal/llm/gollm/gollm.go`, and a response that ended at the cap passes on as a complete answer.
- Call records go only to `.sdd/stats/llm.jsonl` inside an sdd repository, and `pkg/llm` carries no endpoint host, finish reason, reasoning tokens or provider billing data.
