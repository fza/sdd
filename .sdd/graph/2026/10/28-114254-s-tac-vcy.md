Up to release v0.18.0-alpha.2, every `sdd search` reloads the whole graph and the whole vector index whether or not either changed, and an index fill keeps searches waiting for as long as its embedding calls take.

Expected, as a natural expectation: a search over an unchanged graph and index costs little beyond scoring the query, and a long fill does not lock out readers while it waits on the embedding provider. An earlier observation (20260708-164936-s-tac-lcc) already suspected the per-invocation index load in slow CLI searches, without profiling it.

Actual, in v0.18.0-alpha.2, read in the code:

- A fill runs its whole write session, embedding calls included, under the store's exclusive lock (`index.WriteStore` in `internal/handlers/handler_index.go`). A CLI search, the MCP server's searches and a second fill wait until it ends, with no bound.
- Opening the index decodes chromem's gob files, one per indexed row. The MCP server keeps a decoded snapshot, but decodes every row again after any write and holds one mutex across each query.
- The graph loads by reading and parsing entry files one after another, and its revision reads and hashes every graph file each time it is computed.
- `sdd search` loads the graph a second time for its lazy fill, and embeds the query only after the graph has loaded.
- Loading the index manifest runs `EntryState`'s own JSON decoder per entry, which scans each entry's value again.
- Nothing reports which phase of a slow search takes the time.
