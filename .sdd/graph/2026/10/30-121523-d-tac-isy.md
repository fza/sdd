The sha256 that staging returns for a file body covers the staged file's raw bytes exactly as staged: the header block, line endings and any byte-order mark included, nothing trimmed or normalized. This settles the point the staged-body directive (20261030-120506-d-tac-l2b) left open, and its "body's sha256" means this file hash. A client hook needs no rule beyond hashing its file's bytes, the same in any language, and sdd hashes the staged blob as it already hashes stored blobs.

The hash is part of the staging tool's own answer, not only of the playback serve: a client hook sees tool inputs and answers, not serves it does not watch, so it records the hash when the file is staged and compares it with the local file then and again at confirm. A body staged as content must be the file's bytes unchanged; a body staged by path is that by construction.

A header-only edit changes the hash and reopens playback. That is wanted: refs and topics written in the header are part of what the person confirms. A client may keep its own hash of the body for other checks, such as a reviewer's verdict on the body; it lives beside this one and needs no agreement with sdd.

Rejected:
- Hashing the trimmed body after the header: sdd and every hook must agree on the header split and the exact set of trimmed characters. Go's `strings.TrimSpace` and Python's `str.strip` already differ on `\x1c` to `\x1f`, so a correct confirm could fail.
- Serving both a file hash and a body hash: two values in every staging answer and playback, and the trim rule still has to be pinned.

## Acceptance criteria

- [ ] The staging answer for a file body carries the sha256 of the staged bytes, equal to the sha256 of the source file's raw bytes, header, CRLF and byte-order mark included.
- [ ] Playback shows the same hash.
- [ ] Staging the same body under a changed header gives a different hash.
