A person who sets `sync.interval` gets their graph repository synced on a timer by every `sdd serve` they run, so other participants' entries reach an idle agent session without any sdd call, and several servers on one repository sync one at a time and report a merge conflict to exactly one agent. Automatic sync (20261028-000607-s-tac-h74) fetches only when a command or engine call runs, so a session that makes no call never sees others' movement, against the immediate feedback the sync directive aims at (20260817-162701-d-cpt-r8k).

**Host.** A ticker inside `sdd serve`, active while the server runs. Rejected: a standalone `sdd sync --watch` (one more process to start and keep alive, and agent sessions get no notice from it) and one loop serving both (two surfaces to keep and test). Accepted cost: nothing syncs on a timer while no server runs.

**Enabling.** The timer runs when `sync.mode` is `auto` and `sync.interval` is set, which, like `sync.mode` (20261027-211908-d-tac-l8j), only the user-global config or `.sdd/config.local.yaml` may set; setting it declares the repository graph-only. Rejected: deriving graph-only from every tracked file lying in sdd's paths (a README, LICENSE or CI file in the graph repository would silently turn the timer off) and the key plus that check (both costs). The graph repository cannot detect its role, since the `project_dir` pointer runs one way (20261027-192607-s-tac-baf). Accepted cost: a person can enable it in a code repository, where a timed merge moves the branch they work on; the clean-tree and graph-path pull rules still hold there. Below one minute, malformed or committed values are ignored with a warning, per the config rule (20260921-174543-d-cpt-tv9).

**Lock.** Two agents in one code repository each run their own `sdd serve` against the same graph repository; unsynchronized, both would fetch, merge and find the same conflict. One file lock per graph repository, in its git directory, serializes every sync path in every sdd process. Timer and cooldown rounds try the lock and skip silently when it is held; the publish after a graph commit waits for it, since a commit must reach the upstream before the step responds. A killed process frees the lock with it.

**Conflict notice.** A round that finds a conflict records it in a marker beside the lock. The first call any server then receives, step or read, claims the marker under the lock and carries the notice; every other agent stays silent, and the marker goes once the `sdd: merge <upstream>` commit lands. Read responses carry it in a `sync_notice` field, which resolves the dropped-notice gap (20261028-003729-s-tac-mz0); the claim runs in the application layer and finders stay pure. Rejected: a leader holding the lock for its lifetime, or the detecting server owning the conflict (the notice can sit with an idle agent; pid reuse), served steps only (a reading agent stays unwarned), MCP notification push (unverified that clients show it to the model, while it would count as delivered). Accepted costs: a marker file with a delivered flag; every read response grows a field; a read writes that runtime file, never the graph.

**Cooldown.** Each round stamps the existing last-fetch marker, so a call within `sync.cooldown` of a round fetches nothing more. Rejected: the timer replacing per-call fetches in `sdd serve` (serve and CLI diverge; data up to one interval old) and independent clocks without a floor (double fetches; a tiny interval hammers the remote).

Not committed: `sdd sync --watch`, service files, MCP notifications, detecting graph-only trees.

## Acceptance criteria

- [ ] With `sync.mode: auto` and `sync.interval` of at least `1m` in the user-global config or `.sdd/config.local.yaml`, a running `sdd serve` fetches, merges upstream graph commits and pushes local graph commits once per interval with no tool call in between.
- [ ] No timer runs when `sync.interval` is unset, `sync.mode` is `manual`, or the interval is malformed, below `1m` or set in the committed config; each such value is reported as a warning naming file and key, every command still runs, and `sdd config set sync.interval` refuses it.
- [ ] A timed round applies every automatic sync rule unchanged: whole-branch `^sdd:` push and pull, the graph-path pull limit, the clean-tree requirement and the `sdd: merge <upstream>` message.
- [ ] Two sdd processes on one graph repository never fetch, merge or push at the same time, shown by a race-enabled test running concurrent rounds against one bare remote.
- [ ] A timer or cooldown round that finds the lock held skips without output; a publish after a graph commit waits for the lock and still reaches the upstream before the command or step returns.
- [ ] Stopping or killing `sdd serve` stops its timer and leaves the lock free.
- [ ] A conflict found by any round reaches exactly one agent: the first call after it was recorded, from any server, carries the notice, and no other call does.
- [ ] Read responses (search, show, view, info and the other reads) carry an undelivered notice in a `sync_notice` field; served steps carry it ahead of their instructions.
- [ ] Once the `sdd: merge <upstream>` commit lands, the marker is gone, automatic sync resumes, and a later conflict is delivered anew.
- [ ] A call within `sync.cooldown` of a timed round does not fetch.
