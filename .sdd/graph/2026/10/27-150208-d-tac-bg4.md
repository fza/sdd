Every read beyond the local graph reaches the declared closure (20261026-194528-d-cpt-gcq) through one cache reader, one walk step and one optional refresh on the CLI side and one closure walk in the application, while the local composition resolves any cached closure member on demand.

- `repos.Cache`, from `Registry.Cache(repoID)`, is the only reader of a connected repository's cache: `Config()` parses its committed `.sdd/config.yaml` through `meta.ReadCommittedConfigFS`, `GraphDir()` derives the graph directory from it, and their errors name the repository. It replaces `repos.GraphDir`, the reader behind `repos.DeclaredRepoID`, and the reads in the closure step and the local composition.
- `Finder.DeclaredDependencies` is the walk's pure step: the local repository from its config, a connected cached repository from `Cache.Config`, anything else nothing. The finder's closure walks it, and CLI search, view, `sdd index`, export and `<repo-id>:<entry-id>` resolution select from that closure; naming a repository outside it is an error.
- `Handler.RefreshDependencyClosure` walks the closure refreshing each repository before reading its declarations, so a configuration repaired upstream is pulled before it is read. The refresh is optional to the command that runs it: a failed clone or pull reaches the caller through `OnRefreshFailed(repoID, err)` and a closure member not connected on this machine through `OnUnconnected(repoID)`, callbacks on `RefreshDependencyClosureCmd` that its validation requires so no caller drops a warning; the CLI passes its own warning printer and reads the caches as they stand, and the engine side can map the same callbacks to typed warnings. Every CLI command that reads a dependency graph runs it first, replacing `freshenRepoCaches`, the repository selection in the search prepare step, and the recompute-until-stable loop 20261005-155120-d-tac-5vj chose for export, which read cached configurations before refreshing them. Side effects stay in a handler ahead of a pure read, the placement 20260707-175137-d-tac-i6f set for cross-repo search. This is the first piece of the shared refresh the engine path lacks; running it from the engine stays with 20261027-145612-s-tac-2n5.
- The application walks the closure once per request and keeps the runtime it resolved per repository; search, view, `<repo-id>:<entry-id>` reads, attachments and the horizon's member graphs, now loaded on first use, select from it, while bare IDs keep resolving among the direct dependencies.
- The local composition resolves any connected, cached repository on demand from its cache, as one runtime carrying its own language and dependencies, the shape the session-model design record specified (20260903-152247-d-cpt-yjc). It replaces the map built eagerly at startup for the direct dependencies and its pair of member and full runtimes; every use of a dependency runtime reads only that dependency's own snapshot, so one runtime serves both.

Why: on 2026-10-26 the local composition built runtimes only for the home project's direct dependencies, so `sdd serve` refused a cached second-level dependency the CLI could read; two readers parsed the same cached configuration with different rules for a missing file; and the export loop could not recover a configuration repaired upstream once its cache held a broken one, the second finding of the review on pull request #23.
