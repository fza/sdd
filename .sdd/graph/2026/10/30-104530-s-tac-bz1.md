The `sdd merge-entry` driver as shipped in `800c163e` (20261030-095321-s-tac-dfk) can still drop the other side of a merge, route the wrong graph directory, or merge an entry into a file that no longer loads, as an independent review in the evaluation (20261030-104151-s-tac-51l) reproduced.

1. A failure before the `merge-entry` action, such as a malformed `SDD_TIMING` value, exits 1 from `cmd/sdd/main.go`, which the driver command reads as a written conflict, so git keeps ours without markers and skips the text-merge fallback. Expected, per the fallback directive (20261030-093341-d-tac-t6j): only a written conflict yields 1; every other failure reaches the fallback.
2. `sdd init` on an existing project takes the graph directory only from `--graph-dir`, else `.sdd/graph`, so a project configured with another `graph_dir` gets a `.gitattributes` line its graph never matches, without a warning. Expected: init routes the configured graph directory.
3. A field absent in base and added on both sides at different lines survives twice, the merge exits 0 and the entry then fails to load on the duplicate key. Expected: one value, or a conflict.
4. A config-write failure after a landed commit returns an error, so auto-sync skips the push; the re-read after a failed write checks only the `driver` key. Expected: setup trouble never costs the push of a landed commit.
5. An older `sdd` on PATH runs its full startup, sync check included, inside git's merge before failing over. Expected: the driver command runs nothing beyond the merge.
6. The commit path behind `sdd serve` and the MCP application never sets the driver up, so a clone capturing only there text-merges on a plain `git pull`. Expected: every sdd commit path ensures the driver.
7. Init refuses a graph directory with a space only after writing `.sdd/config.yaml`, leaving a half-initialized project that fails the same way on rerun. Expected: validation before any write, and a quoted pattern where gitattributes allows one.
