A project that switches automatic sync on keeps its graph published and current without anyone running git: every graph commit reaches the branch's upstream right away, upstream graph commits arrive on their own, and a conflicting merge is resolved by the agent, which asks the user only when the right resolution is unclear. Everything happens in the repository holding the graph; in a project_dir layout the work repository is never fetched, merged, committed to or pushed.

The plan settles the mechanism and configuration the sync directive (20260817-162701-d-cpt-r8k) left open and answers the gap on unpublished graph changes (20260430-212941-s-tac-jnd). It keeps that directive's whole-branch safety rule: sdd pushes only when every unpushed commit on the branch matches `^sdd:`, pulls only when every incoming commit does, merges instead of rebasing with a merge commit carrying an `sdd:` message, and reports instead of acting when the rule does not hold. A graph in its own repository satisfies the rule by construction.

It departs from that directive in one respect: sync is opt-in. `sync.mode` in `.sdd/config.yaml` takes `manual`, the default when unset, or `auto`. Any config layer may set it, so the committed project file switches it on for every participant, `config.local.yaml` for one, the user-global file for every graph on one machine. A default-on sync, as the directive reads, was rejected because it makes network calls nobody switched on; the accepted cost is that projects which never set it keep their captures unpublished, and the departure needs agreement upstream. Rejected names: a `sync.auto` boolean, the config's first, which needs a pointer type to layer and a new key for a third mode; `sync.push`, which undersells pull and merge.

Timing: a push follows each graph commit in the same CLI command or engine step, bounded by a timeout. A failed push returns an error on that command while the entry stays committed, per the fail-loud rule; working offline therefore turns each capture red until a push succeeds, accepted for captures reaching others within seconds. Pull rides the background sync check (20260423-144715-s-tac-2y0), which fetches at the start of a CLI command once the `sync.cooldown` interval, 15 minutes by default, has passed since the last fetch, and it also runs on engine interaction. Pushing and pulling only on the cooldown was rejected: a capture would reach others up to a cooldown late, and a failed push would surface on an unrelated later command.

Conflicts: the engine aborts a conflicting merge, leaving the tree clean, and serves the agent a resolve step holding both versions of each conflicting file. The agent reports the resolved content through the step, putting the choice to the user when the right version is unclear, and the engine writes it and commits the merge with an `sdd:` message, then pushes. A table of fixed resolution rules was rejected for its maintenance and because a rule preferring upstream silently drops a local edit; report-only, as the directive reads, breaks the quiet flow for the rare conflict. Conflicts are rare in a graph repository: new entries add new files, so only edits to existing files collide (summary and title rewrites, `lint --fix`, WIP markers, `meta.json`, `.sdd/config.yaml`).

Git runs through the adapter of the repository holding the graph: the CLI's `graphGit` and the engine's `GitFinalizer` checkout, both of which already target that repository. The work lands on branch feat/graph-repository, which introduces that routing, so a single pull request carries the separate graph repository and its sync.

Decomposition, per the CQRS planning contract (20260413-142536-d-cpt-ah1). Model, pure: `SyncMode` (`manual`, `auto`) on `SyncConfig.Mode`, validated at config load; `PushVerdict` and `PullVerdict`, decided from commit counts, upstream presence and working-tree state; the `sdd:` merge message; `MergeConflict{Path, Base, Ours, Theirs}`. Queries and finders: `SyncStatus` also counts unfiltered commits in each direction, so the rule compares real totals instead of the filtered count standing in for them; a `MergeConflicts` query reads the three versions of each conflicting path from git objects. Commands and handlers: `PushGraphCmd` through `Handler.PushGraph` behind a new `Pusher` git interface; `PullGraphCmd` through `Handler.PullGraph`, which merges with the `sdd:` message, aborts on conflict and returns `ErrMergeConflict`; `ResolveMergeCmd`, carrying resolved content per path, through `Handler.ResolveMerge`, which writes, commits and pushes. The push after a CLI commit lives in the handler: one commit helper commits and then runs `PushGraph` when the mode is `auto`, and every handler commit site uses it. A committer decorator applied at CLI composition was rejected: it would put a side effect and the push decision in an adapter outside the handlers, and it could not report captured-but-unpublished entries through the handler. CLI: the background sync check runs `PullGraph` when the mode is `auto`. Engine: `application` declares a `GraphSync` port implemented in `pkg/local` over `internal/git`; `GitFinalizer` pushes after its commit; the session runtime pulls on interaction; a conflict dispatches a new base procedure, `merge-resolve`, whose step serves both versions and whose op commits the reported resolution through the port.

Out of scope: creating an upstream for a branch without one (reported instead), pulling into a dirty working tree (reported instead), sync for graphs read through connected-repository caches, and any mode beyond `manual` and `auto`. Every test runs against local bare repositories, never a network remote.

## Acceptance criteria

- [ ] `sync.mode` accepts `manual` and `auto` in every config layer, an unset value means `manual`, a higher layer overrides a lower one, and an unknown value is refused at config load naming the key.
- [ ] With `manual`, no command or engine step pushes or pulls.
- [ ] With `auto`, a graph commit from a CLI command reaches the branch's upstream before the command returns.
- [ ] With `auto`, a graph commit from an engine step reaches the branch's upstream before the step's response.
- [ ] With `auto` and an unpushed commit not matching `^sdd:` on the branch, nothing is pushed and the command reports the entries as captured but unpublished.
- [ ] With `auto` and a branch without an upstream, nothing is pushed and the command reports it.
- [ ] A failed push returns an error on the command or step that committed, and the entry file and its commit remain.
- [ ] With `auto`, upstream commits all matching `^sdd:` are merged on the cooldown-gated check and on engine interaction, the merge commit's message matches `^sdd:`, and the next push succeeds.
- [ ] With `auto`, incoming commits not all matching `^sdd:`, or a dirty working tree, block the pull and are reported.
- [ ] A conflicting merge is aborted with the working tree clean, the agent is served both versions of each conflicting file, and the resolution it reports is committed with an `sdd:` merge message and pushed.
- [ ] In a project_dir layout with `auto`, a command run in the work repository leaves that repository's HEAD, refs, index and remote-tracking branches unchanged while the graph repository syncs.
