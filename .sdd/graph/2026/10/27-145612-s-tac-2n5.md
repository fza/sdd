In engine mode no dependency cache is ever refreshed: `sdd serve` and the application never clone or pull a connected repository, so a dependency's cache stays as `sdd repo add` or the last CLI read left it, a closure member that was never cloned stays unreachable, and a session left open for days reads the same caches throughout.

Actual, from a code audit on 2026-10-26: every clone and pull runs in CLI commands (show, view, search, index, export and repo in `internal/cliapp`, through `internal/handlers`); the application uses `internal/handlers` only for its two search-index handlers; fetch-on-miss, the forced pull when a capture references a dependency entry its cache lacks, runs only inside `sdd new` (`internal/handlers/handler_new_entry.go`), never in a capture through the engine. Served instructions may not send the agent to the CLI (20260707-134311-d-cpt-476), so an agent working through the engine never causes a refresh.

Expected: the closed cross-repo plan committed that cross-repo resolution inside an engine session reads the live cache, with a cooldown pull and fetch-on-miss at capture (20260707-175137-d-tac-i6f). Nothing on the application's path carries that commitment today. Christopher's expectation: dependencies stay current in the background while a session runs. A refresh is optional to the operation that triggers it: the operation reads the caches as they stand and, once the cooldown has passed, starts a refresh whose result the next operation sees, so an unreachable or failing git remote never blocks or fails other work, including the start of a stdio MCP server, which a user cannot inspect when it hangs or exits. A failed refresh shows as a visible warning wherever the operation reports, in session framing and in the result of a search, view or show, and as a warning on the CLI. The orchestration lives once in shared code rather than in each adapter, while each adapter renders the typed warnings its own way. Fetch-on-miss at capture stays synchronous, since a write gate needs the fresh state. The same need for the local graph is decided in 20260817-162701-d-cpt-r8k, fetch on interaction gated by a threshold and a report rather than silence, and has no plan or delivery below it.

Observations bearing on that change. Git runs through `exec.CommandContext` (`internal/git/cache.go`), which kills with SIGKILL, so a clone cancelled at a deadline can leave a partial `.git` that counts as cloned, and a cancelled pull a stale `index.lock`. Two report channels exist: `graphHealthBlock` in `pkg/application/workflow.go` lists graph warnings in session framing, and `SearchResult.Notice` tells a search that indexing is incomplete while it shows what is available; neither carries a refresh outcome, and no route leads from the composition that would run the refresh to them.
