An evaluation of the per-person `dialogue.mode` setting (20261029-150854-d-tac-b2f) on branch `pr/feat-autonomous-dialogue` finds it sound and working in use, both lenses covered.

Inner: the code of commits `1835c446`, `034e7b61`, `03f18c94`, `eeb22b54` and `972efd95` read against the six acceptance criteria, each held by tests at the layer that owns it: config layering and the ignored committed or unknown value in the model, `config set` in the handlers, the session header and its replay, the delegable mark and the answer rules in the engine, the shipped procedures through the real application, the resume and conclude texts in the MCP surface, and `--dialogue-mode` in the CLI. Every new guard was broken once and its test failed on its own assertion. Breaking the refusal of a reason at a non-user choice, or of an answer carrying neither words nor reason, lets the reserved-choice refusal answer instead; the tests tell them apart by wording. The interactive question in `sdd init` lies beyond the tests and was covered by the run below.

Outer: the built binary, in a folder outside every repository, took a fresh repository through `sdd init` in a pseudo-terminal, answering the dialogue question with autonomous; the answer landed in `.sdd/config.local.yaml`. Served over MCP by `sdd serve` to a scripted client, the session opened with the autonomous wording and a `reason` field, an agent's conclude with a reason ended it, and the session log recorded the mode, its source file, and the answer as the agent's with its reason. With the mode moved into the committed config, sdd warned naming file and key, the session served the guided wording, and the same conclude was refused. `sdd config set` refused an unknown value.

Not covered: a real agent carrying a whole autonomous session, and use in a project that runs sdd sessions through agents working on their own, the use the directive was requested for.
