On a graph whose `.sdd/meta.json` records no graph schema version or version 0, `sdd info --format json` reports that titles can be written, while every write refuses the graph.

Observed with `.sdd/meta.json` holding `{}`: `sdd info --format json` omits `graph_schema` and reports `capabilities.titles` true; `sdd new --dry-run --title X` refuses with "graph schema version 0 is unknown to this binary".

Expected: info's capabilities describe the schema writes use, by the write path's own rule (20261027-122627-d-tac-2cx), and writes happen at the graph's recorded schema (20261027-092049-d-tac-7gz). A `meta.json` without a valid version is refused the same way by both, since the doc of `model.SchemaMeta` names `graph_schema_version` required.

Where the deviation sits, from code reading: the rule choosing the write schema (recorded version, else the binary's, then the capability lookup) is written three times, in `internal/finders/info.go`, `internal/handlers/write_schema.go` and `pkg/application/graph_schema.go`. The finder treats a recorded 0 as unrecorded and drops the lookup error; the other two pass 0 to the lookup and fail. `model.ParseSchemaMeta` accepts the missing or 0 version. Surfaced by the evaluation of the info JSON delivery (20261027-130606-s-tac-tca).

Candidate remedy, not settled here: one write-schema function in `internal/model` that all three call, and `ParseSchemaMeta` refusing a version below 1.
