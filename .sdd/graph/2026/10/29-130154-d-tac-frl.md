`sdd init --project-dir <path>` run in a work repository sets up the sdd project at `<path>` itself when `<path>` holds none, then points the work repository at it, so a split setup takes one command. Felix Zandanel asked for it: the `project_dir` layout (20261028-115146-s-tac-15i) refuses a `<path>` without `.sdd/config.yaml` and `--graph-dir` or `--language` beside `--project-dir`, so a new split project took two runs in fixed order, the first inside the other repository.

What the command does when `<path>` holds no sdd project:

- `<path>` missing is created; a `<path>` outside any git repository gets `git init`; a `<path>` that is the root of its own repository, such as an empty clone, is used as it stands, and its remote derives `repo_id`. A `<path>` inside the work repository, or inside another repository whose root it is not, is refused, naming that repository.
- The project's setup is a plain `sdd init` in `<path>`, since the project works on its own (20261027-192607-s-tac-baf): `--graph-dir` and `--language` configure it, prompted on a terminal as on any fresh init, `--language` required without one. `--participant`, `--agents` and `--scope` serve both repositories. It commits in `<path>`.
- The work repository then receives the pointer config and agent surfaces as today, committed there: one commit per repository.

An existing sdd project at `<path>` keeps today's behaviour, and `--graph-dir` and `--language` stay refused beside it, since they configure the project.

Rejected: keeping two runs in fixed order. It spares one command writing and committing in two repositories, but costs every new split project a step in another directory whose order the error messages must teach.

Accepted costs: init writes and commits in two repositories in one run. A failure after the project's commit leaves the project set up and the work repository not; a re-run finds the project and finishes as today's path.
