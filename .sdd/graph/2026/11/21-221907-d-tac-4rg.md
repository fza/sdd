A capture's graph check, the reading `gather` runs for a draft, keeps its topic listings, takes its searches from the agent, orders the merged candidates before the ranking judge scores them, and bounds the judge by a time setting with a minimum number of judged entries.

The check is the reading designed in 20261109-004506-d-cpt-udz. Its judge is the one ranking judge of 20261118-162927-s-tac-pq5.

## One check for every graph size

Every check runs the searches, lists the draft's topics and orders the merged candidates, whatever the graph's size. The all-entries list for small graphs is removed.

Today a graph below `verify.brief_all_below` live entries, 100 by default, gets every live brief and no search (`gatherOn` in `pkg/application/gather.go`). One path leaves fewer code paths and variants to test.

Consequence: a check on a small graph runs the searches and needs the embedding model, as a larger graph's check does today (`checkEmbedder`). The `verify.brief_all_below` setting loses its only use.

Rejected: the all-entries list kept below that count. It is a second code path with its own variants to test.

## Topic listings stay

Every live entry of the draft's topics reaches the judge. The judge scores one combined list: the topic listings, the keyword searches and the vector searches together.

A topic listing shows the agent entries that relate to a topic from an angle its searches do not cover.

Rejected: a cap per topic listing, and a check without topic listings. Either hides entries that only a listing finds.

Accepted cost: the list the judge scores grows with the size of the draft's topics. The time limit and the minimum below bound the wait.

## The agent writes the searches

The agent passes a search phrase and keyword terms into the capture's check. sdd always adds one vector search with the draft's own text. The model call that writes the searches is removed.

Today `llmops.GatherQuery` writes the phrase and the terms through the main `llm` block, on every check of a graph with at least `verify.brief_all_below` live entries, 100 by default. The session log records the searches it wrote, but no later check reuses them, and its failure fails the check (`gatherSearches` in `pkg/application/gather.go`). A capture cannot pass searches of its own: `WorkflowGatherRequest` has no field for them, and `sdd gather --session` refuses `--query` and `--term`.

The agent holds more context for writing the searches than the draft text gives a model. The rule for them is the search-angle directive 20260826-104421-d-prc-8t0: one query per hypothesis about how the sought entry was written. The step that takes the searches serves that rule.

Accepted cost: a weak agent writes poor searches. The draft-text search, the topic listings and the judge then carry the check.

Rejected:

- The call kept on the judge's model and stored per draft. It stays a model call and a point of failure, and it sees the draft only.
- No change. Every check pays a model call whose failure fails the check.

## Order before judging

The merged candidates go to the judge in this order:

- Reciprocal rank fusion over the ranks the searches gave their hits. `sdd search` fuses its hybrid mode the same way (`rrfFuse` in `internal/finders/search.go`).
- Entries only a topic listing found have no search rank. Their similarity to the draft orders them.
- On a tie, an entry one reference hop from an entry the draft references comes first, and an entry of kind done comes last.

No model call orders the list.

Which reads found an entry is used inside sdd only: in this order, and in the rule of 20261121-205340-d-tac-gyk that never sets aside a candidate two or more reads of the check found. The agent's line does not show it. Today `gatherLine` in `internal/presenters/gather.go` prints it as `found by`. On the line it is a second ranking beside the judge's score, and it weighs against the entries only a topic listing found.

Inside the check, this gives the fused, de-duplicated result over several probes that the gap 20260702-204144-s-tac-j5a asks for. A multi-search call for free reads stays open there.

Today `GatherCandidates` in `internal/model/grounding.go` orders by the number of reads that found an entry, then by entry ID. A hit's rank within its search is dropped. Under a time limit, which entries the judge reaches is then partly arbitrary.

Accepted cost: one similarity lookup per check.

Rejected:

- Similarity to the draft alone. It ignores the keyword hits.
- Today's order, for the reason above.

## Entries of kind done

A done entry with a judge score ranks by that score like any other entry. It ranks last only without a score or among equal scores. This holds for the graph check and for the deep verifier's reading.

The verifier's reading ranks done entries last today (20261118-173708-d-tac-euf). This plan narrows that rule to unscored and tied entries. That directive's rule that a done entry never serves in full is not changed here. What the agent and the verifier receive of a ranked entry is decided in a separate plan. This plan decides how candidates are found, ordered and judged.

Measured on five graphs, this repository's and four other software development projects: done entries are 3% to 36% of the entries and receive 1% to 17% of the reference edges (refs, closes and supersedes). On this repository's graph they are 32% of the entries and receive 17% of the edges. A done entry is needed less often than its share, but not never.

Rejected:

- Always last. A needed done entry would always sit at the bottom.
- No rule for done entries. An unscored list would hold up to a third finished work in arbitrary places.

## Judge time and the minimum judged

- The judge's time limit on a live check is a setting. The default is 1 minute. 0 means no limit. A value above 0 and under 30 seconds counts as 30 seconds, because no shorter limit is useful. Today the pass ends after a fixed 45 seconds (`prefilterDeadline` in `pkg/application/prefilter.go`).
- The minimum number of judged entries is a setting. The default is 50. It is a count and never a percentage: a percentage grows with the list, so the wait would grow with the graph.
- The time runs out with fewer entries judged than the minimum, and the list holds more. If at most 10 are missing, sdd keeps judging and waits longer. If more are missing, or the count stays below the minimum after that wait, sdd tells the agent "only x of y judged", or that the judge failed altogether. The person then chooses: wait until the minimum is judged, or the whole list where it is shorter than the minimum, or go on and let the agent judge.
- A session without a person at the check has nobody to choose: `dialogue.mode` `auto`, and `assisted`, whose person only approves the checked draft (`DialogueMode.AgentAnswers`). There sdd waits one further time limit in place of the choice. If the count is still below the minimum, the agent judges from the lines of the list. sdd writes the shortfall to the session log and the server log. No field or mark on the entry records how its check went.
- Background calibration pauses while a live check judges. Today it scores at once until the next recall stage holds (20261119-105440-s-tac-5et), beside any live check.

Accepted cost of the rule for a session without a person: up to one further time limit per check, 1 minute by default.

Rejected for a session without a person:

- Park the check for a person. An unattended job stalls whenever the judge is slow or down.
- The agent judges at once. A judge that needs a few more seconds is not waited for.
- A note on the entry that only x of y were judged. An entry carries no metadata on how it was grounded.

## What the message names

With "only x of y judged" sdd names the cause, and suggests `sdd grounding update` only where the command helps:

- The judge is unreachable or fails: the error, no suggestion.
- The judge answers but is too slow for the list: sdd says so and names the time limit by its value only, not the setting's name or where to set it.
- The judge holds no recall stage, or a lower one than its unscored labelled pairs would give: sdd suggests `sdd grounding update` with the counts.
- Background calibration is running: sdd says so with x of y scored, no suggestion.

Accepted cost: sdd must tell these causes apart.

Rejected:

- Always name the command. The advice is wrong when the judge is down or slow.
- Never suggest it. The person would have to find the cause through the status command.

## Links and time do not change the order

Links between candidates and the age of an entry change no score and no rank. A list line whose entry a newer entry refines names that newer entry.

A measurement re-ranked the stored judge scores of the same five graphs, with no new judge call. The tables are in the [link re-ranking measurement](./21-221907-d-tac-4rg/link-reranking-measurement.md). The four other graphs appear there as project A to D. A needed entry is one the draft references. Three sets of lists were re-ranked: small lists of 62 to 67 candidates and large lists of 184 to 764 candidates, each with 50 drafts and 179 needed entries, and replay lists of 88 to 100 candidates with 200 replayed entries and 676 needed entries.

The judge's own order, as the share of needed entries in the top 10, in the top 30, and their mean rank:

- small lists: 0.962, 1.000, 3.46
- large lists: 0.848, 0.953, 9.66
- replay lists: 0.875, 0.965, 6.41

The variants:

- Link lift, a score plus 0.25 times the highest score among linked candidates: 0.967, 1.000, 3.44 on the small lists, 0.838, 0.947, 7.41 on the large lists, 0.872, 0.970, 6.10 on the replay lists. Every 95% interval of the change over the five graphs includes zero. None of the 8 needed entries outside the top 30 on the large lists reaches it. On this repository's replay lists, the only ones built by embedding search, the mean rank worsens from 5.75 to 5.90. The lift puts 2.5 to 3.8 non-needed entries per list into the top 30.
- Refinement pairing, where a candidate takes the highest score among itself and the candidates joined to it by a refines, supersedes or closes link: harm. The top 10 share on the replay lists falls from 0.875 to 0.806, and to 0.638 over whole chains of such links. A refinement link does not say which end the draft needs. Of the replay pairs with a needed end, both ends are needed in 133, only the newer in 521, only the older in 545.
- The newer entry first among equal scores: no measurable effect. On the replay lists 157 needed entries move up and 167 move down.
- Link lift only over links whose two ends share a topic: no better, mean rank 6.52 on the replay lists.

A linked candidate with a higher score is as common for a non-needed entry as for a needed one: 56.8% against 48.8% on the replay lists. A second run of the judge alone moves ranks more than any variant gains: on the small lists the mean rank of needed entries goes from 3.46 to 3.30.

A lifted score must also stay out of the known-far line of 20261121-205340-d-tac-gyk (`model.FarFloor`). Lifted scores against the stored line cut the share it sets aside on the large lists from 58.6% to 25.8%.

Limits of the measurement: the small and large lists are padded with random earlier entries. The small lists sit at the ceiling. A shared topic stands in for nearness in meaning, since no embeddings were used. The weights were not tuned. An unreferenced entry that bears on the draft counts as non-needed.

Accepted cost: a few more characters on the lines that name a newer refinement.

Rejected:

- Score arithmetic over links or time. The measurement shows no reliable gain, and harm from refinement pairing.
- The link as evidence in the candidate's line the judge reads. It is untested, and testing it costs about 1.50 US dollars of judge calls first.
- No mention of the newer refinement.

## Where the pieces live

The check stays a read. It gains no write intent beyond the read record it writes today.

- Shells, parsing only: the MCP `gather` tool (`pkg/mcpapp/tools.go`) and `sdd gather --session` (`internal/cliapp/gather.go`) take the search phrase and the keyword terms and pass them on in `WorkflowGatherRequest`.
- Read intent: `GatherRequest` in `pkg/application/gather.go` carries `Query` and `Terms` already. `gatherOn` loses its all-briefs branch. `gatherSearches` runs the agent's searches and the draft-text search. `llmops.GatherQuery` and its prompt are removed.
- Model, pure: the merged order beside `GatherCandidates` in `internal/model`, fed with the similarity values the application looks up. The done rule where scores rank candidates: `PlacePrefiltered` and the verifier's lanes in `internal/model/verifier_lanes.go`. The two settings and their resolved values on `VerifyConfig`. The cause of an "only x of y judged" message as a function of the judge's outcome, its recall stage and the state of background calibration.
- Application: `runPrefilter` in `pkg/application/prefilter.go` applies the time limit and the minimum, keeps judging, and returns the judged count with the cause. For a session without a person it waits the further time limit and logs the shortfall. The background calibration in `pkg/application/auto_calibration.go` waits while a live check judges.
- Result and rendering: the message and the two ways to go on travel in the `gather` result. The agent puts the choice to the person, or judges from the lines where the session has none. `gatherLine` in `internal/presenters/gather.go` names the newer refinement and stops printing which reads found the entry.

## Acceptance criteria

- [ ] Every live entry of the draft's topics is in the list the judge scores, together with the hits of the keyword and vector searches.
- [ ] A capture's check takes a search phrase and keyword terms from the agent.
- [ ] Every check runs one vector search with the draft's own text, on a graph of any size.
- [ ] No model call writes the searches of a check.
- [ ] No check sends every live brief in place of searching. A graph below 100 live entries gets the searches, the topic listings and the merged order.
- [ ] In every check the candidates reach the judge ordered by reciprocal rank fusion over the searches' ranks, with entries only a topic listing found ordered by similarity to the draft.
- [ ] On a tie in that order, an entry one reference hop from the draft's references comes first and a done entry last.
- [ ] A done entry with a judge score ranks by it in the graph check and in the deep verifier's reading. Without a score or among equal scores it ranks last.
- [ ] The judge's time limit is a setting: 1 minute by default, 0 for no limit, a value above 0 and under 30 seconds read as 30 seconds.
- [ ] The minimum number of judged entries is a setting with the default 50, read as a count.
- [ ] When the limit ends at most 10 entries short of the minimum, the check keeps judging past the limit.
- [ ] When it ends more than 10 short, or the judge fails, the agent receives "only x of y judged" or the failure, and the person chooses between waiting and the agent judging.
- [ ] For a session without a person, the check waits one further time limit in place of that choice. Still below the minimum, the agent judges from the lines.
- [ ] The session log and the server log record such a shortfall. No field of the written entry does.
- [ ] That message names its cause as one of the four cases, names a time limit by its value only, and suggests `sdd grounding update` only where the judge lacks a recall stage its labelled pairs would give.
- [ ] Background calibration sends no judge call while a live check judges.
- [ ] A list line whose entry a newer entry refines names that newer entry.
- [ ] The agent's line does not show which reads found an entry.
- [ ] No link between candidates and no entry date changes a score or a rank.
