The full-content fetch in sdd-owned clones (20261107-224549-d-tac-r9q) runs with `-c fetch.unpackLimit=1`, and in the same gate admission sdd runs `git backfill --sparse HEAD..@{u}` before the offline merge; with git older than 2.55, sdd runs neither the backfill nor the lazy fetch bar, `GIT_NO_LAZY_FETCH=1`. The [probe record](./08-104247-d-tac-k6f/full-content-fetch-probes.md) holds the numbers and scripts.

**Delta bases.** A fetch sends changed files as deltas against their versions in the commits the clone already has. In a clone of a code repository that holds its graph, those versions are missing for every file outside the sparse set, so git fetches them during the fetch. A fetch of fewer objects than `fetch.unpackLimit` goes through `unpack-objects`, which fetches each missing base on its own: five missing bases opened five connections. With `fetch.unpackLimit=1` every fetch goes through `index-pack`, which fetches them in one batch. Measured on 179 commits of this repository, the fetch opens two connections and the merge none. Both connections run inside the admission, so the gate counts them. The one connection per round that 20261107-224549-d-tac-r9q states holds for a repository whose files all lie in the sparse set; a code repository holding its graph opens two.

**Backfill.** A clone holding upstream commits fetched without contents and not yet merged, as an sdd from before 20261107-224549-d-tac-r9q leaves it, cannot merge offline: the merge exits 128 on every round. `git backfill --sparse HEAD..@{u}` fetches the missing contents inside the sparse set for those commits and their boundary commits in one batch. Measured, it opened one connection in that case and none after a full-content fetch, after a code-only change, or with nothing new upstream. Inside the admission the gate counts it, and an ordinary round costs nothing extra. This makes the merge offline again for every clone 20261107-132320-s-tac-2za concerns.

**Git version.** `git backfill` takes a revision range and includes boundary commits by default from git 2.55. Without the boundary contents a 3-way merge still lacks its base. Below 2.55 the bar of 20261107-224549-d-tac-r9q would turn a clone in the state above into a merge that fails on every round, so sdd reads `git version` once per process and, below 2.55, applies neither the backfill nor `GIT_NO_LAZY_FETCH=1`. Lazy fetches then run as before, outside the gate's count.

Rejected alternatives:

- A blobless fetch followed by the backfill on every round. It opens two connections for every round that changes the graph, also in a repository holding only its graph, where the full-content fetch needs one.
- Choosing per clone between the full-content and the blobless fetch by whether the repository holds files outside the sparse set. Both open two connections in a code repository; it saves only bytes there, at the cost of a second fetch path.
- The bar without a version gate. On git 2.45 to 2.54 it turns a clone holding unmerged commits without contents into a permanent merge failure.

Accepted costs:

- A code repository holding its graph opens two connections per round and downloads about 1.8 times the bytes of a blobless fetch.
- Git marks `git backfill` experimental; its behavior may change.

## Acceptance criteria

- [ ] The fetch in the clone runs with `-c fetch.unpackLimit=1 --no-filter`, and a small fetch whose delta bases are missing opens at most one connection beyond the fetch, counted by the gate.
- [ ] A clone holding upstream commits fetched without contents merges on the next sync round, with the backfill's connection counted.
- [ ] After a full-content fetch, the backfill opens no connection.
- [ ] With git below 2.55, sdd runs no backfill and sets no `GIT_NO_LAZY_FETCH`.
