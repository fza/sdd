The fork's compatibility outcomes with stock sdd are built on `fza-next` and shipped in `fza/sdd` v0.18.0-alpha.3.fza.52 at commit `7f3c20fb`: every item of 20261119-013237-d-cpt-fu4 that names a change, the whole dependency chain of 20261119-013353-d-cpt-ha2, and the capture without a reason hold of 20261119-021758-d-tac-b6i.

The dependency chain change removes the resolver for refs beyond the direct dependencies, its miss record, the three unresolved-reference warning kinds and the reason on the `[unresolved: repo X]` marker; the server instructions, the tool descriptions and the docs no longer limit work to directly declared dependencies.

The capture change also writes the marks of a guided entry: a reason or intent the person gives is stored, with `reason-by` and `intent-by` naming them.

Item 36 of the compatibility directive makes `stage_attachment` accept stock's one-file call shape beside `files`, which ends the "only a `files` array" rule of 20261114-121413-d-tac-n6r. The tool listing and the served instructions still show only the `files` shape, as item 36 sets.

Item 42 restores stock's exported `pkg/` functions and types. Keeping the types comparable needed pointer fields: `Finding.Basis`, `Proofs.Held`, `Proofs.Reread` and `StageAttachmentResult.Files` hold a pointer, so `==` on those types compares the added fields by address.

## Acceptance checks

- Switch-back, met in part: stock's session decoder skips a fork-written log on its start event and reads a stock log the fork appended to as stock's (`internal/proctest/session_stock_decode_test.go`, `internal/engine/build_mark_test.go`). Deviation: no stock binary ran `sdd serve` and `start_session` against fork-written machine state; that stock reads the shared index and state folders past the fork's additions is read from upstream's code.
- API comparison of `pkg/...` between upstream `main` (`ca555fd1`) and the fork, met but for two changed texts: `application.NewSessionNote` and `mcpapp.Instructions`, which state the fork's own behaviour.
- Stock's `examples/extendingsdd` builds, vets and tests unchanged against the fork.
- A project opened through a symlinked folder yields the participant of its `config.local.yaml` (`internal/cliapp/symlink_project_test.go`).

## Still open

The upstream proposals the compatibility directive lists are not filed, and its directive stays active as the fork's standing rule toward stock.
