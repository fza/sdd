The deep verifier's rules pages lose the rule text that code decides, the contract that code enforces and the text of the ref-kind vocabulary, and an entry the drafter dismissed with a verdict reaches the verifier as one line in place of a brief.

These are the two parts of a reading that the gap 20261122-004754-s-tac-2c4 names: the pages headed "Pre-flight's rules" and the verdict briefs. Its deviation is that no decision covers either part. This plan is that decision and closes the gap. It answers the gap's five open questions. The rules pages get no size bound, and their size is stated below as an estimate. Of the contracts only the one whose every demand code enforces gives way. Of the selected check's rules and calibration, only the acceptance-criteria rule of a plan and its `high` band give way, because the draft validation decides them. The rest stays. A fresh verifier keeps the rest of the rules text whole and opens by ID only the ref-kind fact, as Rejected explains. A verdict brief becomes the line with the title, the first summary sentence and the verdict code. With no brief left, no limit on briefs is needed.

`llmops.PreflightRubric` (`internal/llmops/preflight.go:149`) builds the rules text, and `preflightRules` (`pkg/application/workflow_deep.go:761`) pages it. A verdict brief is the block a reading serves for a listed entry that the drafter answered with a verdict. The code references are to `fza-next` at commit `0a89bcb5`.

## 1. The rules pages

Everything else stays in full: the other active contracts quoted as entry blocks, the check the draft's shape selects with its calibration section, the rules on refs and their metadata, the graph-fit axes and the rest. Three pieces of rule text go, each a restatement of something code decides. The type-system contract goes, because code enforces all it demands of a draft. The ref-kind vocabulary becomes one line.

The directive 20261110-164357-d-tac-h1e, closed by the delivery 20261110-211909-s-tac-n1p, moved every rule pre-flight applies into the verifier's reading so that no check is lost. That still holds. Code decides each removed piece before the verifier reads, or the piece can lead to no finding for the draft at hand. The vocabulary stays one open away. The delivery 20261114-000441-s-tac-05p trimmed the rules pages once and kept each check's calibration section on purpose, because it decides a finding's severity. This plan keeps every calibration section too. Only the `high` band of the acceptance-criteria rule leaves one.

The five changes apply in rubric mode only, the mode `PreflightRubric` renders. Pre-flight's own prompt stays byte for byte as it is, as in the first trim. Pre-flight's model still reads it in a capture that runs `prose`.

**The acceptance-criteria rule of a plan.** The rules text of a plan draft carries the rule that a plan needs a section `## Acceptance criteria` with `- [ ]` items, and the rule's `high` severity band (`internal/llmops/preflight_templates/decision_refs.tmpl:28` and `:36`, 412 bytes). The draft validation refuses a plan without them (`internal/model/construction.go:478-482`). Both lines go.

**The applicability paragraph.** The paragraph "Applicability is not your question" (`ref_meta_consistency.tmpl:8`, 443 bytes) tells the judge not to judge whether a ref kind applies. It points at lines of the referenced entries section, which the rules text does not hold. The verifier gets those lines under "Ref fit" (`deepRefFit`, `pkg/application/workflow_deep.go:614`), a section the delivery 20261117-192843-s-tac-19d added, and each of them ends with "Applicability is settled mechanically. Do not flag it." (`ref_applicability.tmpl:12`). The delivery 20260611-102312-s-tac-lpa moved that decision into a matrix in Go and a mechanical check. The paragraph goes.

**The close-pattern rule on standard closes.** The rule "Unusual close-pattern check" (`unusual_close.tmpl`, 2,074 bytes) is in the rules text of every draft with closes (`HasCloses`, `universal_system.tmpl:8`). It lists six standard patterns and asks for no finding on them. A new guard keeps the rule only when at least one close of the draft lies outside the six patterns. The patterns become a matrix in `internal/model`, a pure function of the closing entry's type and kind and the closed entry's type and kind. It stands beside `validateCloses` (`internal/model/graph.go:1156`), which refuses three closes and does not tell a standard pattern from an unusual one.

**The type-system contract.** The rules text quotes every active contract as an entry block (`internal/llmops/preflight.go:503-510`). The block of the type-system contract 20260702-222259-d-cpt-7iy is 6,411 bytes, 45% of the contracts. It applies to every draft, and code enforces all it demands of one. The construction checks (`internal/model/construction.go:394-723`) run in the gate `draftValidates` (`internal/engine/predicates.go:288`). The mechanical pre-flight checks `participantCoverageFindings`, `actorWriteOnceFindings` and `procedureWriteOnceFindings` (`internal/finders/preflight_mechanical.go:335`, `:415`, `:523`) run in every capture. Code names the contract its construction checks implement. A comment already cites it (`internal/model/construction.go:15`), and the build turns that into a named value in `internal/model`. In rubric mode the contracts block leaves out each contract that value names. The cut therefore applies in the graph of this repository only. A successor of that contract stays in the rules text until code names it.

**The ref-kind vocabulary.** The rules text of a draft with refs quotes the body of the ref-kind fact 20260828-160000-s-prc-rfk, 5,719 bytes (`refKindVocabulary`, `internal/llmops/preflight.go:676`). The delivery 20260828-160244-s-tac-jh2 made the vocabulary render from that fact. In rubric mode one line of about 170 bytes takes its place. It names the fact and says when to open it: to judge whether a ref's kind or desc fits the body. The directive 20260730-110228-d-cpt-rh6 asks this of a pointer, because a pointer that only names its target creates no pull. The verifier opens the fact by ID to read a kind's definition. Each "Ref fit" line already names the kinds its ref admits (`ref_applicability.tmpl:11`). The fact is a base entry of every graph (`internal/basefacts/refkinds.go:15`), so this cut applies in any graph.

## 2. Entries the drafter dismissed

An entry the drafter answered with a verdict reaches the verifier as one line, in the line format of the verifier's start that the plan 20261121-223938-d-tac-rqi decides. The line holds the marks that plan gives a line, among them the judge's score, then the drafter's verdict with its code, the ID, the status, the title and the first summary sentence. That plan's list format shows one:

```
! .86 drafter: dismissed, topic-only         s-tac-s1t {open}   Summary lines per check
```

To audit a dismissal the verifier opens the entry by its ID. For a marked line the verifier's report states whether it opened the entry, as that plan decides.

This refines that plan in one point. That plan keeps an entry with a drafter's verdict as a brief, in its section on the verifier's directive and in one acceptance criterion. Under this plan the reading holds no brief, and every entry that is not a declared target is a line. The line format exists once that plan's reading is built, so this part is built with it or after it.

This also refines the directive 20261118-173708-d-tac-euf, whose reading serves the entries the drafter gave a verdict as briefs. That group becomes lines. It is a refinement and no supersession. A supersession would retire the whole directive, and its other parts stay in force until 20261121-223938-d-tac-rqi is built.

In code, `model.PlaceVerifierReading` places an entry with a verdict as a brief (`internal/model/verifier_lanes.go:129-133`), and `llmops.DeepReadingBlock` (`internal/llmops/preflight_light.go:243`) renders the brief as the entry's header and its title, or in a short form when the reading holds the entry's closer. No other entry takes that form (`deepReading`, `pkg/application/workflow_deep.go:713-721`). The placement puts such an entry among the lines, and the brief of `DeepReadingBlock` goes with its short form. `DeepReadingBlock` then renders entries in full only.

## Sizes

The [composition of the rules text](./22-101625-d-tac-r0s/rules-text-composition.md) is the measured basis. It holds the rules text of 22 draft shapes by part, the thirteen checks with their rules against their calibration, what code already decides, the ref-kind vocabulary by part, the cheap passes that run before the deep verifier, and the finding schema. The sizes come from calling `llmops.PreflightRubric` over the graph of this repository on 2026-11-22. All sizes are bytes. The composition's own estimate subtracts the three duplicates only. The table below also subtracts the contract block with its separator (6,418) and the vocabulary (5,719), and adds the line in its place (about 170).

- The rules pages of a plan or a tactical directive with refs come to about 22 KB, against 34.5 to 35.0 KB today. That is 36% to 37% less.
- In another graph only the three duplicates and the vocabulary line apply, and the graph's own contracts stay. A plan with refs loses about 6.4 KB there.
- "After" is an estimate: the measured size minus the bytes of the removed pieces. No rules text was rendered without them.
- The contracts take 14,134 bytes today, 40% to 44% of the rules text of a draft with refs. The seven that stay take 7,716 bytes, about 35% of the rules text of a plan with refs after the cut. The gap puts the contracts at about 10 KB, a figure from the measurement it cites. The composition splits the rules text at its headings and counts 14,017 bytes of entry blocks, 49 of separators and 68 of heading, and its figure replaces the earlier one.
- A verdict brief has a median of 1,024 bytes, a 90th percentile of 1,748 and a maximum of 5,527, as the gap records. A line with title and first summary sentence has a median of 320 bytes. With the drafter's verdict on it, a dismissed entry's line is estimated at about 0.35 KB, about a third of a brief.

## Rejected

For the rules pages:

- The vocabulary narrowed to the kinds `model.AdmissibleRefKinds` (`internal/model/ref_applicability.go:171`) admits for the draft's ref targets. All nine kinds fit any live target, so a draft with one live ref target keeps the whole table. With the three duplicates alone the rules pages of a plan or a tactical directive with refs come to 31.5 to 34.1 KB, 1% to 7% less.
- Contracts selected by topic through a new scope field. Estimated at 12 to 16 KB. It changes the type system, and a wrong scope hides a contract from the verifier.
- Rules and contracts as lines that the verifier opens by ID. Estimated at 8 to 10 KB before opens, 13 to 22 KB with typical opens and about 45 KB with every line opened. A line carries no calibration, so the verifier reads a rule's severity bands and its "No finding" cases only after an open. A rule that its line understates is missed, and nothing records the miss.
- Contracts as lines and the rules in full. Estimated at 16 to 20 KB. A contract judged from its line can be missed.
- The axes of the prose check moved to the cheap model. The rules text holds no rule on style or clarity. Its four axes, `duplicates`, `outdated`, `strain` and `dismissal`, judge the draft against the graph. That is the verifier's own work, and they are four of its ten axes (`internal/model/verifier_deep.go:42`). The writing guide judges style. It runs before the deep verifier on the project's LLM runner and shares no axis with the rules text.
- Results of mechanical checks served as lines in place of their rules. This exists. In a deep capture pre-flight runs only its mechanical checks (`pkg/application/capture.go:65-74`). Their findings reach the verifier under "Already raised by pre-flight" (`preflightRaised`, `pkg/application/workflow_deep.go:626`) and ref applicability under "Ref fit". The guards already drop each rule whose guard the draft fails (`internal/llmops/preflight.go:305-334`). The duplicates and the contract of section 1 are what was left.
- The draft first and the rules after. The verifier would read the draft and the entries without rules, report raw findings, then get the rules. Calibration is about 4 to 5 KB of the rules text of a draft with refs, so the first read shrinks by about 20% at most. It costs one to two more calls on the costly model. A check that exists only as a rule cannot come out of a read without rules. Those are the settled justification, language drift, artifact durability, attachment claims, unusual closes and ref kind against body.
- No change.

For the dismissed entries:

- Briefs for the 20 entries the judge scores highest, lines for the rest. Up to about 20 KB of briefs stay, and one more limit must be built and tested.
- No change. Briefs stay without a limit. The gap's simulated upper bound, a verdict on every listed line, is 34 to 321 KB of briefs per reading.

## Accepted costs

- The rationale of the type-system contract is out of the verifier's view.
- The verifier reads the definition of a ref kind only by opening the ref-kind fact.
- The contracts and the calibration sections stay and are most of the rules pages.
- The verifier judges a dismissal from the line unless it opens the entry.

## Not decided

- A deep finding carries no identifier of the rule it applies, and no decision adds one. `deepFindingSchema` (`internal/engine/schema.go:555-594`) allows `verdict`, `axis`, `severity`, `owner`, `pointers`, `basis`, `sources` and `edits`, and `model.DeepFinding` (`internal/model/verifier_deep.go:175-184`) holds the same fields. Which rule a finding rests on shows only in the words of its verdict.
- An entry the drafter read in full. This plan decides nothing for it. 20261121-223938-d-tac-rqi makes it a line.
- Whether the line of a dismissed entry counts against that plan's limit on entries in doubt.
- Whether the rule's list of standard close patterns is rendered from the matrix. Until then the six patterns stand in the template and in the matrix.
- A limit on the size of the rules pages. None is set.

## Not measured

- Tokens and cost. Every size is bytes of text.
- The rules text after the change. The sizes above are estimates by subtraction.
- Whether a verifier opens the ref-kind fact when a ref kind's fit to the body is in doubt.
- Whether a verifier opens the dismissed entries it should, and whether a line yields the `dismissal` findings a brief yields. No run with a real verifier compares the two.
- Which rules lead to findings. No test compares the rules pages rule by rule.
- How many verdicts a real capture gives.

## Layers

The build follows the CQRS layering of this repository. It adds no command, no query, no handler and no CLI action.

- `internal/model`: the matrix of standard close patterns, as a pure function. The value naming the contracts code enforces, beside the construction checks. The placement of the verifier's reading puts an entry with a drafter's verdict among the lines.
- `internal/llmops`: the read side that renders the rules text. In rubric mode the templates guard the removed pieces, the contracts block leaves out the contracts code names, and the vocabulary renders as one line. `DeepReadingBlock` loses its brief.
- `pkg/application`: `deepReading` hands the verdict code of a dismissed entry to its line.
- `internal/presenters`: renders the line of a dismissed entry, where 20261121-223938-d-tac-rqi puts the rendering of the verifier's lines.

- [ ] For each draft shape of the attached composition, the rules text differs from today's only by the pieces section 1 names. Every calibration section is in it, less the `high` band of the acceptance-criteria rule.
- [ ] Pre-flight's own prompt is byte-identical before and after.

- [ ] The done signal records the size of the rules pages for a plan with refs, a tactical directive with refs and a plan that closes a gap, measured over `llmops.PreflightRubric`, and the size of the dismissed entries' lines in one reading.
