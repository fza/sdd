The committed team proof record of 20261121-210755-d-tac-d5e, its tenth acceptance criterion, is postponed: d297764b9 removes it from `fza-next`, and every machine proves its hiding rules with its own background replays. The code and its design document stay on the branch `wip/team-proof-record`. The other criteria of that plan stand.

## What is removed

The record was one JSON file per judge at `.sdd/proofs/<judge-key>.json` in the graph repository, holding counts only. A machine whose own rules had no valid proof took the record's step, so a newly joined machine could start at a teammate's proven step without a judge call. `sdd serve` wrote the record after a replay round and committed it alone as `sdd: proof <judge-key>`. d297764b9 deletes `internal/model/team_proof.go`, `pkg/local/team_proofs.go` and their tests and `pkg/application/team_proofs_test.go`, and removes the record's read and write from `pkg/application/proofs.go`, which keeps the machine-local proof store. The configuration reference no longer names the record.

## Why

The design document on `wip/team-proof-record` names four problems of the record as built:

- The commit lands at an arbitrary moment on whatever branch the checkout holds: a feature branch, a branch in the middle of someone's work, a branch that is never merged.
- Two machines that write diverging records for the same judge conflict on merge, and no merge driver exists for the file.
- The first record is written only once a rule reaches the full step. A narrowed proof is never shared, so a small graph that never reaches full shares nothing.
- Write churn: with one machine at full and one at narrowed, each sees a step that differs from its own after every merge and writes again, without end.

A test run with the real Haiku judge on 195 entries of this graph (126 live) showed the third problem: after 92 replays the threshold held `narrowed` (3 of 176 needed entries hidden, bound 0.951), the far floor held no proof, and no record was written. Those replays cost $0.60 in logged Haiku calls (20261122-231118-s-tac-c33), the cost a machine pays to prove its own rules on a graph of that size.

## Weighed and not chosen

The design document lists candidates, none chosen:

- When to commit: ride along with the next commit sdd makes anyway, with the pending record kept in machine state outside the work tree; or a dedicated ref or git notes written by plumbing, which a plain `git push` does not carry. A pre-push hook is rejected, since it collides with people's own hooks.
- How diverging records merge: an `sdd-proof` merge driver that keeps the lower step per rule and never pools counts, with a write rule that only tightens; or one file per writer with a fold that takes the lowest step per rule. Summing replay counts across machines is rejected, because overlapping replays inflate the bound.

Keeping the record as built is rejected for the four problems above.

## Accepted cost

A machine that newly joins a graph starts with the threshold at compute-only and the far floor at narrowed in its careful form, and pays for its own replays before a rule hides at full. Team members' machines may hold different steps for the same judge. 20261121-210755-d-tac-d5e rejected this option, a machine's own proof with no record in the repository. This entry takes it until a shared record is decided.

## Settled

This entry removes one criterion from the build and asks for nothing further. A shared record returns only through a decision of its own, which the design document on `wip/team-proof-record` prepares.
