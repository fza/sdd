A search that meets a background cache pruning lock session waits noticeably longer than without one, while 20261101-131514-d-cpt-9ci requires that pruning add no latency to any command or MCP call.

Actual: a probe opened search snapshots on an 800-entry store, one every 5 ms, while `PruneStore` deleted every version in lock sessions of at most 100 versions with a 50 ms pause between sessions. On a heavily loaded machine the median search was unchanged, but the slowest 1% waited about 45 ms, against about 1 ms without a run. With sessions of 25 versions the slowest wait was longer, about 86 ms, because a session's cost is mostly saving the manifest, not the deletions. The probe was a scratch test and is not part of the suite. MCP calls were not measured on their own; they take the same read path.

Expected: the decision's criterion that command and MCP call latency stay unchanged while pruning runs. That holds for the median, not the tail.

Unsettled candidates, not settled here: accepting a bounded tail wait as within the criterion; making the session cheaper by not saving the whole manifest per session; or letting readers skip a held store lock where a snapshot from before the session is good enough.

Confidence is medium because the measurement ran only under heavy machine load and on one store size.
