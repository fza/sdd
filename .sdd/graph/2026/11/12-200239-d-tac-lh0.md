A pre-flight model answer cut at the output token cap counts as the model not judging the draft: sdd retries nothing, and the `verify.skip` policy decides as for a verifier that cannot run. The provider ends such a call with `finish_reason=length`, or `max_tokens` on Anthropic (`ErrAnswerCut`, added with `llm.max_tokens` in 20261028-115840-s-tac-4xr). The observed case, the prose-mode pre-flight of a done capture on 2026-11-12, failed with `finish_reason=length, reasoning 32770 tokens, content 75122 chars`: a runaway, billed in full.

Today the cut fails the capture's pre-flight step like any operation failure, and the failure text of 20260919-141340-d-tac-qws offers a retry. A retry sends the same request, so it can run away again and is billed again. The agent cannot change the request, and no retry count fits a runaway nobody planned.

What the cut does:

- The error carries its own code, assigned where the cut is known, naming the user, who changes the configuration, as the one who must act (20260921-191217-d-cpt-s2i, 20260829-113416-d-cpt-nut).
- `verify.skip` decides what follows, as for a verifier that cannot run: under `failure` or `weighed` the user may skip, and the entry is written with `verification: skipped` and low confidence, as after a deep verifier that could not run, so the marker also covers an entry the pre-flight model did not judge; under `never` the write is held. This widens `verify.skip`, which today governs only the deep exchange, to the pre-flight model's cut under every mode, the default `prose` included, and the configuration reference says so.
- The served text names the cause in one line and the settings that change the request: `llm.max_tokens` and `llm.preflight.params` (20261110-224239-s-tac-3xy), which can lower the pre-flight call's reasoning effort alone.
- Under `verify.mode: deep` the deep verifier already judges in the model's place (20261110-211909-s-tac-n1p), so a cut there arises only in the fallback after a skipped deep exchange; `verify.skip` decides there too.

Rejected:

- One automatic retry with lower reasoning effort or a doubled cap, then the fallback: it may rescue a one-off runaway, but it adds a request-changing path per provider that sdd must own and test.
- Applying `verify.skip` only in the fallback after a skipped deep exchange: a cut in `prose` mode would still offer a retry that likely runs away again.
- A separate key for model cuts beside `verify.skip`: one more setting to document, validate and keep in step with it.
- Only classifying the error and leaving retry, skip or abort to the user: every cut then stops the capture, although `verify.skip` already states what the user wants when a verifier cannot run.
