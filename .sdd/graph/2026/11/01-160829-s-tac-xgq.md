A code review and a real-use check of automatic cache pruning (20261101-145315-s-tac-m3k) find it sound after the fixes the review prompted and working in use. The criterion of 20261101-131514-d-cpt-9ci that command and MCP call latency stay unchanged while pruning runs holds for the median search, not for the slowest.

Inner lens: an independent review of the feature and its fork merge, looking for data loss under concurrent readers, lock errors, races, swallowed errors and run-limit handling. Each claim was re-read in the code before acting. It found nine real defects, none critical. Eight were fixed in `4871bc09`, `662294c3`, `3018fbef` and `afae1561`:

- a search failing on a store removed under it;
- a lost unlock error;
- an unreadable status file stopping all pruning and `sdd info`;
- a failed launch reported only as a warning;
- background failures leaving no trace;
- a manual run during another exiting successfully;
- clone removal racing a repo add;
- one damaged store stopping the pass.

Each fix has a test, and each new check was broken once to confirm it fails. The ninth, protection limited to the launching checkout, became 20261101-153339-d-tac-pnl and is implemented. No test can reach four guards: the status file sync, the unlock error, serve's hourly timer and the five-minute limit.

Outer lens: the real `bin/sdd`, run against a fake cache in isolated directories, removed an unused store and an unconnected clone, wrote the status, showed the last run in `sdd info`, and refused an invalid `cache.retention` while accepting `30d`. The startup check costs 3.0 ms on a day a run is due and 0.1 ms otherwise. A search that meets a pruning lock session waits up to about 45 ms at the 99th percentile on a heavily loaded machine, against about 1 ms without a run; the median is unchanged.

Not covered: a run on a real multi-gigabyte cache, a machine with several active worktrees over time, and MCP call latency measured separately.
