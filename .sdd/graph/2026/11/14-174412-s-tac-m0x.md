A live check of the headless Codex verifier launch showed it starts no MCP server from the user's `config.toml`, which closes the Codex isolation directive 20261114-101145-d-tac-sd3: its live-round criterion is observed for `config.toml` and its MCP servers, and rests on `--ignore-rules` and its tests for rule files.

The build 20261114-103014-s-tac-w7q met the flag and credential-scrub criteria; its live round stopped on the Codex usage limit, so what a round loads stayed unchecked. The check here needs no model answer, because Codex starts its MCP servers before the first model request. With `codex` 0.169 on fza-fork at 8e7e2c0e, sdd's exact fresh-round arguments (`CodexArgs`) and the scrubbed environment ran in an untrusted scratch checkout, under a throwaway `CODEX_HOME` holding the login, a `config.toml` that declares a canary MCP server writing a marker when started, and a rule file. The sdd MCP server started and the canary never did. The control, the same launch without `--ignore-user-config` and `--ignore-rules`, started both. Both runs then stopped on the usage limit before any model output.

What the check does not show: that the rule file is ignored, since Codex consults rules only when the model runs a command, which needs a working turn. That half rests on `--ignore-rules` in `CodexArgs` and its tests. The trusted-project exception, a trusted project's own `.codex/config.toml` still loading, is described in the configuration reference's `verify.runner` row (commit 634ffbb2, on fza-fork).
