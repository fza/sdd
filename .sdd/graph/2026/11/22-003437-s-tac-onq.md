The `precision:` line of `sdd grounding status --verbose` counts replayed labels among the pairs passed in full, so on a ledger that holds replayed labels it reports a higher referenced share than the live labels give. On one machine's ledger for this graph the line reads 84.4%, and 32.8% over the live labels alone. 20261121-232710-s-tac-khe names the line as open. Checked on `fza-next` at 3f694cab.

## What is wrong

`RenderCalibration` prints the line. `internal/presenters/calibration.go:73`:

```go
	fmt.Fprintf(w, "precision: %d of %d pairs passed in full were referenced (%.1f%%)\n", report.Referenced, report.PassedInFull, report.Precision()*100)
```

`RelevanceLedger.Calibration` fills both counts in a loop over `labels`. `internal/model/calibration.go:330-335`:

```go
		if !report.Thresholds.Valid || ScoreValue(label.Score) < report.Thresholds.Relevant {
			continue
		}
		report.PassedInFull++
		if label.Kind == LabelPositive {
			report.Referenced++
```

`labels` holds every label of the judge, live and replayed. Only `--exclude-replay` narrows it to the live labels (lines 296-298).

The threshold the count is taken against rests on the live labels alone since d8ecfe30. `internal/model/prefilter.go:323` and 333:

```go
	live := LiveLabels(labels)
```

```go
	return RelevanceThresholds{Valid: true, Stage: stage, SetAside: ScoreValue(setAside), SetAsideLive: fromLive, Relevant: relevantThreshold(live, setAside)}
```

The doc comment of `Calibrate` gives the reason (lines 314-315): "replayed labels are positives only, so counting them would hold that share at every score". The same holds for the count. A replayed label is a referenced record of source replay (`seedReplay`, `pkg/application/relevance_seed.go:83`), so every replayed label that scores at or above the threshold adds one to both numbers of the line.

The line therefore sets a count over all labels against a threshold from the live labels. The status names the labels each threshold rests on, `(all labels)` or `(live labels)` (`thresholdsText`, `internal/presenters/grounding_summary.go:90-104`). The precision line names none.

## Observed

One machine's ledger for this graph, judge `chat:claude-haiku-5-5`, binary built at 3f694cab. The figures cannot be checked from the repository.

`sdd grounding status --verbose` printed:

```
sources: 7799 live labels, 4691 replayed from past captures
thresholds: set aside below 0.051 (live labels), serve in full from 0.400 (live labels)
precision: 4959 of 5878 pairs passed in full were referenced (84.4%)
```

`sdd grounding status --verbose --exclude-replay` printed:

```
thresholds: set aside below 0.051, serve in full from 0.400
precision: 448 of 1367 pairs passed in full were referenced (32.8%)
```

Both runs hold the same thresholds. Both numbers of the line differ by 4511: that many replayed labels score 0.400 or more, and each counts as referenced. The lines per reason code and the prompt revision hint were the same in both runs. A replayed label is never a dismissal.

## Expected

The line reports how the pairs the judge would serve in full were answered. The configuration reference says of `--verbose` that it shows "how the pairs served in full were answered, per reason code" (`website/src/content/docs/reference/configuration.md:211`). It says of the serve-in-full threshold: "Replayed labels are references only, with no dismissal beside them, so they do not count for it." (line 213). No entry commits the line to the same labels. It is the natural reading of a figure printed below a threshold marked `(live labels)`, and the doc comment of `RenderCalibration` says the same: it writes "how the pairs it would serve in full were answered" (`internal/presenters/calibration.go:13-14`).

Line 211 of the reference also says "Calibration counts both sources; `sdd grounding status --exclude-replay` shows it over the live labels alone." A reader who knows the flag gets the live figure. The default output does not say which labels the line counts.

## What it costs

- A reader takes 84.4% as the share of the pairs served in full that were needed. The live labels give 32.8%.
- Nothing in sdd acts on the figure. `CalibrationReport.Precision` has one caller, the line itself. The cost is a wrong reading by a person or an agent who judges the ranking judge or its prompt from the status.
- The figure rises with every replayed label that scores above the threshold, whatever the judge does in live checks. `sdd grounding update` and the background calibration seed those labels from the graph's references (20261119-105440-s-tac-5et).

## Not part of this gap

This gap is the replayed labels in the count. Two further differences between the count and the threshold hold on live labels alone. They are a separate deviation. This entry does not record it as a gap, and closing this gap does not settle it. Derived from the code.

- The count does not read whether a check served a pair in full. A labelled pair counts when its stored score lies at or above the threshold as calibrated now (`calibration.go:330`).
- The count is unweighted and takes labels of every kind. The threshold rests on a weighted share over positive and negative labels only (`relevantThreshold`, `internal/model/prefilter.go:370-393`). An implicit dismissal weighs 0.25 there (`WeightImplicit`, line 171). The live figure of 32.8% is therefore not the share whose lower bound the threshold holds at 0.5 (`RelevantPrecision`, line 18).
