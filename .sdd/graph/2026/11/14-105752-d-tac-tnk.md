The relevance verdict ledger stays in the binary segment format and lives only in the machine state folder: the `relevance.commit` and `relevance.content` settings and the committed copy under `.sdd/relevance/` go. This drops D14's commit setting and D20 (committed content) of the grounding design 20261109-004506-d-cpt-udz. D15 (binary segments, shared by the ledger and the project event store) and D16 (JSON export and import) stand, so the event store under `.sdd/events/` keeps binary segments as well, in place of the JSON files the event store directive 20261107-115150-d-cpt-0mu names as its local default; the measurements below give the reason D15 left to a refining entry.

**Why.** JSONL was weighed so that files in `.sdd/` stay readable. Measured on one machine's real ledgers (63 segments, 64,274 records): JSONL takes 12.8 times the space (141 against 11 bytes per record; 1.5 times gzipped), and loading and folding the whole ledger takes 5.9 times as long (70 against 11.8 ms; this project's ledger 13.5 against 2.4 ms). Every grounding read, prefilter calibration and grounding status call reloads and folds the whole ledger from disk, so that time is paid per call. Readability matters only for files a user sees. A machine-local ledger is out of view, where per-machine derived state belongs (20260708-184318-d-cpt-6cq); only a committed copy would sit in `.sdd/`. Committing it grows the repository in either format (D20 estimates 7 to 9 MB reader-only and 35 to 50 MB with scores at 100k entries, in binary) and adds a segment to every sdd auto-commit.

**Rejected.** JSONL for the ledger and the event store: 13 times the size and 5 to 6 times the load on real data, with readability gained only for files in `.sdd/`: a committed ledger and the event segments under `.sdd/events/`, which D16's JSON export already makes readable. JSONL for the committed ledger only: two codecs and a switch between them. Keeping the commit setting: repository growth for team-wide reuse of verdicts and pooled calibration.

**Accepted costs.** Each machine, clone and CI run builds its own verdicts and calibration labels, and pairs already judged on one machine are judged again on another. Prefilter calibration is not pooled across a team; until a machine holds enough labels it stays invalid and the deep verifier inspects every listed entry. The daily sweep of 20261114-095140-d-cpt-ad4 removes an unused project's ledger after 90 days, with no copy in git to restore. Hosted sessions do not see a machine's verdicts.

**Removal.** `relevance.commit` and `relevance.content` become retired config keys: read tolerantly, reported as ignored, refused by `sdd config set`, as the retired sync keys are under the tolerant config rule of 20260921-174543-d-cpt-tv9. A repository still holding segments under `.sdd/relevance/` gets them reported as ignored, naming the project's ledger folder in machine state to move them into; segment names never collide (D17), so a plain move merges them. The git auto-commit stops staging relevance segments, so the user commits their removal from the repository.

## Fulfilled when

- No code path reads or writes `.sdd/relevance/`; the ledger lives only in the state folder.
- `relevance.commit` and `relevance.content` in a config are reported as retired, and `sdd config set` refuses them.
- Leftover segments under `.sdd/relevance/` are reported with the folder to move them into.
- The configuration reference describes the ledger as machine-local.
