A full reindex costs time quadratic in the size of the graph, because every entry published to the search index reloads and rewrites the whole manifest. `PersistentSearchIndexStore.PublishEntry` in `pkg/local/entry_publication.go` loads the manifest from disk for each entry and scans the chunk IDs of every published version for conflicts. It then saves the manifest and refreshes the segments, so publishing n entries does work proportional to n². Expected: a reindex costs time proportional to the entries it embeds, and the embedder dominates it. That is a natural expectation nobody wrote down. The load-per-operation that 20260716-142323-d-tac-js8 accepted was sized for search latency, not for a reindex over the whole graph.

Observed on this repository (about 1600 entries): a hash change marked every entry for reindexing, and `sdd serve` ran the reconcile inside the first search request. The serve process sat at full CPU for over an hour. Every MCP call, search and procedure start alike, waited behind it until the process was killed. A stack sample showed the time in `PublishEntry`, then `index.LoadManifest` and its parse, under `SearchIndexHandler.Reconcile`. Upstream `main` carries the same publish path.

Candidate remedies (unsettled reasoning): keep the manifest in memory across one reconcile and save it once, or per batch; check chunk ID conflicts against an index built once per reconcile; and keep a long reconcile from blocking requests that don't need it.
