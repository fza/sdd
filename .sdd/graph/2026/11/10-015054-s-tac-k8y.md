`sdd config set` writes a value outside a setting's allowed set without complaint, so a typo lands in the file and fails or misleads only later, at load or at use; the rule that writes enforce the schema (20260921-174543-d-cpt-tv9) holds today only for key names and YAML types, not for values.

Reproduced with the `fza-fork` build in a throwaway repository, each `sdd config set --local` exiting 0:
- `verify.mode bogus`, `verify.runner bogus`, `verify.skip bogus`: written; every later sdd run then fails at load with `verify.mode "bogus" is not off, grounding, prose or deep`.
- `language xx-bogus`, `llm.structured_output bogus`: written; `sdd config` loads them without a warning, and a bad `structured_output` fails only at the first LLM call.
- `participant` set to an empty string: written; sdd then reports no participant configured.
- Refused correctly: `dialogue.mode bogus` ("is not guided or autonomous"), the retired `sync.mode`, an unknown key.

The value checks are scattered: `dialogue.mode` is judged through the ignored-settings list `sdd config set` consults, the verify values only by the cross-layer check at config load, which `sdd config set` never runs, and `structured_output` only where the LLM client parses it. A new setting with a closed value set gets no write-side check unless someone adds one by hand. The fix must cover every setting, existing and future, not only `verify.mode`.
