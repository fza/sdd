A verifier round sdd launches itself runs in a detached process of its own instead of the goroutine inside `sdd serve` that 20261109-111708-s-tac-tuk introduced, so the round survives the server that started it and records its own outcome; a round whose process died without an outcome fails the capture's wait step with that cause named. This answers gap 20261114-091954-s-tac-n6l, where hosts that restart or stop the server (a `/mcp` reconnect, the Codex harness after every user turn) left the capture waiting forever.

**Launch.** For every round sdd launches (`claude`, `codex`, a custom driver), sdd starts the round as a detached `sdd` process in its own process group, with no stdio tied to the server, and appends a start record to the child session: round number, runner, that process's pid and start time, the start time of the round and its timeout. The round process waits for its start record before it runs the round, so no outcome precedes the record a later call checks it by. That process resumes the stored CLI session as today, enforces `verify.round_timeout` itself, and appends the round's outcome (the CLI session or the error) to the child session. A later round's process waits in the child session for the previous round's outcome before it runs, since it resumes the CLI session that outcome names; when the previous round's process is gone without an outcome, the later round fails with that cause. Rounds a harness launches as its own subagent are unchanged.

**Wait step.** A recorded outcome is picked up as today. Without one, a later call fails the round when its process is gone (no such pid, or a pid with another start time) or when the round's timeout plus a margin has passed, and the capture leaves for `deepFailed` naming the cause: the round's process ended without recording an outcome, or it ran past its timeout. Under 20260829-113416-d-cpt-nut the agent then puts the retry to the user.

**Lifecycle.** sdd owns these processes, as 20261109-004924-d-cpt-cxw accepted: abandoning the capture or ending the child session stops a running round process with its whole process group, the agent CLI and the `sdd serve` it started included.

Rejected, with the reasoning: keeping the goroutine and failing a round whose owning server is gone, with a deadline as backstop (under the Codex harness every deep round would then fail and need a retry each turn); a deadline alone (after a restart the user waits up to `verify.round_timeout`, 10 minutes by default, and Codex rounds still fail); a heartbeat from the server (it needs the same living writer the round has lost).

Accepted costs: a hidden `sdd` subcommand and detached-process handling per platform; a liveness check that reads a process's start time to rule out pid reuse; a round process that keeps running after the session that started it went quiet, until its timeout.

## Acceptance criteria

- [ ] A round sdd launched keeps running after the `sdd serve` that launched it exits, records its outcome, and a later call from a new server picks the outcome up.
- [ ] A round process killed mid-round makes the next call at the wait step fail to `deepFailed`, naming that the round's process ended without an outcome.
- [ ] A round with no outcome past its timeout plus the margin fails the same way, naming the timeout.
- [ ] Abandoning the capture or ending the child session stops a running round process and the agent CLI it started.
- [ ] The configuration reference's `verify.runner` and `verify.round_timeout` rows describe the detached round and both failure causes.
