sdd will isolate the Codex processes it starts the way it isolates Claude's: a headless Codex verifier round will load neither the user's Codex configuration and rule files nor inherited credentials, and will answer on the user's own Codex login.

**Verifier rounds.** The deep verifier directive 20261109-004729-d-cpt-xs5 wants a headless verifier without project instructions, skills, plugins, hooks or other MCP servers. Its Codex launch, `CodexArgs` in `internal/delegatelaunch/delegatelaunch.go` (line 188), keeps only the project instructions out (`project_doc_max_bytes=0`). It will also run Codex with `--ignore-user-config` and `--ignore-rules` and name sdd as the only MCP server. Model and effort keep coming from the `verify.codex` block of 20261109-222220-d-tac-4ev; sdd's config gains no provider setting. A round answers on the user's own Codex login (`auth.json` in `CODEX_HOME`). An evaluation that runs the agent under test through another provider uses the Claude verifier runner.

`--ignore-user-config` drops only `$CODEX_HOME/config.toml`. A trusted project's own `.codex/config.toml` still loads, so in a trusted checkout a round can still start the MCP servers that file declares.

**Credentials.** sdd will remove the inherited variables `OPENAI_API_KEY`, `CODEX_API_KEY` and `OPENAI_BASE_URL` from the environment of both Codex launches, with no exception.

**sdd's own model calls through Codex.** The `codex` LLM provider of 20261109-222220-d-tac-4ev (`internal/llm/codex/codex.go`) already runs isolated: its own temporary directory, `--ignore-user-config`, `--ignore-rules`, `--ephemeral` and a read-only sandbox. It will gain the same credential scrub.

Why: a Codex verifier round today runs in the project checkout and loads the user's whole `config.toml` (other MCP servers, plugins, apps, the notify hook, memories) and Codex rule files. Each costs tokens and can act inside a round that needs only sdd. The Claude verifier already starts with `--setting-sources ""` and `--strict-mcp-config` (`delegatelaunch.go:138`), and commit `04bf83f7` isolated the Claude LLM runner (its own working directory, `--safe-mode`, Anthropic credentials scrubbed). This brings Codex to parity, and past it on credentials: the Claude verifier launch still inherits the environment unscrubbed.

Rejected: keeping `config.toml` and switching features off one by one with `-c`, which is not airtight, since every new Codex feature needs sdd to list it; scrubbing credentials only, which leaves other MCP servers, plugins and hooks running in every round; a provider block in sdd's config, set in personal layers only, because it served only test runs.

Accepted cost: a Codex login that rests only on an environment key, as in CI, must be stored once with `printenv OPENAI_API_KEY | codex login --with-api-key`.

## Fulfilled when

- `CodexArgs` carries `--ignore-user-config`, `--ignore-rules` and only the sdd MCP server among its own overrides.
- Tests show `OPENAI_API_KEY`, `CODEX_API_KEY` and `OPENAI_BASE_URL` removed from the child's environment in both launches, the verifier round and the `codex` LLM provider.
- A live Codex verifier round in an untrusted checkout loads no MCP server besides sdd and none of the user's `config.toml` or rule files.
- The verifier runner page describes the isolation, the login it uses and the trusted-project exception.
