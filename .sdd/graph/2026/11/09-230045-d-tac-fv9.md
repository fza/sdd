`sdd init` no longer reads an `init.skip` key: every init writes, refreshes and deletes the `mcp`, `permissions` and `skills` surfaces again, as before 20261109-153425-d-tac-5dh. The key goes from the config model, `sdd config set`, the `sdd move` install step and the configuration reference. A config still holding it loads, and sdd reports the key as unknown (20260921-174543-d-cpt-tv9).

The key carried one project's agent setup into sdd's config surface: a value list with its own validation, a committed-only rule, and a carry path from a work repository's init into its project's init that lived only in memory, so an init run in the project repository alone ignored the work repository's skip. A project that manages its own agent setup fixes the clash on its side, for example by renaming a skill whose name collides with an sdd skill.

The gap 20261030-164247-s-tac-avs is open again.

Rejected:

- Writing the work repository's `init.skip` into its project repository's config, so a direct init there honors it: a second copy of the key to keep in step, for a key with one user.
- Keeping the key: each later init surface (hooks, verify) would have to decide whether it is skippable too.

Accepted costs: a project with its own agent setup cannot run `sdd init` without init writing `.mcp.json`, `.codex/config.toml`, `.claude/settings.json` and the skill renders; a commit-msg hook admitting `sdd:` only under `.sdd/` refuses init's commit there again.

## Acceptance criteria

- [ ] No code, test or doc on `fza-fork` reads or names `init.skip`.
- [ ] A config holding `init.skip` still loads, with the key reported as unknown.
