The fork drops contribution mode from `fza-next` and keeps it only on its own upstream branch `up/contribution-mode`, cut from upstream `main`.

Contribution mode (delivered as 20261027-104455-s-tac-l72) refuses graph writes in a checkout whose machine-local config names an upstream ref, unless the checkout is on a feature branch cut from that ref. The fork has no use for it: fork graph entries live only on `fza-next`, and `next/` and `pr/` branches carry none (20261117-092355-d-prc-3vb). No sdd config on the owner's machine sets the key. Kept on `fza-next`, it costs a contribution hint in every fork session's framing and code the fork maintains without running.

- `a8908ee5` on `next/remove-contribution`, merged into `fza-next`, removes the write guard, the `contribution` config field, its `sdd info` and MCP output and the session-start hint. `contribution` becomes a retired key: a config that still sets it gets a warning naming the removal, not a failure.
- `up/contribution-mode` (`5ee1c347`, `8cae0721`) carries the feature alone, rewritten on stock `main`. It leaves out the session-start hint, which would show in every stock session, and the fork-only placement of keys beside `graph_repo`.
- `fza-integration` never carried the feature.

It closes the fact that contribution mode works in a project_dir layout (20261027-113552-s-tac-1rb): the fork no longer carries the mode, and `project_dir` is gone from the fork, removed by item 1 of the fork compatibility directive (20261119-013237-d-cpt-fu4). The removal also ends that directive's item 23, under which the server told the agent about contribution mode at session start.

Settled: the removal is built, and the full isolated test suite, vet and lint pass on both branches. Whether `up/contribution-mode` is proposed upstream is the owner's call.
