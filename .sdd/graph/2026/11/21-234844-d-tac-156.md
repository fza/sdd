Points 17, 28 and 37 of the fork compatibility directive (20261119-013237-d-cpt-fu4) are corrected to match four plans that change what these points state; every other point of the directive stands.

Each section names the point, its text so far, its new text and the cost. None of the corrected behaviour is built on `fza-next` yet. A correction takes effect when its plan is built. Until then the fork behaves as the point read before.

## Point 37: a required answer replaces the markers and the `held` argument

So far: the server keeps its markers in served text and the optional proof arguments `held` and `reread`, and an agent that sends none gets everything in full, as in stock.

Now, under the plan for the text question (20261121-230157-d-tac-ym8): the server puts no marker into served text and takes no `held` argument. Every response that starts, resumes or advances a session ends with one question about a served text. The next call that advances the session answers it in a required argument, with the words the question asks for or with `lost`. A call without the answer is refused with a message that names what is missing. The `reread` argument stays as it is until a decision of its own settles it, as that plan leaves it.

Under the plan for shorter repeats (20261121-233256-d-tac-mm2), two more texts come short to an agent that proves nothing. sdd sends a framing block the first time and again only when its content changes. When a move ends, sdd sends a short landing with the move's outcome and the choices for what comes next. The landing names the base step and does not send its text again. Neither rule asks the agent for a proof. A caller sdd has not served yet gets every framing block in full, and `resume_session` sends every framing block and the base step in full.

Deviation: a call in stock's shape that advances a session carries no answer, so the fork's server refuses it. The sentence that an agent sending no proof gets everything in full, as in stock, no longer holds. An agent that proves nothing gets a framing block only when it is new or changed, and a landing in place of the base step's text at a move's end. The plan for shorter repeats leaves open whether a wrong answer or `lost` to the text question sends every framing block and the base step in full again. The markers no longer show in served text. A program that sends the answer argument, or `reread` while the fork keeps it, to stock's server still gets an unknown-argument error, as point 37 named for `held` and `reread`.

Accepted cost: fork and stock differ in one more place, the shape of a call that advances a session. Under the framing rule and the landing rule, an agent whose host compacted its context and that does not call `resume_session` works without the framing until a block changes and picks its next move from the listed choices alone.

Rejected: a tolerant path, where a missing answer counts as `lost` and stock's call shape keeps working. An agent that skips the answer then gets everything in full and saves nothing, which is what agents did with the optional proofs. The plan holds the measurements.

In the closing section's list of outcomes proposed upstream, "markers and proof arguments (37)" becomes "the text question with its required answer (37)". For the text question the proposal follows the fork, so that the two behave alike, which is that section's stated purpose. No decision puts the framing rule and the landing rule on that list. Until one does, the fork differs there from stock and from the proposals.

## Point 17: `embedding.keep_alive` joins the fork-only keys

So far, as the earlier correction left it (20261120-010806-d-tac-uj2): the fork-only keys `verify`, `hooks`, `connected`, `inbound`, `llm_prefilter`, `graph_repo` and `titles.backfill` stay in the committed `.sdd/config.yaml`.

Now, under the plan that adds the setting (20261121-231007-d-tac-ose): `embedding.keep_alive` joins that list until upstream has the key. It differs from the other keys in one respect. Stock knows the `embedding` block and applies its other keys. Only the key `keep_alive` inside it is unknown to stock.

Cost: stock prints `ignoring unknown config key` for `embedding.keep_alive` on every command in a project whose committed config sets it, and does not apply it. The same warning comes from any config stock reads that sets the key: the user-global config makes stock warn in every project on that machine, and `.sdd/config.local.yaml` in that checkout. Where no config sets the key, stock has nothing to warn about.

`embedding.keep_alive` (17) joins the closing section's list of outcomes proposed upstream. Rejected: a setting that stays on the fork with no proposal upstream, because stock would then warn about the key for as long as a project sets it.

## Point 28: the sweep also removes idle open sessions

So far: the session folders stay shared, the fork's state sweep skips a project it has no record of using, and in a project both binaries use the fork removes old ended sessions stock wrote.

Now, under the plan for the open-session sweep (20261121-223858-d-tac-cg2): in such a project the daily sweep also removes an open session, stock's included, whose log holds no event younger than `sessions.retention` and that has no move in progress, with its staged attachments. Every session with a move in progress stays, whether the move was parked or left mid-step. An open session inside the retention stays, and so does a log the sweep cannot read. The rest of point 28 stands: the folders stay shared, the sweep skips a project the fork has no record of using, and it removes old ended sessions stock wrote by the machine's global retention instead of the project's. The rule for open sessions reads the same global `sessions.retention`.

Cost: stock keeps every open session. In a project both binaries use, the fork removes an open session that stock wrote once it is untouched for the retention and has no move in progress, and its handle no longer resumes under stock.

Item 28 stays among the outcomes the closing section keeps on the fork alone.

## Rejected for all three

Superseding the whole directive with the three points corrected, because it repeats every other point unchanged. Leaving the points as written, because the directive would then misstate what the fork does once the plans are built.

Settled: this entry changes only the graph record and asks for no build of its own. The four plans named above carry the builds.
