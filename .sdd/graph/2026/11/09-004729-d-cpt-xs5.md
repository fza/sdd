A draft verifier checks every capture against the graph it was grounded in, for contradictions, duplicates, outdated claims, strains and wrong dismissals, before the entry is written. One key sets how far it goes, `verifier.mode: off | light | deep`, and every mode other than `off` requires grounding enforcement (20261109-004506-d-cpt-udz). It realizes the graph-fit guide of 20260810-141555-d-cpt-20r. The full design, its decisions with reasons, rejected alternatives and accepted costs, and two reports on verifiers built outside sdd are attached: [verifier design](./09-004729-d-cpt-xs5/verifier-design.md), [reference verifier A](./09-004729-d-cpt-xs5/reference-verifier-a.md), [reference verifier B](./09-004729-d-cpt-xs5/reference-verifier-b.md).

**Modes build up.** The capture's pre-flight (20260703-094500-d-prc-cap) is the light verifier; `llm_verifier` does not exist.

- `off`: pre-flight runs as today, over the draft's refs.
- `light`: pre-flight runs over the grounding reading and adds the axes duplicates, outdated, strain and dismissal. No tool calls are possible, so it is fast and safe, and it gives one verdict: no rounds, no proposal. The drafter fixes the draft, may ask the user, and carries on.
- `deep`: the light pre-flight, then a deep exchange with a tool-using verifier agent, which receives the pre-flight findings as already raised. It starts only once no `high` pre-flight finding is open; a draft revised for one goes through playback and pre-flight again first.

Pre-flight's own checks stay in every mode, and `high` findings block the write with the user-only override, as today.

**Sizing a light call.** The window is `llm.context_tokens` when set, else what the provider reports (Anthropic `max_input_tokens`, OpenRouter `context_length`, vLLM `max_model_len`, Ollama `num_ctx`), else the call is refused naming the key. Half of the window left after the answer reserve is filled, at 3 characters a token. Every call carries the draft's header and a fixed header per entry (id, type, kind, layer, status), never cut. A pair too large for one call is sent as paragraph excerpts in draft order, with markers where text is left out at the start, between excerpts and at the end.

**The deep exchange.** The verifier returns findings with severity `high | medium | low` (pre-flight's scale) and a boolean `owner`, and per finding search-replace edits over the draft. The drafter answers every finding (accept, or contest with a reason); sdd then applies the edits and builds the proposal, its diff and hunks. An `owner: true` finding carries no edits and goes to the user. The verifier reads its input in pages of at most 50,000 characters. The deep verdict, or a recorded skip, is a session event over pre-flight's input fingerprint; `write` requires it to be current.

**Timing.** In guided mode the draft is shaped freely in playback; once the user approves the content, the writing guide runs once, then the verifier, and the user confirms again if either changed something; a last adjust gets a delta check of the changed lines. In autonomous mode both run before playback.

**Launch.** The deep verifier runs a `verify` task procedure in a child session that lasts across rounds. `verifier.launch: subagent | claude | codex | custom_driver`, the same procedures for every value:

- `subagent`: the drafting agent's harness runs a fresh-context subagent, visible to the user.
- `claude`: sdd runs `claude -p --output-format json` and resumes each round with `claude -p --resume <session-id>`.
- `codex`: sdd runs `codex exec --json` and resumes with `codex exec resume <SESSION_ID> <prompt>`.
- `custom_driver`: sdd runs `verifier.driver: {command, args}` per round, writing one JSON request (`round`, `session`, `instance`, `prompt`, `driver_state`) to its stdin; the driver runs the agent its own way and prints `{"driver_state": ...}`. Findings never travel through the driver, only through the child session's `next` calls.

A headless verifier works in the project checkout with read, search and glob, web fetch and search, the sdd MCP tools and read-only git (`git log`, `git show`, `git diff`, `git blame`); no project instructions, skills, plugins, hooks or other MCP servers, no file writes. With `subagent` and no subagent tool, sdd falls back to the headless launches of the agents `supported_agents` names, in its order, where their CLI is found; none found is refused. The parent handle never enters a verifier prompt.

**Skip and failure.** `verifier.skip: never | failure | weighed`. `never`: a verifier that cannot run blocks. `failure`, the default: the user may skip only when it cannot run, and the entry gets `confidence: low`. `weighed`: sdd also weighs before the deep exchange by a fixed rule and puts run or skip to the user, one option marked recommended in the dialogue's language; a skip caps confidence at `medium`. sdd recommends run when the draft names checkable things (paths or code names in the checkout, URLs, commit hashes), is a strategic, conceptual or tactical directive, plan or contract, supersedes or closes an entry, or pre-flight left `medium` findings.

**Config and init.** `verifier.mode` and `verifier.skip` layer like `grounding.enforce`: global and committed set them, committed wins, local may only tighten. `verifier.launch` is personal: the local layer wins. `sdd init` asks "How strictly should drafts be checked against the graph?" (`off`, `grounding`, `light`, `deep`, setting `grounding.enforce` and `verifier.mode` together, committed), and with `deep` and no launch set "How should the deep verifier run?" (`subagent` default; `claude` and `codex` only where `supported_agents` names them; `custom_driver` only where a layer already sets it, local). The CLI gets verification once the session-aware CLI of the grounding directive (20261109-004506-d-cpt-udz) lands, which logs CLI reads into an engine session; until then `sdd new` refuses under grounding enforcement, which every verifier mode requires.

**Build order.** Light first; then child sessions with interim deliveries (20260827-232430-d-cpt-voa, 20260829-122157-d-cpt-zpe), whose first consumer is deep; then deep.

Rejected, with the reasoning: a separate `llm_verifier` model and op (two checkers on one draft, one is enough when pre-flight reads the grounding); light rounds (a plain model call has no turns to pause or resume; one verdict, then the drafter acts); verifying on every dialogue edit (model calls on text about to change); the drafter deciding the skip (the judged party must not argue its way out); a `substantive | minor` scale for deep (two scales in one capture); routing findings through a custom driver (they would lose engine provenance); a headless verifier with write or general shell power (nobody watches it).

Accepted costs: deep findings arrive after the user approved the content; a headless verifier needs its own tool allowlists and sandbox flags per CLI; two probes stay open for the build (whether `claude --safe-mode` drops a server passed with `--mcp-config`, and whether `codex exec` can skip the project's `AGENTS.md`); deep runs cost minutes per capture.

## Acceptance criteria

- [ ] `verifier.mode` other than `off` with grounding enforcement off is refused at config resolution, naming both keys and their layers.
- [ ] With `light`, pre-flight reads the grounding reading, adds the four axes, sizes its calls by the detected or configured window, slices with ordered excerpts and gap markers, and returns one verdict.
- [ ] With `deep`, the exchange starts only with no open `high` pre-flight finding, runs in one child session across rounds, applies accepted edits into a proposal, and `write` refuses without a current deep verdict or skip.
- [ ] Each `verifier.launch` value runs the same `verify` procedure; headless launches hold only the listed tools; `subagent` without a subagent tool falls back in `supported_agents` order.
- [ ] `verifier.skip` behaves as `never`, `failure` and `weighed` above, with the confidence caps.
- [ ] `sdd init` asks the strictness and launch questions as above.
