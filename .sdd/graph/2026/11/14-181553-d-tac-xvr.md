sdd serves the hold-next line of 20261114-121534-d-tac-qdb, and the instructions to prove exactly its tags, only to MCP clients whose name identifies a Claude agent; every other client, Codex included, gets the anchor proof as it was before hold-next: the rule of 20261112-075604-d-tac-t4r that the agent proves every tag it still sees, without the 20-newest reminder of 20261113-121039-d-tac-ca2.

**Why.** The mechanism is not shown to work for Codex: in a live round its main agents mostly skipped the proofs, so repeated pieces came back in full. Its verifier subagents did send most proofs, but they report the same client name, so the gate turns the line off for them too. That gap, 20261114-180559-s-tac-vwu, carries the rethinking of how to make it work there; the branch `pr/hold-next-codex-rethink` keeps the ungated state it starts from. Claude agents send proofs on most calls in recent transcripts, so the line stays on for them. The name comes from the MCP initialize handshake, which sdd's stateless HTTP transport does not keep, so over HTTP every client, Claude included, reports no name and gets the every-tag rule.

**Measured on Claude.** The fourth criterion of 20261114-121534-d-tac-qdb is judged on Claude agents: deep-verifier captures with Sonnet, sdd's default model, against the build before hold-next, plus one smoke run with Opus.

## Fulfilled when

- A client whose MCP name holds "claude", matched case-insensitively as the verifier's client match is, gets the hold-next line and its proof instructions; any other client gets the every-tag proof rule and no hold-next line.
- The Sonnet runs meet the fourth criterion of 20261114-121534-d-tac-qdb, and the Opus smoke run shows its main agent sending the named proofs.
