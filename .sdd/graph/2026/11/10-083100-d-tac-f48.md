`sdd move` carries the graph's runtime folder `.sdd-runtime/` (graph lock, titles lock, lineage record) from the former graph folder to the new one, and removes the former graph folder once nothing is left in it. Today the move carries sessions, staged blobs and stats but not this folder, so a move inside one repository leaves the old graph folder on disk holding only ignored files, and the new location starts without the lineage record that lets a read prove it includes an earlier write. That breaks the move directive's promise of nothing stranded behind (20261109-004100-d-tac-f8r).

The folder moves after the move releases its own locks, so no held lock file is renamed; a file of the same name already at the new location stays where it is. The folder keeps its place inside the graph folder, as 20261109-004100-d-tac-f8r settled when it rejected `.sdd/runtime/`.

Rejected:
- deleting the former runtime folder: simpler, but the lineage record from before the move is lost;
- recording the leftover without a fix: every move keeps leaving a folder that looks like a stale graph.

Accepted cost: carrying the folder while a lock is held needs its own test, since a move run under the graph lock must not rename the lock file it holds.

## Acceptance criteria

- [ ] After `sdd move --graph-dir <dir>` the former graph folder no longer exists, and the new graph folder holds `.sdd-runtime/` with the former lineage record.
- [ ] A move out to another repository or back carries the runtime folder the same way.
- [ ] A former graph folder holding anything besides the runtime folder stays, with that content untouched.
- [ ] No lock file is renamed while held; a test covers a move started while the graph lock is taken.
