The `pr/embed-openai-path` landing on `fza-fork` delivers a configurable embeddings request path and embedding calibration keyed by endpoint, so it closes the gap on the fixed `/v1/embeddings` path (20261102-142152-s-tac-xzn) and the calibration plan (20261031-113150-d-tac-6ij).

The gap closes with 2af1a85e: `embedding.path` sets the request path joined to `embedding.endpoint`, `/v1/embeddings` when empty, so a gateway serving its compatible API under another prefix is reached at its documented route (`TestOpenAIEmbedder_RequestPath`).

The plan closes with 313b8a23 and a0db7d22:

- The vector fingerprint holds provider, model, dimensions and the document template hash; the endpoint URL and path stay out of it.
- Calibration lives in its own file under the cache root's `calibration` folder, keyed by fingerprint, endpoint URL and path, outside the vector store, and is measured once per key (`TestLoadOrCalibrate_StoredOncePerKey`).
- No code path splits a batch on its summed `prompt_tokens`: batches split by input count, and the reported counts are only summed into usage.

The third criterion holds only in part. A changed endpoint or path recalibrates, and it re-embeds nothing while the new limit yields the same rune cap. Chunks are cut by that cap, so a cap that differs makes the fill re-embed every entry (`TestIndexHandlerFillRefillsWhenEndpointCapChanges`): chunks cut for a wider cap would overrun the new endpoint's limit, and chunks cut for a narrower one would differ from what a fresh fill stores.
