`stage_attachment` now takes only `{session, files: [...]}` and answers one `{handle, sha256, bound}` per file in call order: commit `1e9f6ee6` on branch `pr/feat-stage-files`, merged into `fza-fork` as `ba2a327f`. It completes the batch-staging directive 20261114-121413-d-tac-n6r.

- Every item is checked before anything is written: name, exactly one source, duplicate names, a readable path, patches that apply to the file as staged, credentials, the restage refusal and an empty `files` list. One failing item refuses the call, names the item and stages nothing.
- A write failing after the check names the item, says whether it was staged, and lists the files staged before it, which stay staged.
- A call carrying the old top-level `name`, `content`, `path` or `patches` is refused with a message naming `files`.
- A `path` item keeps its source path, so a playback confirm reads the file again.
- The single-file application methods are gone; one path stages every file.
- The tool description, the capture procedure's attachments paragraph and the tool contract snapshot show only the `files` shape; the snapshot diff changed for `stage_attachment` alone. Other served texts only name the tool.

Evidence: new tests in `pkg/mcpapp/stage_attachment_test.go` and the capture suite cover one call staging from `content`, `path` and `patches` with results in call order, eight failing-item cases, the empty list, the old fields, the write-failure report and a restage beside another file. Seven guards were each broken once and failed their own test.

Departures: the commit subject carries no breaking-change marker, since the repository's commit hook refuses it, and the body states the break; the credential check and the empty-list refusal run in the check phase beyond what the directive listed; a write failure while updating a capture bound to a staged body has no test.
