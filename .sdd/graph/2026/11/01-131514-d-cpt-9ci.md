sdd prunes its machine-global cache automatically: search index versions, index stores left behind by an embedding-model change, graph snapshots and connected-repo clones are deleted without a user command, under rules that keep every current version and everything another sdd binary used within its retention period. This replaces the alignment frame of 20260911-121434-d-cpt-cm2, whose direction two allowed only deliberate cleanup, and reverses the rule of 20260910-183941-d-tac-c9c that kept deletion out of every automatic path.

What changed: the cache grows without bound in real use. One machine measured 2.3G under the cache root: 1.8G of index stores, 335M of graph snapshots, 144M of clones. In one repository's store, current versions took 61M of 848M. Nobody runs `sdd index gc` unprompted, and it does not reach stores left by a model change or the snapshots at all.

The frame that stands: the graph is the authority over the search index and the manifest is the authority over its rows. Direction one, graph to index, is `sdd index` and the lazy fill before a search; it must be reliable, fails loud and publishes per entry. Read-time filtering keeps only versions matching an entry's current state, so extra versions never produce wrong results. A store serves several graphs at once (20260708-184318-d-cpt-6cq): the checkout's own, other branches and worktrees, and binaries with another derivation rule. The manifest never names a row that does not exist: a row exists before the manifest names it and is deleted after the manifest stops naming it; orphan files are the only tolerated inconsistency. A fingerprint change starts a new store directory; a derivation change stays in one store as a group.

Direction two, index to graph, becomes automatic as well as deliberate. Pruning must go unnoticed by a person or an agent using sdd: no added latency on any command or MCP call, no output, no lock a foreground call waits on. So sdd startup only checks a machine-wide stamp and, at most once a day, starts pruning as a detached background process that the command neither waits for nor reports. `sdd serve` checks the same stamp at start and then once a day on its own timer, as it already does for graph sync, so a machine working only through a long-running server still prunes; whichever process comes first starts the run, and the stamp keeps it to one a day. That process takes each store's lock without waiting, skips a store another process holds, and works through stores in short lock sessions so a foreground index write never waits behind it. It deletes:

- an index version a retention period after a newer version of the same entry replaced it, counted from the replacement, so a version current for a long time is not deleted the moment it is replaced. The retention period defaults to 90 days and is set by `cache.retention` in the user-global config only, one setting for every rule here that measures how long unused cache data survives, in the days-or-duration form of `sessions.retention`: the cache is machine-global, so a per-repo value would let one repository prune versions another still uses;
- an index store unused for the retention period. Every search and index fill refreshes a last-used stamp file in the store it reads, at most once a day, recording the time per derivation rule and store format of the binary that used it, so a store that is only read stays; a store written by an older binary carries no stamp, and its manifest's last write stands in. Judging use by writes alone was rejected because a quiet graph writes nothing and its live store would be deleted; judging it by the user-global embedding config was rejected because a repository may set its own embedder, which a background process cannot see;
- a graph snapshot whose graph folder no longer exists;
- a connected-repo clone whose repository the user-global `repos` list no longer names. That list is the only machine-wide record of connections; a repository's `dependencies` declaration lives in each checkout, which a background process cannot enumerate. A connected repository keeps its clone whether read or not, because deleting it would make the next read wait for a full clone.

It never deletes a version current for the checkout running it, and it deletes the versions of another derivation rule or an older store format only once no binary using that rule and format has stamped the store for the retention period. Use is read from the stamp, never from the process table: a process scan cannot see an sdd in a container or under another user, cannot order fork and upstream versions, and on a developer machine a dev build beside the installed sdd would block deletion for good. `sdd index gc` stays for deliberate cleanup beyond these rules, and reports orphans and groups as before.

Accepted costs: a branch or worktree untouched for the retention period loses its replaced versions and re-embeds them on its next search. A store nothing reads for the retention period is deleted and its next search re-embeds the whole graph; the stamp adds one file per store and one small write per store a day on the read path. A binary released before the stamp leaves none, so its group's last write stands in, and such a binary that only reads loses its versions after the retention period and re-embeds its namespace. These are the eviction failures 20260910-183941-d-tac-c9c was written to stop; they are now bounded by age instead of excluded, because unbounded disk growth on every machine costs more than an occasional re-embed.

Rejected: pruning only the cheap caches (snapshots, clones) and leaving index data manual with a size hint, which leaves the largest share of the waste to a command nobody runs; deleting stores left by a model change but keeping versions manual, which leaves the 848M store at 848M; a size cap per store or for the whole cache, which deletes versions inside the retention period and makes another branch, binary or repository re-embed early, while the retention period already bounds growth and `sdd index gc --drop stale` cuts a busy store by hand.

A pruning failure is never swallowed: each run records its result (time, what it deleted, any error) in a status file under the state root, and after a failed run the next sdd command reports it once, as one warning line on stderr or a warning in the MCP response, naming the error and `sdd info`, which with `sdd index gc` shows the last run. The user's command itself never fails because of pruning. Rejected: the status file alone, which leaves a failure unseen until someone asks; repeating the warning until a run succeeds, which puts a lasting fault into every agent call.

Fulfilled when sdd prunes all four kinds of cache data in the background under these rules, with tests for each rule and for skipping a locked store, and a measurement showing command and MCP call latency unchanged while pruning runs.
