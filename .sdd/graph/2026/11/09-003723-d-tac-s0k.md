`sdd serve` follows every config layer while it runs, without a reconnect: the user-global config (`~/.config/sdd/config.yaml`), the project's `.sdd/config.yaml` and `.sdd/config.local.yaml`, and in a split layout the graph project's config files. Files created after serve started count, and so do files that vanish.

**Mechanism.** Before every MCP call and before each tick of the background sync timer, serve stats each config file (size, modification time, existence). If any changed, appeared or vanished, serve rebuilds its runtime before it answers. Engine sessions in `.sdd/sessions` survive the rebuild. No file-watching dependency and no polling goroutine: the standard library and the calls that already happen are enough.

**Broken file.** A config file that does not parse makes every call fail, naming the file and the parse error, until it is fixed. Serve never keeps the old config silently.

**Running sessions.** A running engine session follows the new config on its next call, in the middle of a move too. The next serve after a change carries a one-time `host_notice` naming the changed keys with old and new values; a secret value never appears, only its key. A gate a procedure instance already passed does not run again; later gates evaluate under the new config.

**Graph location.** When `graph_dir`, `project_dir` or `graph_repo` changes and the new graph folder is missing or empty, or the move is partial (entries left in the folder serve used before, or fewer of them in the new one), every MCP tool call fails, naming the state, until it is settled.

Rejected: a file-watching dependency (a mechanism the stat check makes unnecessary); a polling goroutine (work when nothing calls); keeping the old config when a file breaks (the agent acts on values the owner already changed); requiring a reconnect (the agent cannot restart its MCP server, and the owner would have to know when to).

Accepted costs: a stat of a handful of files before every call; a change takes effect at the next call or tick, not the instant it is saved.

## Acceptance criteria

- [ ] A changed, created or removed file in any config layer, the graph project's included, takes effect on the next MCP call or sync tick without a reconnect.
- [ ] A config file that does not parse fails every call with its file name and parse error until fixed.
- [ ] The first result after a change carries `host_notice` with the changed keys, old and new values, secrets by key name only.
- [ ] A running session's next call runs under the new config; a gate already passed is not re-run.
- [ ] A graph location change to a missing, empty or partially moved graph folder fails every MCP call naming the state until settled.
