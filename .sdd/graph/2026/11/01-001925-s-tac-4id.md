An entry ID's timestamp is written in local time but read back as UTC, so every entry and WIP marker carries a time off by the writer's UTC offset. `GenerateIDAt` formats the handler clock's time, which is local, while `ParseID` in `internal/model/entry.go` and `ParseWIPMarker` in `internal/model/wip.go` read the 15-character stamp with `time.Parse`, which assumes UTC. A capture made in UTC+1 reads back as one hour in the future. Expected: the parsed time is the instant the entry was captured. That's a natural expectation nobody wrote down; an ID's stamp has no other meaning.

The observation came from agentic-helpers, which reads graph ID times as local time and saw sdd's times disagree. Reading the code confirmed the format/parse mismatch. A test that generates an ID at a fixed instant under a UTC+1 local zone and parses it back gets the instant shifted by the offset.

What the wrong time reaches: date-scoped listings, heat and coldness age (a negative age clamps to zero, so a fresh entry looks maximally hot for the offset's span), and every comparison of an entry's time with now.

Candidate remedy (unsettled reasoning): parse the stamp in local time at both parse sites. That matches the IDs already on disk, all written in local time; formatting in UTC instead would change the meaning of every new ID against the existing ones.
