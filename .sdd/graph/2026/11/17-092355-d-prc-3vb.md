The fork keeps its work on four kinds of branches with one upstream sync route, and fork graph entries live only on `fza-next`. `main` mirrors upstream `networkteam/sdd`. `fza-next` is the fork line: installs, tap releases and every fork graph entry. `next/*` branches carry fork features and fixes that are not upstream and merge only into `fza-next`. `pr/*` branches carry upstream pull requests: each one starts fresh from upstream `main`, takes its code by cherry-pick or rewrite, holds one standalone topic, and merges only into `fza-integration`, a testbed cut from upstream `main`. A `pr/` branch or `fza-integration` reaches `fza-next` only case by case. The fork line `fza-fork` continues under the name `fza-next`: the branch rework for the upstream pull requests renamed it, renamed its feature branches (`pr/core`, `pr/feat-*`, `pr/fix-*`, `contrib/base`, `contrib/fork-graph`) to `next/*`, and cut the `pr/*` branches fresh from upstream `main`. `fza-backup` keeps the older fork line `fza` frozen, as it stood when `fza-fork` replaced it.

`pr/*`, `next/*` and `fza-integration` carry code, tests and docs, never a graph entry. Each `next/` branch dropped its fork entries in one deletion commit, merged into `fza-next` with `git merge -s ours` so the deletion never reached it. A commit may still name an entry in its `entries:` trailer.

Upstream `main` merges straight into every `next/*` branch, into `fza-next` and into `fza-integration`; into a `pr/` branch only when its pull request conflicts. Merges only, never a rebase. The private remote `fza/sdd` receives pushes to `fza-next` and `main` only; every other fork branch lives locally.

Rejected: cutting `pr/` branches from `next/`, `contrib/` or another intermediary, because each pull request then carries foreign commits and conflicts; fork entries on `pr/` branches, because upstream would receive them with the code; rebasing onto upstream, because it rewrites published history.
