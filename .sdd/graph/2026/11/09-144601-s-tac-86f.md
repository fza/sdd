An engine capture fails when another process holds the checkout's Git index lock while the capture commits, although the CLI's own commit path waits that lock out.

Actual, read in `pkg/local/git_finalizer.go` on `pr/core` at `01f0ec6c` and reproduced by tests that hold the lock: the Git finalizer, sole committer of a capture publication (20260915-090615-d-tac-ugt), runs `git add`, `git rm --cached` and `git commit` once each. While any other Git writer in the same checkout holds `.git/index.lock` (an IDE, a merge another tool runs, a second capture), the call fails with Git's `index.lock': File exists` error, and the capture stops at a pending operation the user has to retry.

Expected: the finalizer waits while the lock is held, bounded by its own timeout, as `CLI.Commit` in `internal/git/git.go` already does through its index-lock retry, and still fails at once on every other Git error. The CLI path sets the source of this expectation: both paths commit graph entries into the same checkout and meet the same concurrent writers.

The same three calls also run attached to the terminal, the separate deviation 20261029-130137-s-tac-8bf records.
