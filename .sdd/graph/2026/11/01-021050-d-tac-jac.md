The credential scan lets a `generic-api-key` hit pass when its value holds no digit and no mixed-case letters, so prose that reads like an assignment, such as a markdown heading of the form "Key …: word/word", stays in the vector index and passes capture. This answers the false-alarm gap 20261101-003644-s-tac-qm9.

The narrowing is an sdd-side condition checked after the vendored gitleaks rule matches; `rules.json` and its vendor script stay identical to upstream gitleaks, so refreshing the rules keeps working. It holds wherever the scan runs (index chunks, capture, summaries, lint), since all of them go through `internal/secrets`.

Rejected: a reviewed-hit list in gitleaks' fingerprint form, kept in the graph and read by the index, capture and lint checks. It keeps the rule exact, but it adds a file format every check must read, and each later false alarm needs someone to review and record it by hand, while the narrowing clears the whole class at once. Rejected too: leaving the rule as it is, which keeps the chunk out of search and lets the next prose hit drop out silently.

Accepted cost: a real credential whose value is in one letter case with no digit passes `generic-api-key`. Generated keys and tokens almost always carry digits or mixed case, and the provider-specific rules still apply.

## Acceptance criteria

- A `generic-api-key` match whose value has no digit and no mixed case is no finding; a match whose value has a digit or mixed case still is.
- The heading shape the gap describes is indexable, and the entry it names has that chunk in the vector index after a reindex.
- No other rule changes, and `rules.json` stays unchanged.
