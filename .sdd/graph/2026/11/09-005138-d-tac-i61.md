Configured commands, hooks, run at the steps of every engine procedure, so a prose linter can report findings into a capture step and an external orchestrator receives status at every step without building on sdd's Go API. Today only compositions embedding sdd have extension points (`MutationFinalizer`, the engine's `EventSink`), and nothing is configurable. Hooks add no abilities a procedure can name; registering those per deployment stays an open idea (20260814-171302-s-cpt-5zq). The design record is attached: [capture hooks design](./09-005138-d-tac-i61/hooks-design.md).

**One kind.** A hook names an event and a command, with an optional `timeout` in seconds, default 600. sdd runs the command and writes one JSON object to its stdin. Exit 0 passes; output that is empty or `{"findings": [...]}` in pre-flight's finding format, which joins the step's findings, a `high` one blocking as in pre-flight. A nonzero exit or a timeout fails the call loud, so a status hook never misses a step unnoticed.

**Who declares them.** Only the user-global config and `.sdd/config.local.yaml`. A `hooks` key in the committed `.sdd/config.yaml` is refused when the config resolves, naming the file and the layers that accept it: a hook runs code on the machine running sdd, and only the person on that machine chooses what runs there.

**Events.** Engine-level for every shipped procedure: `<procedure>.<step>.<entered|left>`, `*` matching any step or procedure, `entry.written` after a publish, and for the verifier (20261109-004729-d-cpt-xs5) `capture.verify.<entered|left>` plus `capture.verify.round` per round. Event names are checked against the running procedures when the config resolves; an unknown name is refused, listing the valid ones. Findings are accepted only on steps with a findings channel (`assemble`, `guide`, `preflight`, `verify` of capture, 20260703-094500-d-prc-cap); a hook returning findings elsewhere is refused at config time.

**Several hooks on one event** run as Claude Code runs its hooks: all in parallel and to completion, results merged, any `high` blocking. Unlike Claude Code, which discards a timed-out hook's output, a failure or timeout of any hook fails the call once all have finished.

**Payload.** The same over MCP and CLI, since hooks fire in the engine: `event`, `time`, `project`, `branch`, `session`, `procedure`, `instance`, `step`, `phase` (`entered`, `left`, `round`), `transition` (on `left`), `draft` (capture only: type, kind, layer, refs, topics, body, attachment names, `body_hash`), `findings` (steps with a findings channel), `verify` (verification step: mode, launch, round, open findings). Readers ignore unknown fields; new fields need no version bump. Hook changes reach a running `sdd serve` on its next call (20261109-003723-d-tac-s0k).

Rejected, with the reasoning: two kinds `observe` and `check` (two contracts, a hook doing both declared twice); status hooks first and checks later (the linter use waits); committed hooks after a one-time approval per machine (code from a repository running on every clone's machine); capture-only events (status for other procedures would need a second mechanism, and the engine needs the same hook point anyway); sequential runs in config order (the wait is the sum of all hooks, and a failure hides later hooks' results).

Accepted costs: a slow hook slows every step it is attached to; step ids become a public surface, so renaming a step breaks hooks naming it, loudly at config time; two hooks on one event deliver in no fixed order.

## Acceptance criteria

- [ ] A hook in the global or local config runs at its event with the JSON payload on stdin; a `hooks` key in the committed config is refused, naming the file.
- [ ] `{"findings": [...]}` from a hook joins the step's findings on a findings-channel step, and a `high` one blocks; findings on any other step are refused at config time.
- [ ] An unknown event name is refused at config resolution, listing the valid ones; `*` matches any step or procedure.
- [ ] Hooks on one event run in parallel to completion; a nonzero exit or a timeout (default 600 s) fails the call after all finished.
- [ ] `capture.verify.entered`, `capture.verify.round` and `capture.verify.left` fire around the verification step, and `entry.written` after a publish.
