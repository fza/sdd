A deep verifier sdd launched itself because the harness has no subagent tool now takes a revised draft through sdd's launch again, never through the drafting agent: commit `1d4d239f` on `pr/fix-capture-eval-defects`, merged into `fza-fork` as `50a8d7d5`. Before, opening the revision reset the record of that fallback, so the re-check's dispatch told the drafting agent to continue the verifier itself, and in two Codex eval runs the agent then answered as the verifier with no findings: the last check before the write was the drafter judging its own draft.

- `prepareDeep` keeps the fallback record while it revises the live verifier; a fresh verifier still asks again. The headless fallback that 20261109-054916-s-cpt-mn7 built thus covers every round and revision of that verifier, as the configuration reference (`website/src/content/docs/reference/configuration.md`, deep verify) now states.
- `TestCaptureDeep_AFallbackVerifierResumesHeadlessForARevision` in `internal/proctest/capture_deep_revision_test.go` failed on its own assertion before the fix and passes after; the full suite passes on the fix branch.
- Live check: Codex capture runs through Opper (gpt-5.3-codex) on the merged build. In the one run that took the fallback and changed the draft after the verifier's verdict, sdd relaunched the same headless Claude session for the revision, the dispatch carried no handles and no continue instruction, the agent never touched the verifier's session, and the revision verdict arrived before the write. Three runs took the agent's own subagent instead, and two settled the verifier's points without a re-check, so they did not exercise the fix.
