`relevance.Halving` does not finish a request when the scorer it wraps reports no batch bound (`MaxBatch() == 0`) and no size is remembered for its key: it sends calls without a candidate until the inner scorer fails. With far candidates in the request it finishes, but sends one call per candidate. The shipped wiring reaches neither case, because it wraps only the chat judge, which reports a bound of 100.

## Expected

The `Scorer` port allows a scorer without a batch bound. Its doc comment in `pkg/llm/relevance/relevance.go` reads "MaxBatch bounds the candidates one call takes, 0 for no bound". `Halving` takes any `Scorer`, so it should score a request of such a scorer in one call, as the scorer does without it. The package plans such a request the same way elsewhere: `PlanWithFar` in `pkg/llm/relevance/far.go` applies the bound only when it is above 0, and the test case "an unbounded scorer takes one call" in `far_test.go` expects one call.

## Where

`pkg/llm/relevance/halving.go` on `fza-next` at 3f694cab.

- `halving.MaxBatch` (lines 85 to 90) returns the remembered size when it is above 0, else the inner scorer's `MaxBatch()`. For a scorer without a bound and without a remembered size that is 0.
- `halving.score` (lines 99 to 106) replaces a size of 0 by the length of the request, its candidates plus the far candidates, and passes it to `split`.
- `halving.split` (lines 126 to 132) sets `size = min(size, h.MaxBatch())` on every pass of its loop, which makes the size 0 again. Without far candidates a call has room for 0 candidates: each pass sends a request with no candidate, and `start += room` does not advance. With far candidates the room is `max(size-len(far), 1)`, so 1.
- The loop has no exit of its own. It ends when the inner scorer returns an error that `halving.batch` does not halve (line 171): one that is neither a broken answer nor a deadline, or any error once `ctx` has ended.
- `halving.grow` (lines 110 to 119) raises nothing from a held size of 0, so no size is remembered and the next request behaves the same.

The line `size = min(size, h.MaxBatch())` dates from the delivery of the chat judge and its batch halving (20261118-162927-s-tac-pq5, commit cd61ad1b). The batch size fixes of 20261121-232710-s-tac-khe reworked how a halved size grows back and kept the line. The open points of that entry name a size that alternates and the `precision:` line of the status, not this defect. The far floor of 20261121-233522-s-tac-qcq added the far candidates: its `relevance.ScoreWithFar` calls `halving.score`, which gives the case of one candidate per call.

## Observed

A probe program against the exported API ran a scorer with `MaxBatch() == 0` that answers every call, a request of 40 candidates and an empty `relevance.MemoryBatchSizes`.

| Call | Inner calls | Candidates per inner call | Scores returned | Size remembered |
|---|---|---|---|---|
| `Halving(...).Score` | 1,000, ended by the probe scorer's own error on its 1,000th call | 0 | 0 | none |
| `ScoreWithFar` over `Halving(...)` with 3 far candidates | 40 | 4: one candidate and the 3 far ones | 40 | none |
| The same scorer without `Halving` | 1 | 40 | 40 | not applicable |

Read from the code and not run: an empty call that fails with a broken answer is halved at a length of 0. `Lower` then stores a size of 0, the inner `split` of the empty request returns at once, and the outer loop goes on.

## Reach

- The shipped composition does not reach the defect. `NewPrefilter` in `internal/llm/factory/prefilter.go` (lines 93 to 99) wraps a scorer in `Halving` only for the `chat` protocol. The chat judge reports 100 (`ChatBatch` in `internal/llmops/chat.go`).
- The `cohere` and `systemone` scorers report a bound above 0 and are not wrapped.
- Scorers that report 0 exist in test code only: `stuckScorer` and `countingScorer` in `internal/proctest`, `test.ScriptedScorer` while its `Batch` is unset, `scriptedScorer` in `pkg/application` while its `maxBatch` is unset, and `fixedScorer` and `callScorer` in `pkg/llm/relevance` while their `maxBatch` is unset. None of them runs under `Halving` while it reports 0.
- No test covers the case. Every scorer a test wraps in `Halving` reports a bound of 10, 13 or 100.

## Cost

- In the shipped binary: none today.
- A composition that wraps a scorer without a bound in `Halving`, for a request without far candidates: the request loops in the calling goroutine and sends empty requests to the provider. A deadline per call does not end it while the request's `ctx` lives, because a call that ran out its deadline is halved. A scorer that answers an empty request never lets it return.
- The same composition with far candidates: N calls for N candidates where one call would do, and each candidate is scored beside the far ones only, not beside the other candidates.
- `pkg/llm/relevance` belongs to the exported Go surface under `pkg/` (20260831-092538-d-tac-zhc), so code outside this repository can build that composition.

## Not known

- Whether any composition outside this repository wraps a scorer without a bound in `Halving`.
- Whether the rerankers `cohere` and `systemone` are ever meant to run under `Halving`.
- The behaviour with a `local.FilesystemBatchSizes` store. It was not run.
- Which fix is wanted. Two directions are open, neither settled: `Halving` treats an inner bound of 0 as the length of the request throughout, or the composition refuses a scorer without a bound.
