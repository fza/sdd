Automatic pruning of sdd's machine-global cache is implemented: commit `7fcd1ff7` on `pr/feat-cache-prune`, merged into `fza-fork` as `1d0d572c`. It fulfills 20261101-131514-d-cpt-9ci.

The background run is the command `sdd cache prune`, which also works by hand. CLI startup reads a status file under the state root and, at most once a day, starts it as a detached process. That check costs 3.0 ms on the day a run is due, including the spawn, and 0.1 ms otherwise. `sdd serve` checks the same status every hour, so runs stay a day apart.

The run applies every deletion rule the directive names, and never deletes a version current for the checkout that started it. Last-used stamps are files `<store>/used/<rule>@<manifest format>` whose modification time is the use time; every search and fill refreshes them at most once a day. `cache.retention` is accepted in the user-global config only, defaults to 90 days, and takes days or a Go duration. Store locks are taken without waiting and a held store is skipped. The fill lock is never taken, and the manifest is saved before rows are removed.

A run records its result in the status file. A failure is reported once: as a warning on the next CLI command, or as `cache_notice` on the next MCP response. `sdd info` and `sdd index gc` show the last run. Tests cover each rule, a locked store, the daily launch, and the notice raised once. Each new check was deliberately broken once, to confirm that its test catches the fault.

Three things were added while building it. A run is bounded at five minutes, a limit Felix Zandanel confirmed; it handles snapshots and clones before stores and stops quietly at the limit. On `fza-fork`, an entry's hash depends on each store's rune cap, so the current versions are hashed per cap. The third was found by measuring search latency while pruning ran. A run that released a store's lock and retook it at once starved searches, which waited up to 461 ms, because flock gives a waiting reader no precedence. A lock session now holds at most 100 versions and the run pauses 50 ms between sessions. Smaller sessions of 25 versions made it worse, because a session's cost is mostly the manifest save.

The measurement criterion is not fully met. During a run, a search that meets a lock session waits up to about 45 ms at p99 on a heavily loaded machine; without a run, p99 is about 1 ms. The median is unchanged. MCP calls were not measured separately; they take the same read path. Serve's hourly timer and the five-minute limit have no test, because both are time-based.
