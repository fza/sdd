A first clone of a connected graph repository into a data folder that holds no clone of it is no longer deferred by a fetch cooldown another process started: commit 6780f454 on `next/fix-first-clone-cooldown`, merged into `fza-next` at 87891fa0 and released in v0.18.0-alpha.3.fza.49. No graph entry tracked the defect; it was reported between agents and fixed on the spot.

The per-machine git gate (20261107-132238-s-tac-1xf) keeps its cooldown record per remote in the shared state folder, while clones live per data folder, so a data folder without a clone was refused its first fetch whenever any other process had fetched that remote recently; an `sdd export` in a fresh data folder failed this way several times in a row. A clone now passes the gate as its own kind, `gitgate.Clone`, which skips the per-repo cooldown and retry wait but is recorded, bucketed and credited like a fetch, so the hourly and per-minute limits still hold. Refresh fetches of an existing clone keep their cooldown, and a commanded `sdd repo sync` still spends a credit past it.

Tests failed before the fix: a clone into a second data folder after another folder's fetch, and a clone during a retry wait, ran only with the fix, while a refresh in the same state stays deferred; a full bucket still defers a clone. A clone that keeps failing, for example on a login error, is now retried on each read, limited only by those buckets.
