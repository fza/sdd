The Git finalizer now waits out an index lock another process holds, as the CLI's commit path does: commit `1b72e099` on `pr/fix-finalizer-index-lock`, merged into `fza-fork` as `2858aec9`. This closes 20261109-144601-s-tac-86f.

The CLI's index-lock retry became the exported method `RunPastIndexLock` on the Git adapter, and `CLI.Commit` and the finalizer's `git add`, `git rm --cached` and `git commit` all go through it. It waits while Git's output names `index.lock`, starting at 100 ms and doubling up to 2 s, until the finalizer's timeout ends, and returns every other Git error at once. Tests hold the lock during staging, during removal and between staging and commit, and check that a rejected commit fails without waiting.

Through the same method the three finalizer calls now run detached from the terminal, as `CLI.Commit` already did. That is part of what 20261029-130137-s-tac-8bf asks; the gap stays open for the other Git calls it lists, which still run attached.

One rough edge remains: when the wait runs out, the error text names the adapter's fixed 30 s, not the finalizer's own timeout. The two are equal unless the finalizer's timeout is set, and nothing sets it in production.
