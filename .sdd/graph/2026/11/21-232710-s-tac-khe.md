Three defects of the relevance judge are fixed on `fza-next`: a serve-in-full threshold that lay below the set-aside threshold, a halved judge batch size that never grew back, and a gather note that named an order by score when nothing was scored. The commits are d8ecfe30, c841fddb, cd78a009, 0189ae66, 6fd6e929, d254f773 and 1c6ead97, the last three merged in 8ba7913f. No release holds them yet.

## Serve-in-full threshold below the set-aside threshold

The defect lay in the recall-stage calibration of 20261119-105440-s-tac-5et. On one machine's ledger for this graph, `sdd grounding status --verbose` printed "thresholds: set aside below 0.200, serve in full from 0.012" for the chat judge.

- The serve-in-full threshold is the lowest score at and above which the Wilson lower bound (95%) of the positive share of the labels reaches 0.5. The calibration computed it over all labels. Labels replayed from the graph's references are positives only, so the share stayed above 0.5 down to a score of 0.012.
- Placement tested the serve-in-full threshold first. Every candidate scoring 0.012 or more was served in full, and the set-aside threshold of 0.200 applied only to scores below 0.012.

d8ecfe30 changes four things.

- The serve-in-full threshold rests on the live labels alone and never lies below the set-aside threshold (`model.Calibrate`). While the live labels reach the bound at no score, the judge serves nothing in full.
- Placement tests the set-aside threshold first (`model.PlacePrefiltered`, `model.RelevanceLedger.Lookup`).
- Once the live labels alone hold a recall stage, the set-aside threshold is the lower of two cuts, the one over all labels and the one over the live labels. A replayed reference is an easier positive than an entry a live reading had to find.
- Where replayed labels take part in the calibration, `sdd grounding status` names the labels each threshold rests on, `(all labels)` or `(live labels)`.

On the same ledger the status then read "thresholds: set aside below 0.078 (live labels), serve in full from 0.349 (live labels)".

c841fddb corrects the configuration reference. A judge that misses no reference holds the 0.98 stage from 189 referenced pairs, not 188.

## Halved batch size that never grew back

The defect lay in the batch halving of the chat judge (20261118-162927-s-tac-pq5). A call that breaks is sent again in halves, and the half is remembered per judge in a file on the machine. Nothing raised a remembered size. One machine's file held 1 for `chat:claude-haiku-5-5`, so every judge call scored one candidate, and no candidate was scored beside others.

cd78a009 doubles the remembered size after a request in which no batch broke, and 0189ae66 tidies its test. That did not recover a size of 1. A gather of 377 candidates sent 377 calls of one candidate, eight at a time. All 377 ended in `context deadline exceeded` at the pass deadline of 45 s, and the gather reported "scored 0 of 377 pairs". No request answered, so the size did not grow, and every candidate went out unjudged.

Two further commits, merged in 8ba7913f, repair the recovery.

- 6fd6e929: a single call answered at the remembered size doubles that size at once, up to the scorer's full batch of 100, whatever the other calls of the request do (`relevance.Halving`). A request raises nothing once one of its batches broke.
- d254f773: a stored size below 10 is not carried into a new process (`relevance.MinCarriedBatch`, `local.FilesystemBatchSizes`). The process starts at the full batch, and the first call that breaks replaces the stored size.

Two alternatives were rejected.

- Dropping every stored size at each process start, with no growth per call. A size cut down then stays down for as long as a server runs.
- Removing the stored value by hand. The value returns after the next stretch of failed calls.

The accepted cost is that a judge whose working size lies below 10 starts every new process at the full batch and pays the failed calls of halving down again.

1c6ead97 corrects the gather note. It read "judge <name> scored N of M pairs; lines to judge run by falling score" even with 0 pairs scored. It now names the order by score only when at least one candidate holds a score.

## Open

- A judge that always fails above some size alternates between two sizes. An answered call doubles the size, the next request breaks at the doubled size and halves it, so every second request pays a failed call.
- The `precision:` line of the verbose status still counts replayed labels among the pairs passed in full, so it reads high.
- No run measured the share of candidates the corrected thresholds set aside in a live gather.

The plan 20261121-205340-d-tac-gyk names both defects as fixed and cites d8ecfe30 and cd78a009. For the batch size that holds only with 6fd6e929 and d254f773. The plan's replayed checks, not built, are to rest both thresholds on calls like a live one.
