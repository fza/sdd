A ranking judge that fails on every call above some batch size makes its remembered batch size alternate between a size that answers and its double, so every second scoring pass pays failed calls at the doubled size. The behaviour follows from the growth rule of `relevance.Halving`. cd78a009 added the doubling after a request in which no batch broke, 6fd6e929 made one answered call double the size at once, and d254f773 stopped carrying a stored size below 10 into a new process. 20261121-232710-s-tac-khe records the three commits and names this behaviour as open. Checked on `fza-next` at 3f694cab.

## What is wrong

The chat judge of 20261118-162927-s-tac-pq5 remembers one batch size per judge. Two rules in `pkg/llm/relevance/halving.go` change it.

A call that breaks is sent again in halves, and the half is stored. Lines 174-176:

```go
	*broke = true
	half := n/2 + len(far)
	if err := h.sizes.Lower(h.key, half); err != nil {
```

A call answered at the stored size doubles it. Lines 157-158 and 110-119:

```go
			if !*broke && len(call.Candidates) >= held {
				err = h.grow(held)
```

```go
func (h halving) grow(from int) error {
	size := 2 * from
	if limit := h.Scorer.MaxBatch(); limit > 0 {
		size = min(size, limit)
	}
	if size <= from {
		return nil
	}
	return h.sizes.Raise(h.key, from, size)
}
```

The store holds one number per judge: `BatchSizes` (`halving.go:16-20`), kept in a file by `FilesystemBatchSizes` (`Raise` at `pkg/local/batch_sizes.go:62-64`). Nothing records that the doubled size broke before. For a judge that answers at a size S and fails at 2S, the stored size goes S, 2S, S, 2S without end. One answered call at S raises it. The next call at 2S breaks and lowers it.

The package test expects this sequence. `pkg/llm/relevance/halving_test.go:407`:

```go
		{"a size that fails again halves again", 4, 4, []int{8, 8, 8}, []int{8, 4, 8}},
```

The inner scorer answers at most 4 candidates and the stored size starts at 4. Three requests of 8 candidates leave the stored size at 8, 4 and 8. The second request pays one failed call of 8 candidates.

Expected, as a natural expectation no entry commits to: once a size has failed and keeps failing, later passes stop paying for calls at that size. The configuration reference describes the built rule and sets no bound on the repeats (`website/src/content/docs/reference/configuration.md:150`): "A call answered at the remembered size doubles that size at once, up to 100, so a failure that passed does not keep the calls small; a size that breaks again is halved again."

A failed call here is one the halving sends again (`halving.go:153-171`, `halvable` at 184-187): a broken answer, an answer that lacks a score, or a call past its own time limit while the pass still runs. With the defaults the call limit (`llm_prefilter.timeout`, 45 s) is no shorter than the pass limit of a graph check or a ranking pass. There the pass ends first and a slow call is not halved, so in these passes only a broken or incomplete answer alternates the size.

## How it shows in a pass

This section is derived from the code. No run observed it.

Every caller splits a pass into requests of the stored size before its first call. `relevance.Plan` and `relevance.PlanWithFar` read the size once (`pkg/llm/relevance/relevance.go:100`, `far.go:42`). The callers are the graph check and the deep verifier's ranking pass in `scoreCandidates` (`pkg/application/prefilter.go:156-159`), and `sdd grounding update` with the background calibration in `scoreSubject` (`pkg/application/grounding_scoring.go:98`).

- A pass planned at S: the first full request that answers raises the stored size to 2S. The other requests of the pass stay at S. No call fails.
- The next pass is planned at 2S. Up to 16 requests run at once (`prefilterInFlight` at `pkg/application/prefilter.go:21`). Every full request that begins before another request lowered the size sends its first call at 2S, and that call fails. A request that begins after the lowering sends calls of the half (`halving.go:100`, `halving.go:127`). The request then scores in halves. A request with a broken batch raises nothing (`halving.go:157`).
- The pass after that is planned at the half again.

The cost falls on every second pass. It is at most one failed call per full request of that pass, not one per pass.

Two details shift the picture without removing the failed calls.

- With the three far candidates of a graph check the stored half is `n/2 + len(far)` (`halving.go:175`), where n counts the request's own candidates. A request planned at 50 holds 47 candidates and stores 26, not 25. The two sizes then move from cycle to cycle. Without far candidates, in a ranking pass, `sdd grounding update` and background calibration, the half is exactly S.
- `broke` is kept per request (`halving.go:104`). A request begun after another request of the same pass lowered the size has no broken batch, so its first call answered at the lowered size raises the size again (`halving.go:157`). A request begun after that raise fails at the doubled size once more. In a pass of more than 16 requests the size can therefore go down and up several times, and the pass can end at the size that fails. The next pass then fails too. `TestHalving_ARequestThatBrokeRaisesNothing` (`halving_test.go:484-497`) expects the raise of the other request to stand.

## Stored sizes below 10

A stored size below 10 is not carried into a new process (`relevance.MinCarriedBatch`, `halving.go:26`; `pkg/local/batch_sizes.go:39-43`). For a judge whose answering size lies between 5 and 9, the doubled size is 10 or more and is carried.

- A process that ends on the answering size leaves the next process to start at the full batch of 100 and halve down. 20261121-232710-s-tac-khe accepts that cost.
- A process that ends on the doubled size leaves the next process to start at a size that fails.

Which of the two a new process meets depends on where the alternation stood. Derived, not observed.

## What it costs

Each failed call at the doubled size is paid for and its answer is dropped: the input tokens of the candidate lines it held, and the time until it failed.

In a graph check and in a ranking pass that time comes out of a pass limit of 45 seconds (`prefilterDeadline` at `pkg/application/prefilter.go:22`, `model.DefaultRankingTimeout` at `internal/model/verifier.go:129`). A candidate the judge has not scored when the limit ends goes to the agent unjudged. 20261121-221907-d-tac-4rg plans a judge time limit of 1 minute by default and a minimum of 50 judged entries. Failed calls at the doubled size spend from that limit as well.
