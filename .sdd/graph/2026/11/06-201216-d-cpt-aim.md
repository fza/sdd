A graph repository kept apart from its code repository is read and written only through one clone sdd owns per machine, and writing an entry into a connected graph is gated on both sides and off by default.

sdd keeps that clone at `$XDG_DATA_HOME/sdd/repos/<repo-id>/`. It serves the project whose code repository names the graph with `graph_repo: <repo-id>`, and every project that declares the graph as a dependency. The clone is partial and sparse: it fetches all commits and trees, but file contents only for `.sdd/` and, when `graph_dir` lies outside `.sdd/`, for that directory as well. sdd never reads or writes a clone a person made.

Nobody edits the sdd clone by hand. Before every operation on it, sdd silently discards uncommitted changes: it restores tracked files and removes untracked ones. A marker file `SDD_MANAGED__EDITS_ARE_DISCARDED.md` at the clone's root says so and tells a person to edit the graph in a clone of their own. The clone's own `.git/info/exclude` ignores the marker, so the repository's `.gitignore` stays untouched.

Today a split project needs a hand-made checkout at its `project_dir` path (20261028-115146-s-tac-15i), and a connected graph gets a second, read-only clone in sdd's cache (20260606-003344-d-cpt-s6q). Two projects on one machine that connect to each other's graphs therefore hold four checkouts of two repositories. With one clone per graph repository, the graph lives in one place on disk, whether a project owns it or connects to it. Because only sdd writes to that clone, it never holds hand edits, and every merge into it reduces to cases fixed rules settle without asking an agent or a person; a tactical directive building on this one names those rules. Measured on a copy of this project's graph with 301 commits of history, a full clone downloads 12,644 KiB and the partial sparse clone 5,249 KiB.

This refines 20260713-214050-d-cpt-65i, which rejected persistent managed writable clones for now because sdd would then own repository lifecycle, locking, cleanup and recovery. For the graph repositories it serves, sdd takes that on: every capture into a project's own graph is a write, so a clone per write does not fit. The connected-repository cache stays read-only and is never a write origin, and the directive's repository-and-branch authority rules stand unchanged.

It also refines 20260713-214523-d-cpt-n8z: a capture into a connected graph writes through the target's sdd-owned clone instead of an ephemeral one, and needs permission from both sides. The writing side allows it with `connected.write`, layered global, project and local, default false. The receiving graph allows it with `inbound.accept`, set only in its committed `.sdd/config.yaml`, default false. Both take a per-repository override. Permission to write into a graph still does not let the new entry reference the writing project: its refs may cross only into repositories the target graph itself declares as dependencies, as 20260713-214523-d-cpt-n8z requires.

Backwards compatibility is complete. `project_dir` keeps working as it does today, and `graph_repo` is added beside it. This design is built in a fork of sdd, and teams may mix the stock release with the fork: stock sdd skips keys it does not know (20260921-174543-d-cpt-tv9), the graph repository stays an ordinary sdd project that stock users work in directly (20261027-192607-s-tac-baf), and the fork's merge routing writes nothing into the shared repository. Stock users simply lack the new features.

Rejected alternatives:

- Writing through the read cache. Unpushed commits break its fast-forward-only pull and its deletion when a repository is disconnected.
- Keeping user clones in sync with the sdd clone, or letting a person name a folder sdd writes to. An uncommitted hand edit in such a folder clashing with pulled commits has no rule that settles it without asking someone.
- A full clone. It downloads 2.4 times as much and keeps code files nobody works with.
- A treeless clone. Reading one entry's history across 300 commits took 77 seconds and grew the download to 37,229 KiB, because each commit fetched its tree on its own.
- A shallow clone. A merge whose base lies beyond the depth fails or needs further fetches.
- Migrating or dropping `project_dir`. It breaks existing setups and stock users.

Accepted costs: someone working in a clone of their own sees sdd's captures only after pulling; the sdd clone sits in a folder nobody opens, so `sdd repo path <repo-id>` prints its path; a hand edit made in the sdd clone is lost without notice; file contents outside the sparse set come from the remote on first use; and sdd owns the clone's lifecycle, never deleting one that holds unpushed commits.
