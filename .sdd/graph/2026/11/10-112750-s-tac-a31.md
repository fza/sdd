`sdd init --graph-repo` cannot switch a code repository that points at its graph through `project_dir` in one run: on the released `v0.18.0-alpha.3.fza.43` it fails three ways, each needing a hand step before it completes. The expected state comes from 20261106-202055-d-tac-eyl: `--graph-repo <url>` sets the pointer and guard in one commit, and with both pointers set this sdd follows `graph_repo` while older builds keep `project_dir`, so one config serves a transition.

Observed while switching three code repositories, each with a sibling graph checkout named by `project_dir` and an existing sdd-owned clone from reading it as a dependency:

1. With the project settings (participant, `llm`, `llm_prefilter`, `verify`) already moved into the code repository's `.sdd/config.local.yaml`, where a `graph_repo` project keeps them, `sdd init --graph-repo` is refused by project resolution before it runs: "config.local.yaml sets participant, sync, dialogue, llm, llm_prefilter, verify, but a repository with project_dir may set only project_dir, hooks". Adding `graph_repo` by hand to the committed `.sdd/config.yaml` first let init proceed.
2. `EnsureGraphClone` leaves an existing clone as it stands, without a fetch, so init refreshed the setup on a base behind the remote, and the publish push was rejected (`fetch first`). An `sdd sync` in the code repository pulled and merged, after which init completed.
3. With the clone level with its remote and nothing to push, init still failed: "push ... deferred (cooldown)" from the 30 s push cooldown of 20261107-095427-d-tac-yux. A rerun after the cooldown completed.

Candidates, unsettled: resolve the work repository's layers for `--graph-repo` without the `project_dir` key check; fetch an existing clone before init refreshes it; treat a deferred push with nothing waiting as success.
