sdd starts git network operations on its own: fetches and pushes of the graph a project works in, and pulls of the repositories it connects to. Every such operation, automatic or commanded, from the CLI or the MCP server, passes one gate per machine that keeps it within limits per remote host and protocol. Remote hosts limit git traffic per user, per IP address and per repository, and sdd's traffic shares those budgets with everything else the person does.

The published limits this rests on, as of 2026-11-07:

- GitLab.com: Git over SSH, 600 operations a minute per user, project and git command. Git over HTTPS, 10,000 requests a minute per authenticated user, 15,000 a minute per IP address without login, and 2,000 a minute for all traffic from one IP address; each clone, fetch or push counts as one request. At most 60 clones and fetches over HTTPS and 30 over SSH run at once per repository, shared by all users. The SSH server caps handshakes in progress through `MaxStartups`, with no published value. Plan limits proposed but not in effect would cap a Free user at 5,000 requests an hour and 100 a minute across Git over HTTPS, the API and the web.
- GitHub.com: no published limit on concurrent git operations or SSH connections. It recommends at most 15 read operations a second and 6 pushes a minute per repository. Since May 2025, HTTPS clones without login fall under stricter limits with no published number.
- Neither host limits git operations differently on Free and paid plans today.

## Configuration

The limits live in the global config only, under `sync:`:

```yaml
sync:
  default:
    fetch_cooldown: 5m
    push_cooldown: 30s
    retries: 2
    concurrency: 2
    ssh: {per_hour: 600}
    https: {per_hour: 600, per_hour_unauthenticated: 60}
  hosts:
    gitlab.com: {}
    github.com: {}
```

The built-in defaults are the values shown, the same for every host. An entry under `hosts` overrides any default key for that host. A `fetch_cooldown` below 1m or a `push_cooldown` below 10s is ignored with a warning naming the file and key. The project-level keys `sync.mode`, `sync.interval` and `sync.cooldown` are no longer read. They stay known to the config schema, so the unknown-key warning stays quiet for them, and `sdd init` asks nothing about sync.

## The gate

- One record per machine at `$XDG_STATE_HOME/sdd/remotes.json`, read and rewritten whole under a `gofrs/flock` lock and replaced by an atomic rename. Per host and bucket (`ssh`, `https`, `https_unauthenticated`) it holds per-minute counters over the last hour; per repository, the last fetch and push attempts, their outcomes, the retries used and the next allowed times. It replaces the last-fetch marker in `.sdd/tmp/` and the last-pull marker in each cache clone.
- An operation runs only when the cooldown for its kind has passed for its repository, its bucket has room in the last hour, and fewer than `concurrency` operations run against its host. Otherwise it is skipped and reports the next allowed time.
- The cooldown starts again after a successful operation or after the first failed one. A transport failure (timeout, connection reset, HTTP 5xx, `ssh_exchange_identification`) is retried up to `retries` times at random moments within the cooldown, and after that nothing runs until the cooldown ends. A refused login, a rate-limit answer (HTTP 429, `unable to handle this request due to load`), a rejected push and a merge conflict are not retried before the cooldown ends. Retries count against the hourly limit.
- Each next allowed time moves by a random amount of up to 10 percent, so repositories with equal cooldowns do not come due together.
- A push runs only when local commits are waiting. When the remote has moved, the fetch and merge the push needs belong to the push and run under `push_cooldown`.
- Whether an HTTPS operation logged in is read from git's trace output (`GIT_TRACE2_EVENT`): git starts a credential helper only after the server asks for a login. sdd records the answer per repository, and until it is known the operation counts against both HTTPS buckets. SSH always logs in.

## Surfaces

- `sdd sync` reaches only the repository at hand: the graph in the code repository, or its `graph_repo` clone.
- `sdd repo sync [<repo-id> ...]` reaches connected repositories, all or the named ones, with fetches and owed pushes. The MCP tool `sync_repos(session, repos?)` does the same and returns per repository `synced`, `pushed`, `skipped` with the next allowed time, `failed` with the reason and the retry time, or `refused` for a repository that is not connected.
- No command or tool bypasses the gate. A commanded sync within the cooldown is a skip that says so.
- `sdd serve` checks the gate once a minute and runs whatever is due, for the project's graph and its connected repositories. A refresh never blocks the operation that started it: reads use the clone as it stands, and a failed or skipped refresh shows as the sync notice that timed sync delivers (the `sync_notice` field of engine responses, a banner on the CLI). Fetch-on-miss at capture also passes the gate; when the gate refuses, the ref stays unresolved and the capture block stands.

## One clone per connected repository

Every connected repository, whether a graph repository or a code repository holding its graph, is read and written through one sdd-owned clone at `$XDG_DATA_HOME/sdd/repos/<repo-id>/`, partial and sparse as 20261106-201216-d-cpt-aim describes. The full read-only clone under `$XDG_CACHE_HOME` goes, and that directory keeps search indexes only. Cache pruning moves to the sdd-owned clones and never removes one holding unpushed commits or a held lock. An existing cache clone is dropped, and the sdd-owned clone is made on first use.

## Automatic sync for graph repositories only

A graph inside the code repository is no longer synced automatically: `sync.mode: auto` goes, and `sdd sync --pull` stays the way to merge upstream graph commits there. The background check every CLI command runs still fetches that repository, through the gate. A `graph_repo` clone is always synced automatically.

## Rejected alternatives

- An hourly limit without a cap on concurrent operations. The hard limits are per minute and per concurrent operation, and an hourly budget alone can exceed them in one burst.
- A record of an index plus fixed or versioned data slices written in place. Rewriting the JSON whole takes 3.6 ms at 1,000 repositories (8.1 ms with fsync) and 15 ms at 5,000 (21 ms with fsync), as the [measurement of the record rewrite](./07-095427-d-tac-yux/git-operation-record-benchmark.md) shows; a slice format needs a binary layout, version handling, compaction and torn-write checks that an atomic rename makes unnecessary.
- A library. `mennanov/limiters` has no file backend and no cooldown, and brings Cosmos, DynamoDB, etcd, Consul, ZooKeeper, Redis and grpc into `go.sum`. `throttled/throttled` v2 had no release in a year, limits by rate with burst instead of an hourly window, and has no concurrency cap. `cenkalti/backoff` covers only the retries, which the standard library does in a few lines.
- A new `sdd fetch` command. `sdd sync` and `sdd repo sync` already separate the repository at hand from connected ones, and both are stock commands.
- Keeping the cache clone beside the sdd-owned clone. Every written repository then fetches twice per cooldown, and a capture is visible to reads only after the cache pulls it.

## Accepted costs

- Hosts count per user across machines and per IP address across everyone behind one network address, while sdd sees one machine. Its defaults therefore take a small share: 600 an hour is 12 percent of the proposed GitLab Free limit of 5,000, and 60 an hour without login matches GitHub's limit for API calls without login.
- With a 5m fetch cooldown, 600 an hour covers about 50 repositories before fetches wait, and 60 an hour covers 5 public repositories over HTTPS without login.
- A commanded sync cannot fetch sooner than the cooldown allows.
- A new entry reaches the remote up to 30 seconds after its commit, longer when the hourly limit is used up.
- A project-level `sync.cooldown` set for stock sdd stops applying without notice, and automatic sync of a graph inside the code repository goes.
- Until sdd knows whether an HTTPS repository needs a login, each operation counts against both HTTPS buckets, and an operation that does need one costs two requests.

## Acceptance criteria

- [ ] The global `sync:` block takes the keys and defaults above, host entries override the defaults, values below the minimums are ignored with a warning, the project-level `sync.mode`, `sync.interval` and `sync.cooldown` are not read and raise no warning, and `sdd init` asks nothing about sync.
- [ ] Every git network operation sdd starts passes the gate; several processes asking for one repository's fetch within its cooldown run exactly one fetch.
- [ ] Operations beyond `per_hour` within one hour are skipped per bucket and report the next allowed time.
- [ ] No more than `concurrency` operations run against one host at once across processes.
- [ ] A transport failure is retried at most `retries` times within the cooldown at random moments; a refused login, a rate-limit answer, a rejected push and a merge conflict are not retried before the cooldown ends; the cooldown starts again after a success or the first failure.
- [ ] A push runs only with commits waiting, under `push_cooldown`, including the fetch and merge a rejected push needs.
- [ ] Whether an HTTPS operation logged in is read from `GIT_TRACE2_EVENT` and recorded per repository, and an unknown one counts against both HTTPS buckets.
- [ ] `sdd sync` reaches only the repository at hand; `sdd repo sync` and `sync_repos` reach connected repositories with fetches and owed pushes, report the outcome per repository, and never bypass the gate.
- [ ] `sdd serve` runs due operations for the project graph and its connected repositories without a configured interval, and a failed refresh shows as the sync notice without blocking a read.
- [ ] Connected repositories are read and written through the sdd-owned clone, no clone remains under `$XDG_CACHE_HOME`, pruning never removes a clone with unpushed commits or a held lock, and an existing cache clone is replaced on first use.
- [ ] A graph inside the code repository is not synced automatically, and `sdd sync --pull` still merges there.
- [ ] Read-only and read-write repositories share one code path; the last-fetch and last-pull markers, the separate cache clone path and its cooldown are removed.
