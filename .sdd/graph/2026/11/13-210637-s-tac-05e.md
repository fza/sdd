sdd's auto-commit now records a tracked file that is gone from both disk and index, as `git rm` leaves it, instead of failing: `git add` gets only the paths still on disk, and the commit's own pathspec records the deletion. Commit 859324e9 on `pr/fix-init-deleted-path`, merged into `fza-fork` at 1d7dbc67.

In a project whose `.gitattributes` held only the line sdd init removes, init deleted the file and the deletion was staged. Init's commit then ran `git add --all -- <paths>` with that path and git refused it (`fatal: pathspec '…/.gitattributes' did not match any files`, exit 128), so the commit failed. The path reached the commit through the changed-paths filter of 20261110-101216-s-tac-w3o, since a staged deletion differs from the last commit, and the retry record of 20261030-182052-s-tac-t2c kept the failed commit pending; a re-run on a build with this fix passes the recorded path through the fixed commit call; no re-run in that project has been made. The CLI's auto-commit call (`CLI.Commit`, used by `sdd new`, summarize and init) stages every commit this way, so any of them would fail on such a path; the engine's git finalizer has its own staging calls, commits only entry files it just wrote, and is unchanged.

The design Felix Zandanel approved for this fix also staged the missing paths with `git rm --cached --ignore-unmatch`. That step was dropped: `git commit -- <path>` records the deletion of a tracked path on its own, and with the step switched off every commit test still passed, so it added code that carried nothing.

`TestCommit_RecordsATrackedPathMissingFromDisk` commits a deleted `.gitattributes` beside a new file, with the deletion staged and unstaged. The staged case failed with git's refusal before the change and passes after it; handing `git add` every path again, missing ones included, makes it fail again.
