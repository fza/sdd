A revised draft that any call delivers to a waiting deep verifier now starts that verifier's round in the same call, and a round a call owed and never started is started by the session's next call.

The defect was seen in a consumer project on fza.52. A drafting agent amended a capture's staged body through `stage_attachment` patches. The staging re-advanced the capture to `deepRevise`, which delivered the revision to the waiting headless child of the verify procedure (20261109-010000-d-prc-vfy), and the child logged it as received. Only `WorkflowSession.Advance` launched the rounds of the children a call delivered to. The staging path did not, and the list of those children was held in memory for the one call, so no later `next` launched the round either. The capture stayed at `deepWait` until the child's idle timeout ended it, then failed. sdd's relaunch of a headless verifier for a revision (20261114-153325-s-tac-2er) thus held only for a revision that `next` delivered. Like the capture publish fix (20261119-221932-d-tac-c0y), the defect concerns a committed effect that outlives the call that made it: the delivery was logged, the launch it required was not.

The fix has four parts:

- `Advance` and `StageAttachments` end in one shared tail, `settleDelegates` in `pkg/application/workflow_delegate.go`. It ends the forks whose move ended. Then, for each live delegate the call sent input or that is owed a round, it launches the round or composes the handoff for an agent that launches the delegate itself.
- An owed round is read from the child's session log (`owesRound`): sdd launched rounds for the child, none is pending, and its last `received` event follows its last round outcome. The check reads the round launch and outcome records that the detached round processes write there (20261114-172813-s-tac-k3w), so it holds across a restart, as the event-sourced session model requires of state the log can rebuild (20260914-113737-d-cpt-qst). A child without a launched round is the harness's to drive and is never owed one.
- `StageAttachments` returns a `StageResult` with `Files` and `Dispatches`, and the MCP `stage_attachment` result carries `dispatches`, so an agent that launches the verifier itself is told to continue it.
- Fresh forks are unaffected: only a chooser answer inside `Advance` forks a delegate.

Rejected: only routing the staging path through the launch step, because any later path that delivers outside `Advance` would lose its round again; only the durable owed-round check, because the delivering call would still return without the launch.

Accepted costs: every `next` and staging call reads the session log of each live delegate child it did not deliver to; `StageAttachments`, the fork's batch method, changes its exported return type, so its Go callers adapt; stock's `StageAttachment` and `EditStagedAttachment` keep their signatures as wrappers in `pkg/application/compat.go`.

Open, named and not fixed:

- A child that ended while its fork is still live would make every call fail on the launch. No path to that state was found.
- Batch approval ignores a dispatch a batch option carries. No batch option carries one today.

Settled: built as `9aa4c9c4` on `next/fix-delegate-relaunch`, merged into `fza-next` (`5558b9e8`). Three new tests cover it: a revision staged as a patch launches the headless round, an owed round launches on the next call, and `stage_attachment` answers the dispatch it owes. The staging test failed before the fix, and the full isolated suite passes.
