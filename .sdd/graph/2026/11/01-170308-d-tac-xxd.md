While a background cache pruning run holds a store's lock, a search waiting about 50 ms at the 99th percentile counts as within the criterion of 20261101-131514-d-cpt-9ci that pruning adds no noticeable latency to a command or MCP call. The median search stays unchanged during a run. The measured tail (20261101-160940-s-tac-03f) is about 45 ms against about 1 ms without a run, on a heavily loaded machine; a run happens at most once a day and lasts as long as its lock steps.

The likely causes stay recorded for a later reopening, read from the code but not profiled: every pruning step holds the write lock through the manifest save's file and directory sync (`internal/index/manifest.go`), which on macOS is a full flush; each step bumps the store generation, so the next search rebuilds its segment view under the write lock (`internal/index/segments.go`); and a waiting search retries the lock every 20 ms (`internal/index/store.go`).

Rejected:
- Profiling the causes and fixing the largest now. It changes the index store's locking for a wait that occurs at most once a day.
- Leaving the gap open. The measurement and its reading would wait unowned.

Accepted cost: the criterion is weaker than first written. A larger store or a slower disk could stretch the tail with no test watching it.

Reopens when a user or agent notices a search slowing during a run, or a measurement shows the 99th percentile above about 100 ms.
