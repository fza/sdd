An agent that opens a new sdd session in the same conversation is to name an earlier session it still holds, prove with one answer that it still holds the oldest text that session served, and then get every text identical to one served there short.

## Decision

**The link.** `start_session` takes an optional argument holding the handle of an earlier session whose served texts the agent still holds in its context. The handle was issued to that agent, so sdd derives nothing from the connection. Links chain: a third session that links the second carries the texts of the first through the second's link. A delegate's child session links nothing and gets every text in full, since a delegate starts with a fresh context, the only launch mode 20260829-122157-d-cpt-zpe supports.

**The question.** The opening response of a linked session ends with the text question of 20261121-230157-d-tac-ym8. It asks about the oldest text, by its latest copy, among everything the session and its linked sessions have served and still count as held. Texts repeat across sessions, and the agent holds the newest copy: in real conversations the nearest earlier copy of a repeated text lay a median of 48.8k tokens back, its first copy 258k. The agent's context runs in one line from old to new, so a held oldest text proves the whole span after it.

**The answer.** A right answer at the next call proves the text asked about and every text whose latest copy is newer. In the next response sdd may serve short any text identical by content to one of them, whichever linked session served it. sdd compares texts by content after removing the parts that differ per session, such as session handles. After a wrong answer or `lost`, sdd empties the held set and sends the next response in full, as today. Only texts served from then on count as held: each text that response serves gets a new latest copy and starts the held set again. A compaction removes everything before a point, and one full response re-serves what the agent needs next, so a compaction costs one full response, not one per lost text. A partial loss, an old text gone while newer ones are held, costs the same single full response. The opening response comes as today, since no answer precedes it. From the next call on, each call's own answer decides, as 20261121-230157-d-tac-ym8 sets.

**The same rule within one session.** The question of 20261121-230157-d-tac-ym8 targets the oldest text, by its latest copy, the session still counts as held, in place of any text the agent should still hold at its next call. A right answer about a recent text can hide a lost older one, and a pointer could then name text the host removed.

**A link sdd cannot use.** A handle sdd does not find, never issued or removed by the sweep of 20261121-223858-d-tac-cg2, is refused with a message that says the session is unknown or was removed and that `start_session` works without the argument. A handle is a capability, and a wrong one is a caller error. sdd keeps no record of swept handles: a swept session sat idle past `sessions.retention`, so inside one conversation this is rare, and a refusal costs one call. A session whose log holds no record of served texts, one stock sdd wrote or one the fork wrote before 20261121-230157-d-tac-ym8 was built, opens the new session without the carry-over and with every text in full, and the opening response says in one line that the link was not used and why. Today `start_session` takes no handle, and the session lookup behind `resume_session` answers a handle without a log as an unknown session (`ErrSessionNotFound` in `pkg/application/errors.go`). The sweep deletes a session's log (`collectSessions` in `pkg/application/collect.go` calls the session store's `Delete`), so a swept handle and one never issued look the same. A log stock writes carries `served_blocks` content hashes and no served texts.

**Framing.** Within a session, framing blocks follow the rule of 20261121-233256-d-tac-mm2 for each caller. Through a link they count as served only after a right answer, like every other text.

**Two callers.** The link carries texts by the answer, not by the handle. A caller that never saw a text answers `lost` and gets it in full. The latest copy of a text is counted per session, not per caller: a full serve to a second caller on the handle gives a text a newer copy the first caller never received, and a right answer of the first caller can then serve short a text it lost. This adds a case to the gap 20260828-171826-s-cpt-ox6 records, that sdd cannot tell two callers on one handle apart; the mark 20261121-233256-d-tac-mm2 leaves open would close it.

**The way back.** The answer to the question pending at a compaction can come from the summary, one call late, as 20261121-230157-d-tac-ym8 accepts. The probe saw this once: a Sonnet summary held the answer but almost none of the text, and the next repeat went out as a pointer to a text the agent no longer held. This plan leaves `reread` as 20261121-234844-d-tac-156 states it: it "stays as it is until a decision of its own settles it". While it stays, an agent that meets a pointer to a lost text lists the piece in `reread` and gets it in full. `resume_session` serves its call in full.

## Measured basis

Two measurements, attached in full: [cross-session repeats in 18 real conversations](./22-105026-d-tac-wl5/cross-session-repeats.md) and [the oldest-text probe](./22-105026-d-tac-wl5/oldest-text-probe.md). Opus and Sonnet are the main agents measured.

**Real conversations.** 18 Claude Code conversations with at least two sdd sessions each, C01 to C18, hold 39 later sessions. Sessions per conversation: median 3, range 1 to 11.

- The `start_session` result of a new session is a median 13,375 bytes, about 5.2k tokens. Up to the first capture playback, at most 15 sdd calls, a new session receives a median 92,940 bytes, about 36.4k tokens.
- Of those bytes, 62% had already reached the agent in an earlier session of the same conversation, 53% with no compaction in between. By piece kind, carried and still in context: framing 90% and 77%, type-system lane 100% and 83%, other instruction lanes 71% and 60%, report schema 95% and 82%, graph entries 5% and 3%. Hashing whole lanes, the strict bound, gives 52% and 44%.
- The carried text still in context is a median 19.6k tokens per later session. At assumed cache prices that is about 111k fresh-input-token equivalents per later session, over a median of 73 later API calls.
- The nearest earlier copy lay p10 8.4k, median 48.8k and p90 147k tokens before the new session. The first copy lay a median 258k back.
- 15 compactions ran, all automatic at about 968k tokens, in 7 conversations. In 4 later sessions every earlier copy had been compacted away.

**Probe.** 8 runs with Opus and Sonnet as main agent, two linked sessions each, the second session asking about the oldest first-session text not yet asked about. A right answer turned the repeat of that text into a pointer of about 270 characters.

- With the text in context: 204 of 204 answers right, for each model 24 of 24 up to 20k tokens back, 68 of 68 from 20k to 60k and 10 of 10 past 60k. The farthest answer came about 66k tokens after its text.
- Overall Opus answered 107 right and 13 `lost` of 120, Sonnet 103 right and 17 `lost`. No answer was wrong. Every `lost` came after a compaction.
- Without compaction the second session sent about 5.5k of 44.1k characters, 12.6%.
- Compaction between the sessions: Opus 1 right and 11 `lost`, Sonnet 12 `lost`. The one right answer had its text in the summary.
- Compaction inside the second session: Opus 4 right and 2 `lost`, Sonnet 1 right and 5 `lost`. Every right answer after a cut had its passage in the summary. The Sonnet case above is the one pointer to a lost text, and its step report still passed because the summary listed every sign-off phrase.

## Rejected

- **The link with the question of 20261121-230157-d-tac-ym8 as it stands.** A right answer about a recent text can hide a lost older one, so a pointer may name lost text.
- **Each session on its own, as today.** Every new session pays its first serves again, a median 19.6k tokens the agent already holds.
- **A question about a text's first copy.** The agent holds the newest copy. The first lies a median 258k tokens back, where a compaction may have removed it while a later copy stays.
- **A question about the oldest of the texts the next response is predicted to serve.** It needs a forecast of the next response, and a right answer about a newer text says nothing about older ones.
- **Dropping only the text asked about after `lost`.** After a compaction each lost text then costs a full response of its own.
- **A search for the cut point by several questions.** It takes several questions and responses for the outcome one full response gives.

## Accepted costs

- One more optional argument on `start_session`.
- A change to the choice of text of 20261121-230157-d-tac-ym8.
- The opening response of a linked session comes in full, a median 5.2k tokens.
- The one-call lag at a compaction can send one pointer to a lost text. `reread`, while it stays, and `resume_session` are the way back.
- A delegate gets every text in full.
- A wrong answer or `lost` costs one response in full, also after a compaction. Texts held before it go in full when sdd serves them again. This holds for every caller on the session, also when the `lost` came from a second caller on the handle or was given with the text in view.

## Not measured

- Distance past 66k tokens. The real p90 is 147k. No probe context passed 74k tokens.
- Automatic compaction. The probe used manual `/compact` far below the window. The real compactions ran at about 968k tokens.
- Each compaction finding rests on one run per model.
- The probe asked about its first step about 19 times, which keeps words of it in recent context, and the summary writer saw the rule.
- Invented step texts, more uniform than procedure text.
- Recall in real conversations. There "in context" means only that no compaction ran in between.
- Agent hosts other than Claude Code, and delegate sessions.

## Fork compatibility

Checked point by point against 20261119-013237-d-cpt-fu4 as 20261121-234844-d-tac-156 corrects it. The argument is optional: a `start_session` call in stock's shape works and gets everything in full. The plan departs from no point.

- Point 37: the argument joins the deviation point 37 names. A program that sends it to stock's server gets an unknown-argument error, as for the answer argument and `reread` while the fork keeps it.
- Point 42: the argument is a new field on the exported `StartSessionArgs` in `pkg/mcpapp/tools.go` and `WorkflowOpenRequest` in `pkg/application/workflow.go`. No exported signature changes.
- Points 44 and 45: the link is recorded in fork sessions, which stock already skips by their fork-only start event. No session crosses between the binaries: a link to a session stock wrote opens without the carry-over.
- Point 28: the shared session folders and the sweep stay as they are.

Upstream: the argument joins the item that 20261121-234844-d-tac-156 sets for point 37 on the directive's closing list of outcomes proposed upstream, which becomes the text question with its required answer and its carry-over across linked sessions. An agent that never sends the argument works with fork and stock alike. A correction entry that updates the directive's list is owed, as one is for point 38 under 20261122-103723-d-tac-npg. Accepted cost: upstream may refuse the proposal. Rejected: keeping the argument on the fork alone, since a program that sends it to stock's server would then get an unknown-argument error for good.

## Not decided here

- What becomes of `reread`, which 20261121-230157-d-tac-ym8 leaves to a decision of its own.

## Context

20261121-223858-d-tac-cg2 has agents start a new session on every change of the ground topic and keep the earlier handle, so a conversation holds several sessions and the agent holds the handles the link names.

## Layers

No graph write or read changes, so no command, query, handler or finder is added.

- **Model** (`internal/model`), pure: picking the text whose latest copy is oldest, and comparing texts by content with per-session parts removed.
- **Engine** (`internal/engine`): today a session keeps its served memory from its own log, each piece as a name and content hash (`Piece` in `internal/engine/pieces.go`) with the tags folded from its `anchors` events (`EventAnchors` in `internal/engine/session.go`). 20261121-230157-d-tac-ym8 adds each served text. This plan records the link as a session event, reads the served record of each linked session along the chain, and picks the question across them.
- **Application** (`pkg/application`): the link passed through `WorkflowOpenRequest` to the engine, and the linked sessions' logs loaded.
- **MCP shell** (`pkg/mcpapp`): the optional field on `StartSessionArgs` with its description.
- **Served text**: the session shell's rule from 20261121-223858-d-tac-cg2 tells the agent to pass the earlier handle when it starts a new session.

## Acceptance criteria

- [ ] `start_session` takes an optional argument holding an earlier session's handle, and a call without it behaves as today.
- [ ] With a link, the opening response ends with the question about the oldest text, by its latest copy, among everything the session and its linked sessions have served and still count as held.
- [ ] After a right answer, the text asked about and every text whose latest copy is newer may come short in the next response, matched by content with session handles removed.
- [ ] After a wrong answer or `lost`, sdd empties the held set, the next response comes in full, and only texts served from then on count as held.
- [ ] When several held texts are lost at once, one full response follows the `lost`, and a right answer after it serves short again.
- [ ] A session linking a session that links a third carries the texts of both earlier sessions.
- [ ] A delegate's child session carries no link and gets every text in full.
- [ ] Within one session the question targets the oldest text, by its latest copy, the session still counts as held.
- [ ] While `reread` exists, naming a piece pointed at through a link serves it in full.
- [ ] `resume_session` serves its call in full whatever the link.
- [ ] A link holding a handle sdd does not find, never issued or removed by the sweep, is refused with a message that says the session is unknown or was removed and that `start_session` works without the argument.
- [ ] A link to a session whose log holds no served texts, one stock sdd wrote or an older fork build wrote, opens the session with every text in full, and the opening response says in one line that the link was not used and why.
- [ ] The link changes no exported signature in `pkg/`.
- [ ] Before it ships, a live probe with Opus and Sonnet as main agent asks about texts from past 66k to at least 147k tokens back and reports right, `lost` and wrong answers per distance band.
