`stage_attachment` takes a `files` array and nothing else: one call stages one or more files, each item `{name, content | path | patches}`, so an agent staging the attachments of a capture spends one tool call, not one per file.

## Shape

```
stage_attachment {session, files: [{name, content | path | patches}, ...]}
-> files: [{handle, sha256, bound}, ...]
```

- The single-file fields `name`, `content`, `path` and `patches` leave the top level. A call carrying them is refused with a message naming `files`.
- Each item takes exactly one of `content`, `path` and `patches`. `content` stages the given text; `path` stages the file read from that local path and keeps the path, so a playback confirm reads it again; `patches` edits a file already staged under `name` with exact search-replace pairs. A name appears at most once in a call, so a `patches` item edits the file as staged before the call.
- Results come back in call order, one per item, with the fields a single stage returns today.

## Failure

- Every item is checked before anything is written: names, the one-source rule, paths readable, patches applying, and the unfinished-write refusal for a file a running capture takes its body from. One failing item refuses the whole call and names that item.
- A write failing after the check (disk, log append, or the unfinished-write check rerun after a catch-up per 20261114-120345-d-tac-6n4) stops the call. The error names the item, says whether that item was staged before the failure, and lists the files staged before it, which stay staged.

## Why one shape

One shape to learn and to describe in served instructions. Two ways to stage one file would leave every instruction naming both, and a call passing both would need its own refusal.

## Rejected

- A `files` array beside the single-file fields: existing calls and installed renders keep working, and older and newer builds stay compatible. Rejected for the two shapes it keeps.

## Accepted costs

- A breaking change to the MCP tool: existing callers, cached tool schemas and calls between older and newer sdd builds fail until they pass `files`.

## Fulfilled when

- One call stages three files, from `content`, `path` and `patches`, and returns three results in call order.
- A call whose second item fails the check stages nothing and names that item.
- A call with a top-level `name` is refused with a message naming `files`.
- Served instructions and the tool contract snapshot show only the `files` shape.
