`sdd move` moves a graph to another folder or repository with its history, leaving the same state a fresh `sdd init` of the new layout would plus the moved content, and nothing stranded behind. The ignore and attribute files sdd writes stop depending on `graph_dir`, so no move and no hand edit of `graph_dir` leaves them stale. The full spec is attached: [move spec](./09-004100-d-tac-f8r/graph-move-spec.md).

**Forms.** CLI only, no MCP verb; flags mean what they mean for `sdd init`. The target must hold no graph yet.

- `sdd move --graph-dir <dir>`: to another folder in this repository, or back into it from a separate one.
- `sdd move --project-dir <path>`: out to a checkout on disk, created and `git init`-ed when missing; a non-empty repository without a graph is accepted.
- `sdd move --graph-repo <repo id>`: out to a repository sdd clones and pushes itself (20261106-201216-d-cpt-aim).

**History.** Inside one repository a `git mv`. Across repositories `git subtree split --prefix=<graph dir>`, pushed into the target, the same way back. No commit is rewritten (20260924-231829-d-cpt-r1c). Without `git subtree` the move refuses, naming the cause. The move refuses while the graph folder holds uncommitted changes and makes its own `sdd:` commits in both repositories.

**End state.**

- Committed keys beyond the pointer keys move into the graph project's `.sdd/config.yaml`; the code repository keeps the pointer config init writes, and the reverse on a move back. `meta.json` moves with the graph.
- A `--project-dir` target gets init's install step (skills, MCP registration) with the code repository's scope and agents, in the move commit. An sdd-owned clone gets none.
- A checkout the graph leaves ends with no sdd files: config, `meta.json`, `.sdd/.gitignore`, skills and MCP registration are removed in the move commit. A skill whose content no longer matches its `sdd-content-hash` stamp refuses the move before anything changes, naming the file.
- Machine-local data (sessions, staged blobs, stats, machine-local keys of `.sdd/config.local.yaml`) moves to where the new layout reads it.
- In a repository holding only the graph, the default graph folder is `graph/`.

**Publishing.** Before the push, sdd fetches. An sdd-owned clone that moved on since the split is pulled and split again, at most 3 attempts. A person's checkout is never pulled: the move refuses with nothing changed and names `sdd sync --pull`.

**Version floor.** The move raises `minimum_version` in `meta.json`, so builds without move records refuse the moved graph. A released build writes its own version or keeps a higher recorded one; a dev build writes `MoveRecordsMinimumVersion`.

**Move record and strays.** The move commit carries trailers, in both repositories where both change:

- `sdd-move: v1`, `sdd-move-id: <ULID>`, `sdd-move-from: <location>`, `sdd-move-to: <location>`, `sdd-move-revision: <source revision>`, `sdd-move-entries: <count>`.
- A location is `<kind>:<address>` with options as query parameters, parsed by the adapter owning the kind: `git-dir:<dir>`, `git-path:<path>?dir=<graph dir>`, `git-repo:<repo id>?dir=<graph dir>&branch=<branch>`. Later store kinds fit without a format change. An unknown kind or version is refused; unknown fields are ignored. Each store adapter reads its own move records; the stray check is pure and lives in `internal/model`.
- A stray is an entry-shaped file in a former location whose id the current graph does not hold. sdd checks on start, after each pull or sync and on each config change; while strays exist, CLI and MCP refuse, naming the files and the `sdd move` call that carries them over. A former `project_dir` without a checkout on this machine is skipped.

**Search index.** A store is keyed by the repository's `repo_id`, else by a hash of its root path, so a move into another repository changes the key. The move links `<cache>/index/<new repo key>` to the store's real directory as a relative symlink, resolved through existing links so links never chain; the store is neither copied nor renamed, so agents still on the old key share it and its locks. A key that already is a real directory stays. Each open through a link touches `<cache>/index/.links/<hash of key>`; any store open removes links, with their markers, unused for 30 days, never a real directory. `sdd index gc` and store listings count each real store once.

**Ignore and attribute files.** The root lines init derived from `graph_dir` were what every move had to rewrite in both repositories, so they change with the move. This replaces the `.gitignore` part of 20261029-132740-d-tac-g32, which gave both repositories the same root lines; the rest of it stands.

- Wherever sdd creates `.sdd-runtime/` (graph lock, titles lock, lineage, publication temp file) inside the graph folder, it writes `.sdd-runtime/.gitignore` holding `*`.
- Init writes a committed `.sdd/.gitignore` listing `tmp/`, `config.local.yaml`, `index/`, `stats/`, `sessions/`, `staged-blobs/` in every repository with a `.sdd/`. The root `.gitignore` gets no sdd lines.
- Init writes a committed `<graph dir>/.gitattributes` holding `EntryPathGlob merge=<EntryMergeDriver>` with a fixed pattern (20261030-085158-d-tac-vyt); it travels with the graph through `git mv` and the split.
- Init removes from the root `.gitignore` and `.gitattributes` only the exact lines earlier builds derived; lines added by hand stay. The move rewrites neither root file.

Rejected, with the reasoning:

- printing `sdd init` as the move's last step: the checkout lacks sdd tools until someone runs it;
- turning a vacated checkout into a pointer: it ties a repository to a project it may not belong to;
- keeping skills and MCP in a vacated checkout: sdd tools there fail on every call;
- pulling a person's checkout before publishing: a merge into their working branch can conflict mid-move;
- a guessed upstream release as the floor for released builds: wrong if that release ships without move records;
- a tombstone file at the old location instead of move records: a file someone deletes or never pulls;
- rebuilding the index after a move: a full re-embed every time;
- copying the index: a second path every format change must follow, and the old copy drifts;
- keying the index by the oldest entry ID: a second identity concept beside `repo_id`;
- moving `.sdd-runtime/` to `.sdd/runtime/`: the publish rename would cross folders, losing write confinement and failing across filesystems;
- keeping the root `.gitattributes` line derived from `graph_dir`: stale after a hand edit of the key, and merges conflict on it.

Accepted costs: a checkout that also holds other work loses its sdd tools when the graph leaves it; one manual pull and rerun in a person's checkout that moved on; coworkers upgrade to at least the mover's build; a forge that squashes or rewrites the move commit loses its trailers; a checkout idle for over 30 days that still resolves a swept key re-embeds lazily.

## Acceptance criteria

- [ ] `sdd move` with `--graph-dir`, `--project-dir` and `--graph-repo` moves the graph with its history, no commit rewritten, and refuses a target holding a graph, a dirty graph folder and a missing `git subtree`.
- [ ] After a move the layout matches a fresh `sdd init` of it plus the moved content; a vacated checkout holds no sdd files; an edited skill refuses the move before anything changes.
- [ ] A person's checkout that moved on refuses the publish with nothing changed and names `sdd sync --pull`; an sdd-owned clone retries the split up to 3 times.
- [ ] The move commit carries the `sdd-move` trailers; a stray entry at a former location makes CLI and MCP refuse, naming the files and the `sdd move` call.
- [ ] Agents on the old index key keep reading the same store after a move; links unused for 30 days are removed, real directories never.
- [ ] `.sdd-runtime/.gitignore`, `.sdd/.gitignore` and `<graph dir>/.gitattributes` are written as above; init removes only the exact root lines earlier builds derived.
- [ ] The moved graph's `minimum_version` refuses builds without move records.
