Cache pruning protects the index versions every checkout reading a store still uses, not only those of the checkout that starts the run. Each checkout that searches or fills a store records the versions it currently reads, and pruning keeps every version such a record names while the record is fresher than `cache.retention`.

A store is shared by every checkout of a repository on a machine: the main checkout, its worktrees and other clones (20261101-131514-d-cpt-9ci). The implementation in 20261101-145315-s-tac-m3k keeps only the versions current for the checkout that launched the run. A version another active worktree still reads is deleted once a newer version replaced it elsewhere more than the retention period ago. That worktree's next search re-embeds the entry, and a search running at that moment misses it. The decision accepted that cost only for a branch or worktree untouched for the retention period.

The record is one file per checkout under `<store>/used/checkouts/`, named after a hash of the checkout's graph directory and holding the version hash of each entry as that checkout computes it. A search or fill already computes those hashes, so writing the file adds no hashing. The file is rewritten when the hashes change, and otherwise its modification time is refreshed at most once a day, the same pace as the rule stamps. Pruning reads the files under the store lock in each lock session, keeps the union of the versions named in files fresher than the retention, together with the launching checkout's own as before, and deletes files older than the retention. A checkout untouched for the retention period then loses its protection, which is the cost the decision accepted. Because hashes are recorded as each checkout computes them, they match the store's versions exactly even where binaries hash entries differently, for example by splitting them into chunks of a different maximum length.

Rejected:
- A last-current time on each version in the manifest. Searches would write the shared manifest under the exclusive store lock once a day, contending with fills on the store's busiest file, and the manifest format would change.
- Accepting the gap. An active worktree would keep re-embedding versions replaced on another branch, and its searches would miss them until the fill ends.

Accepted costs:
- One file of about 100 KB per checkout per store, and one small write a day per checkout.
- A narrow race on a checkout's first read of a version replaced more than the retention ago. If a pruning session reads the records just before that checkout writes its own, and deletes the version just after the checkout planned to skip it, the entry is missing until that checkout's next fill re-embeds it.

Fulfilled when pruning keeps every version a fresh checkout record names, expired records are deleted, and tests cover a version kept for a second checkout, a version released once that checkout's record expires, and the record refresh on search and fill.
