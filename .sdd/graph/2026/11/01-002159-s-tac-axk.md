Writing a new entry can silently overwrite an existing entry file. The new-entry handler in `internal/handlers/handler_new_entry.go` writes the file with `os.WriteFile`, which truncates whatever is already at the path. The path comes from the ID: second-resolution timestamp, type, layer and a 3-character random suffix. Two captures in the same second with the same type and layer draw the same suffix about once in 46656 pairs, and the second write then replaces the first entry. Its stored attachments are overwritten the same way. Expected: an entry, once written, is never replaced. Entries are immutable, so a write must never land on an existing file.

The observation came from agentic-helpers, and reading the handler confirmed it: no existence check before the write. A test that captures 1000 entries under a frozen clock gets fewer distinct IDs than captures. The reported IDs repeat and the earlier files are gone.

The risk grows with concurrent writers: several agents capturing at once, or a batch capture.

Candidate remedy (unsettled reasoning): create the file exclusively (`O_CREATE|O_EXCL`), and when the ID is taken, draw a fresh suffix and retry; write attachments exclusively too.
