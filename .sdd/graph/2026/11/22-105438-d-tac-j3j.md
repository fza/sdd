Point 38 of the fork compatibility directive (20261119-013237-d-cpt-fu4) is revised to match the plan for per-host result sizes (20261122-103723-d-tac-npg), and the closing section's list of outcomes proposed upstream gains the result size by host and the carry-over of held texts across linked sessions (20261122-105026-d-tac-wl5); every other point of the directive stands.

Neither plan is built on `fza-next` yet. The revision of point 38 takes effect when the plan for per-host result sizes is built. Until then the fork behaves as point 38 read before. The entry takes the form of the earlier correction of points 17, 28 and 37 (20261121-234844-d-tac-156).

## Point 38: the result size follows the host

So far: "The cap of 18,000 characters per tool answer (`model.MaxResultChars`) and the pages stay. When the same call arrives again without `page` right after a paged answer, the answer opens with a line saying that this is page 1 again and how to get page 2. Cost: one more special case in the server."

Now, under the plan for per-host result sizes: a caller whose MCP client name is exactly `claude-code` gets results of at most 45,000 characters, below Claude Code's 50,000-character threshold for saving a result to a file. When sdd finds `MAX_MCP_OUTPUT_TOKENS` in its own environment, it lowers that bound to 2 characters per token of the variable's value where this falls below 45,000. Every other host, Codex and Claude Desktop included, gets at most 18,000 characters per result and its pages as today. The bounds derived from the cap, for serves, read pages and the verifier's reading pages, follow the caller's limit. The "page 1 again" line stays as written.

Effect on a team that mixes fork and stock: a result's size stays between one server and the host it serves. No shared file, committed setting or machine folder holds it. Only the size of answers differs: a Claude Code agent on the fork's server gets fewer, larger pages than one on stock's server.

Cost of the point: two result sizes to build and test, beside the special case of the "page 1 again" line.

## Proposed upstream

In the closing section's list of outcomes proposed upstream, "result size by host (38)" joins "the 'page 1 again' line (38)". The plan for per-host result sizes left open whether the larger size is proposed upstream. This entry decides that it is, so that the proposal and the fork behave alike, which is that section's stated purpose.

The item for point 37, "the text question with its required answer (37)" as the earlier correction worded it, becomes "the text question with its required answer and its carry-over across linked sessions (37)". The carry-over is the optional `start_session` argument of the plan for carrying held texts across linked sessions, which names an earlier session whose served texts the agent still holds. An agent that never sends the argument works with fork and stock alike. A program that sends it to stock's server gets an unknown-argument error, which joins the deviation of point 37 as the earlier correction worded it.

Each proposal goes upstream after the fork has built its change and passed its test run, the test run of the plan for per-host result sizes for the result size and the acceptance criteria of the plan for carrying held texts for the carry-over, and the owner files the pull request.

Accepted cost: one more correction entry for the directive, and upstream may refuse either proposal.

Rejected: revising point 38 for the fork alone, with no proposal upstream, because the fork would then differ from stock in result size for good. Keeping the carry-over argument on the fork alone, because a program that sends it to stock's server would then get an unknown-argument error for good.

Settled: this entry changes only the graph record and asks for no build of its own. The two plans named above carry the builds.
