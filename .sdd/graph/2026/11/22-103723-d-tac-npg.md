sdd is to size one MCP result by the host that receives it: a Claude Code caller gets results of at most 45,000 characters, below Claude Code's 50,000-character file threshold, and Codex, Claude Desktop and every other client keep today's 18,000 characters. This narrows the bound of 18,000 characters for every host, recorded as a deviation in 20261112-195218-s-tac-day, to the hosts other than Claude Code. It departs from point 38 of 20261119-013237-d-cpt-fu4, which keeps that cap and the pages; the "page 1 again" line of point 38, the part proposed upstream, stays. An entry revising point 38 is owed. The deep verifier's reading then takes a median of 6 calls on Claude Code instead of 20, and the main agent gets fewer `gather`, `show`, `search` and `view` pages by the same rule. A test run with real verifiers comes before it ships.

## Decided

- **No truncation, no file.** Every result reaches the agent whole: no host cuts it and no host saves it to a file, because an agent that has to read a result from a file tends to read only parts of it. Each limit therefore stays below the host's own threshold and depends on no host feature.
- **Claude Code.** sdd serves a caller whose client name is exactly `claude-code` at most 45,000 characters per result, counted as Claude Code counts them (`model.ServedChars`, `internal/model/result_bound.go`). Claude Code saves a tool's text result past 50,000 characters to a file, and also a result past its MCP token limit, `MAX_MCP_OUTPUT_TOKENS`, default 25,000 tokens, for a tool that declares no limit of its own (Claude Code documentation, MCP page, section "MCP output limits and warnings"). sdd reads `MAX_MCP_OUTPUT_TOKENS` from its own environment when present and lowers the Claude Code bound to 2 characters per token of that limit where this falls below 45,000. The measured ratio on sdd results is 2.67 bytes per token (runs below), so 2 leaves a margin of a quarter; at the default of 25,000 tokens the bound stays 45,000, about 17,000 tokens. Whether Claude Code passes the variable to a stdio MCP server it starts is not verified. If it does not, a person who lowers the variable gets larger sdd results saved to a file, a known limit.
- **Codex.** Codex callers keep 18,000 characters. Codex keeps a budget of about 10,000 tokens per tool result and drops the middle of a larger one (20260719-122547-s-tac-40d).
- **Telling hosts apart.** sdd chooses the size of one result at serve time from the client name of the connection that makes the call (`ClientInfo.Name`, `mcpClientName` in `pkg/mcpapp/tools.go:748`). Only the name `claude-code` gets 45,000 characters. Claude Desktop reports `claude-ai` and Codex `codex-mcp-client` (`internal/model/mcpclient_test.go`). `model.ClaudeClient` matches any name holding "claude", so this rule gets its own exact match. Every other client keeps 18,000 characters, so serve-side size discipline, the only host-independent guarantee 20260719-122547-s-tac-40d and 20260816-205521-s-tac-x9l name, stays the default.
- **Every bound derived from the limit follows it.** Today these derive from `model.MaxResultChars = 18000` (`internal/model/result_bound.go:13`): `MaxServeChars` (minus 2,000) for a serve, `textBudget` (minus 3,000, `pkg/mcpapp/result_bound.go:17`) for the paged text of `search`, `gather`, `show` and `view`, the pages of `registry` and `read_attachment`, `model.DeepPageChars` (minus 6,000, `internal/model/verifier_deep.go:34`) and `DeepFirstPageChars` (`MaxServeChars` minus a measured 7,500-character margin, set in 20261117-192843-s-tac-19d; the margin stays) for the verifier's reading, and the room for the list of unproved pieces (`pkg/mcpapp/tools.go:1645`), unless 20261121-230157-d-tac-ym8, which removes that list with the proof arguments, is built first.
- **The size of a verifier's reading follows the host that reads it.** The capture builds the reading for the verifier (`deepReading`, `pkg/application/workflow_deep.go:647`), and `verify.runner` can run the verifier on another host than the drafter (`claude` runs a headless Claude Code, `driver` an external command; `internal/model/verifier.go:88`), so the drafter's client cannot set its page size. The same serve-time rule applies: a page is cut when it is served to the delegate's call, from that call's client name. Today the capture cuts the reading into pages at dispatch (`deepPages`, called from `prepareDeep` at `pkg/application/workflow_deep.go:454`) and stores them, and the verifier's `loadVerifyInput` and `turnPage` serve the stored pages (`pkg/application/workflow_deep.go:1115` and `:1146`); a revision's reading is cut the same way (`pkg/application/workflow_deep_revision.go:123`). The plan moves the cut to serve time: the store keeps the reading whole and pages it per call.

## Why

The number of turns times the carried context drives a verifier run's cost, and page turns are most of the turns. In 15 deep-verifier runs on this repository (Claude Code, `claude-opus-5-5`, 2026-11-20 to 2026-11-22), `next` calls that turned a page of the reading were 28 per run (median; 11 to 69), or 20 per reading (11 to 69), since three runs hold a second reading for a revision, and took 62.1% (42.1 to 88.4%) of the run's carried cost. Reads such as `show` were 8 turns and 22.3%; the findings report 1 turn and 5.0%. Cache reads were 95.7% of the input side, so each turn re-reads the whole prompt at the cache price. A run cost a median of 634,127 fresh-input-token equivalents (cache write 1.25x, cache read 0.10x fresh input). The page envelope (report schema, framing, pending chooser and the rest) was 17.9% of page-result bytes, and report schema, framing and pending chooser repeated on every page came to 48,448 bytes per run. The tables are in the [measurement](./22-103723-d-tac-npg/verifier-turn-cost.md); they also give the rules pages' share of a run's input-side cost as 10.5% (4.7 to 15.9%), a token figure 20261122-004754-s-tac-2c4 lists as not known. That gap is closed by 20261122-101625-d-tac-r0s, which cuts the rules pages by an estimated 36% to 37%; the 15 runs predate it.

## Expected saving

About a quarter to 30% of a verifier run's input side on Claude Code, measured on the 15 runs. The measurement pages each reading at a cap of 45,000 characters per result. A reading's page text (the `instructions` field of its page results, median 197,414 bytes; 113,741 to 640,609) goes into as many calls as it needs, with the room per page that sdd's bounds leave today, scaled: the cap minus 6,000, the first page the cap minus 9,500. A reading then takes 6 calls (median; 4 to 17) instead of the measured 20 (11 to 69), and the run's input side falls by 30.5% (10.5 to 46.7%). The same model at 18,000 characters, the check against today, gives 18 calls per reading instead of the measured 20 and a saving of 7.5% (-1.1 to 13.9%): it packs pages tighter than sdd does. Against that 18,000 baseline, 45,000 saves 25.0% (11.5 to 39.0%). With only the measured envelope per result (median 1,927 bytes) taken from the cap, 45,000 gives 5 calls per reading and a saving of 30.5% (12.4 to 48.2%). The model spreads the tokens of a reading's page turns evenly over the new calls and assumes the verifier takes no extra thinking turns and writes no more output with larger pages.

## Rejected

- Serve Claude Code up to 100,000 characters and declare 120,000 as `_meta["anthropic/maxResultSizeChars"]` in `tools/list`. Claude Code raises a tool's file threshold to a declared value, up to 500,000 characters, whatever `MAX_MCP_OUTPUT_TOKENS` is (Claude Code documentation, MCP page, section "Raise the limit for a specific tool"; 20260816-205521-s-tac-x9l also records the key). This relies on the declared limit: a Claude Code version that ignores it saves the result to a file, so it needs a fallback.
- Serve up to 450,000 characters and declare 500,000. One result could reach about 100,000 tokens, and how carefully a verifier reads a result that large is not measured.
- Codex above 18,000 characters through its per-tool setting, `mcp_servers.sdd.tools.<tool>.output_token_limit` (Codex documentation, MCP page, section "Other configuration options"), written or named by `sdd init`. sdd cannot see whether a person's Codex setting is in effect, and a result past Codex's budget loses its middle.
- Keep 18,000 characters for every host. The page calls, 62% of a run's carried cost, would stay.

## Accepted costs

- Two result sizes to build and test.
- About a third less saving than the declared options.
- A result of 45,000 characters may be read less carefully than several of 18,000. This is not measured.
- On Claude Code, a person who lowers `MAX_MCP_OUTPUT_TOKENS` gets larger sdd results saved to a file if Claude Code does not pass the variable to sdd.

## Not measured

- Reading quality on larger results: whether a verifier finds the same problems in a reading of 6 pages of 45,000 characters as in 20 of 18,000. The test run below measures it before the change ships.
- The main agent's saving. The same bound governs its `gather`, `show`, `search` and `view` pages, and its context is larger than a verifier's, so each avoided call saves more there, but no main-agent run was measured.
- Readings under 20261121-223938-d-tac-rqi. That plan has the verifier read lines and open entries by ID, and states that the reading's size must be measured again. The 15 runs predate it.

## Not decided

- Whether the larger size is proposed upstream.

## Layers

The split follows the CQRS planning contract. No graph write or read changes, so no command, query, handler or finder is added.

- **Model** (`internal/model`): the serve, read, verifier page and unproved-list bounds become functions of one result limit instead of constants derived from `MaxResultChars`, and the exact `claude-code` match picks that limit.
- **Application** (`pkg/application`): the verifier's reading is stored whole and paged per delegate call with the limit of that call's host.
- **MCP shell** (`pkg/mcpapp`): the limit picked from the connection's client name, lowered by a `MAX_MCP_OUTPUT_TOKENS` value `sdd serve` reads from its environment and passes in, and serves and read pages bounded by it.

## Acceptance criteria

- [ ] Before the change ships, one test run with real deep verifiers on Claude Code judges the same drafts on 45,000- and on 18,000-character pages, and its findings are compared draft by draft; the comparison is recorded.
- [ ] In that test run no result carries Claude Code's note that a result was saved to a file, and none carries a truncation marker.
- [ ] No sdd tool declares `_meta["anthropic/maxResultSizeChars"]` in `tools/list`.
- [ ] A connection whose client name is exactly `claude-code` gets serves, read pages and verifier reading pages of at most 45,000 characters each, as `model.ServedChars` counts them.
- [ ] A connection from Codex, from Claude Desktop (`claude-ai`) or from any other client, gets every result within 18,000 characters, as today.
- [ ] A verifier reading is stored whole and cut into pages as each page is served, for the client name of the delegate's call, not for the drafter's host.
- [ ] `MaxServeChars`, the read text budget, `DeepPageChars`, `DeepFirstPageChars` and the room for the unproved list, while it exists, derive from the connection's limit, not from a fixed 18,000.
- [ ] With `MAX_MCP_OUTPUT_TOKENS` in sdd's environment, the Claude Code bound is at most 2 characters per token of its value.
- [ ] The test run checks whether Claude Code passes `MAX_MCP_OUTPUT_TOKENS` to the stdio sdd server it starts, and records the answer.
- [ ] The test run records the page calls per reading on Claude Code against the 20 measured today.
