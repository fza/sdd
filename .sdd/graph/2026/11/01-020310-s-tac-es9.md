Search index publication now writes finished entries in batches of up to 64 per store write session, so a full reindex no longer reloads the whole store and parses the manifest once per entry (commit aeced398 on `pr/fix-index-publish`). This closes the quadratic reindex gap 20261101-003415-s-tac-1fw: the per-entry write session was the cost it named.

The shared indexing path of 20260907-150733-d-tac-qiq buffers entries the embedder has finished and hands them to the store in batches, flushing the remainder at the end. On a failure it still publishes what already finished, then returns the error, so an interrupted run redoes at most 63 entries' embeddings. A batch takes one store load, one chunk-ID ownership map, one staged write with one reload, and one manifest save; the save commits the batch, so a failure before it publishes none of the batch. `sdd index` and the MCP server's reconcile both take the batch path. Publishing a single entry after a capture keeps one write per entry, where batching gains nothing.

Evidence: tests of the batch sizes (64, 64, then the rest), of a mid-run embedder failure still publishing the finished entries, of one store write generation per batch, and of chunk-ID conflicts refused within a batch and against stored versions; each guard was broken and its test went red. No test observes that a batch reloads the store once rather than once per entry. A timing probe over 400 entries with 768-dimension vectors took 18.1s publishing per entry and 2.1s in batches.

Accepted costs: a reindex still loads the store once per batch, so its cost still grows quadratically, at a 64th of the former reload count. An entry the store refuses, such as a chunk-ID conflict, now holds back the other entries of its batch. The third remedy the gap listed, keeping a long reconcile from blocking requests that don't need it, is not part of this work.
