sdd's credential scan reads gitleaks' default rule file `config/gitleaks.toml` as gitleaks publishes it, from two copies: one built into each sdd release and one fetched once a day from gitleaks' latest release tag. Felix Zandanel decided the shape so the scan follows new credential formats between sdd releases, and nobody converts rules by hand.

**Built-in file.** The binary embeds gitleaks' `gitleaks.toml` unchanged, stamped with the release tag and commit it came from. One loader reads the built-in and a fetched copy alike, decoding with `github.com/pelletier/go-toml/v2` (v2.4.3 or later) and refusing unknown fields. It keeps the normalization `vendor-rules.py` applied: keywords and stopwords lowercased, as gitleaks does on load, and allowlist conditions uppercased. The hand-run converter `vendor-rules.py` and its output `rules.json` go. The sdd-side narrowing of `generic-api-key` (20261101-021050-d-tac-jac) keeps applying after a rule matches.

**Release refresh.** A devbox script fetches `gitleaks.toml` at gitleaks' latest release tag into the package. The release procedure runs it and commits a changed file before tagging, and the test against gitleaks' own per-rule samples runs on the result.

**Daily fetch.** The daily background pass that prunes caches (20261114-095140-d-cpt-ad4) also asks GitHub for gitleaks' latest release tag. When that tag is newer than the copy in use, it downloads the tag's `config/gitleaks.toml` into the machine-local cache and accepts it only when it decodes with no unknown key, every regex compiles, and every rule id of the built-in file is still present. The scan uses the newest accepted copy, the fetched one replacing the built-in one; `sdd serve` picks it up without a restart. Only release tags are fetched, never gitleaks' main branch: a tag is a reviewed upstream release.

**Failure.** A failed or rejected fetch never blocks a write: the scan keeps the newest accepted copy. The failure is logged as a warning, and `sdd info` shows its reason and the time of the last accepted fetch.

**Switch.** `secrets.rules_update` takes `daily` (default) or `off`; a hand-edited unknown value is ignored with a warning and the default applies, as for every config value (20260921-174543-d-cpt-tv9) and is set in the user-global config only, like `sessions.retention`: the daily pass runs once per machine for every project, so it reads one value. `off` stops the outbound call and leaves the built-in file in use. Whether a machine calls GitHub is that person's choice, not the project's, so a value in the committed `.sdd/config.yaml` or in `.sdd/config.local.yaml` is ignored with a warning naming file and key.

Rejected, with the reasoning: fetched rules replacing the built-in ones with no floor (an upstream file that drops or allowlists rules turns the check off until the next sdd release); fetched rules only adding new ids (upstream fixes to existing rules, against false alarms or for sharper patterns, wait for an sdd release); a fetch with no switch (offline, air-gapped and privacy-strict machines could not stop the daily call to GitHub); a fetch off unless enabled (most installs never get new rules); gitleaks' main branch as the source (unreleased rules); `github.com/BurntSushi/toml` (one release in the last year against six, and unknown keys come back as a list our code must check); an own TOML parser (a parser to own and keep in step with TOML and gitleaks' syntax, where a wrong parse of a regex silently weakens the check).

Accepted costs: a new dependency; one request to GitHub per machine and day by default; a fetched file can still loosen one rule's pattern or allowlist, since the floor checks rule ids, not patterns; a newer gitleaks file using a field the scanner does not know is rejected until an sdd release learns the field.

## Acceptance criteria

- [ ] The binary embeds gitleaks' `gitleaks.toml` unchanged with its tag and commit; `rules.json` and `vendor-rules.py` are gone; the gitleaks sample test passes on the built-in file.
- [ ] A devbox script refreshes the built-in file from gitleaks' latest release tag, and the release procedure runs it before tagging.
- [ ] The daily pass fetches the latest release tag's file when it is newer, keeps it in the machine-local cache, and the scan uses it; `sdd serve` uses it without a restart.
- [ ] A fetched file with an unknown key, a regex that does not compile, or a missing built-in rule id is rejected; the scan keeps the previous copy, a warning is logged, and `sdd info` shows the reason.
- [ ] A failed fetch never blocks a write.
- [ ] `secrets.rules_update: off` stops the fetch; `sdd config set` refuses other values; a value in a per-repo config is ignored with a warning naming file and key.
- [ ] The docs describe the built-in file, the daily fetch and the switch.
