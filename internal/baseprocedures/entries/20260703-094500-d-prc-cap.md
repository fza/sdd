The capture procedure is the shared spine for recording signals and decisions through dialogue: assemble a draft grounded in the graph, play it back for the user's explicit confirmation, judge the writing guide's findings on the approved content and fold them in, write through the pre-flight gate (the prose draft verifier over the grounding reading where `verify.mode` enables it), whose override is reachable only through the user, and verify the generated summary for fidelity. The guide runs once on the content the user approved and a later adjust gets a delta check of its changed lines; in an autonomous dialogue the guide and the verifier run before playback, since no dialogue edits follow (20261109-005108-d-cpt-wcj). Supersede, close, and anchored captures are not separate moves; they are this procedure entered with start inputs (`supersedes`, `closes`, `anchor`, a pre-selected `kind`). The instruction units below are the authoritative capture guidance, served step by step against the running draft.

### lane: lifecycleAndBody

**Lifecycle** (`closes`, `supersedes`). `closes` retires a target this work resolved; `supersedes` replaces an entry with this one. Either obliges the body, so settle it before writing: a retirement states why the target is retired, not merely that it is; a replacement carries the full current understanding on its own and says why each predecessor is replaced. A closure is often discovered while drafting — the retirement *is* the substance being recorded — so report it here when it surfaces, and report `null` to withdraw one you thought better of. Neither belongs in `refs`: an `addresses` ref reads as merely responding to the target, so the body claims a closure the entry does not carry and the target keeps deriving as open.

**Body** (`body`). The first sentence must work as a standalone summary — overview surfaces lead with it, so "Plan for X" tells a reader nothing; lead with what the entry is about. Fold the dialogue's substance into the description — trade-offs weighed, alternatives rejected, the why — so future readers get the reasoning, not just the conclusion. Every entry ID typed in the body must appear in `refs` (or be the supersede/close target), and every ref must be visible in the body's narrative. A body drafted in a file the user reviews need not travel in the report: stage the file (`stage_attachment`) and report its handle as `bodyHandle` instead of `body`. The body is the file's text after an optional block between two `---` lines; a key in that block named and shaped like a report field must agree with the report before the confirm (re-staging the file and reporting the field may come in either order), every other key is ignored, and nothing is taken from it. Edit such a body by patching the staged file — a `bodyPatch` is refused for it — and expect a fresh playback: the confirm binds to the staged file's hash, shown in playback as `bodyHash`.

**Refs** (`refs`, each `{id, kind, desc?}`, full entry IDs). The kind names why the pointer exists, chosen from what the body asserts — never a default, and the choices are trap-laden (`related` over-reached as a default, a terminal done "addressed"). Read that fact at least once before constructing any reference — it is the expected step, not an option. The optional `desc` says why this ref exists in this entry's narrative.

A ref may point across a repo boundary, written as `<repo-id>:<entry-id>`. Resolve-or-block applies equally there: a cross-repo ref must resolve to a declared dependency of this graph, or capture blocks — so confirm the target resolves (via `show`) before drafting, and a bare foreign ID is stored in full prefixed form. The lifecycle fields `closes` and `supersedes` never cross the boundary — a decision retires only entries in its own graph.

**Intent** (`intent`) is required when the kind is directive and is never derivable: `pending` — demands follow-up (the default posture) · `guiding` — standing context that shapes later decisions without ever completing · `settled` — born terminal; the body must justify why no follow-up is needed.

**Attachments** (`attachments`). The description is the summary; the attachment is the record. When the dialogue produced design trade-offs, evaluation findings, exploration synthesis, or research, stage the full record (`stage_attachment`) and list the handles here — a compressed summary without the record loses the reasoning permanently. Skip only when the description alone carries the full substance. Link each staged record from the body — `[label]({{"{{attachments}}"}}/filename.md)`, resolved to the entry's attachment directory at write — and keep that link in plain prose: inside a code span, fence, or indented block it reads as documentation of the syntax, not a live link.
