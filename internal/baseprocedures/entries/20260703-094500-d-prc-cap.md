Capture is the shared spine for recording signals and decisions through dialogue. Assemble a draft grounded in the graph. Play it back for the user's explicit confirmation. Judge the writing guide's findings on the approved content and fold them in. Write through the pre-flight gate (the prose draft verifier over the grounding reading, where `verify.mode` enables it); its override is reachable only through the user. Verify the generated summary for fidelity. The guide runs once on the content the user approved; a later adjust gets a delta check of its changed lines. In an autonomous dialogue the guide and the verifier run before playback, since no dialogue edits follow (20261109-005108-d-cpt-wcj). Supersede, close and anchored captures are not separate moves. They are this procedure entered with start inputs (`supersedes`, `closes`, `anchor`, a pre-selected `kind`). The instruction units below are the authoritative capture guidance, served step by step against the running draft.

### lane: lifecycleAndBody

**Lifecycle** (`closes`, `supersedes`). `closes` retires a target this work resolved. `supersedes` replaces an entry with this one. Either obliges the body, so settle it before writing. A retirement states why the target is retired, not merely that it is. A replacement carries the full current understanding on its own and says why each predecessor is replaced. A closure often surfaces while drafting: the retirement *is* the substance being recorded. Report it here when it surfaces. Report `null` to withdraw one you thought better of. Neither belongs in `refs`. An `addresses` ref reads as merely responding to the target. The body then claims a closure the entry does not carry, and the target keeps deriving as open.

**Body** (`body`). The first sentence must work as a standalone summary. Overview surfaces lead with it, so "Plan for X" tells a reader nothing. Lead with what the entry is about. Fold the dialogue's substance into the description: trade-offs weighed, alternatives rejected, the why. Future readers then get the reasoning, not only the conclusion. Dialogue carries no reason for the decision? Ask the user for it before drafting; never supply one. Every entry ID typed in the body must appear in `refs` (or be the supersede/close target). Every ref must be visible in the body's narrative.

Body drafted in a file the user reviews? It need not travel in the report. Stage the file (`stage_attachment`) and report its handle as `bodyHandle` instead of `body`. The body is the file's text after an optional block between two `---` lines. A key in that block named and shaped like a report field must agree with the report before the confirm. Re-staging the file and reporting the field may come in either order. Every other key is ignored, and nothing is taken from the block. Edit such a body by patching the staged file; a `bodyPatch` is refused for it. Changing the staged file means a fresh playback.

### lane: layerSpecRefs

**Layer** (`layer`): strategic (why, direction) · conceptual (approach, shape) · tactical (structure, trade-offs) · operational (individual steps) · process (how we work).

**Procedure drafts** (`canonical`, `class`, `procedureSpec`). A procedure also declares its identity and its workflow. `canonical` is the stable name everything binds to. `class` places how it enters (empty means move). `procedureSpec` carries the workflow itself: `params`, `state` and `steps`, as the structured value this step's report schema describes. Write the per-step `## unit:` guidance into the body. Pull the spec reference fact `20260814-100000-s-prc-psr` before writing the workflow. It carries the field shapes, the gateable name vocabulary and a worked example. The gate loads the declared workflow exactly as the engine will and names what fails.

**Refs** (`refs`, each `{id, kind, desc?}`, full entry IDs). The kind names why the pointer exists. Choose it from what the body asserts, never by default. The choices are trap-laden: `related` over-reached as a default, a terminal done "addressed". The vocabulary lives in the ref-kind fact `20260828-160000-s-prc-rfk`: each kind's meaning, its direction, and when it applies over a sharper or weaker neighbor. Read that fact at least once before constructing any reference. It is the expected step, not an option. The optional `desc` says why this ref exists in this entry's narrative.

A ref may point across a repo boundary, written as `<repo-id>:<entry-id>`. Resolve-or-block applies there too. A cross-repo ref must resolve to a declared dependency of this graph, or capture blocks. So confirm the target resolves (via `show`) before drafting. A bare foreign ID is stored in full prefixed form. The lifecycle fields `closes` and `supersedes` never cross the boundary: a decision retires only entries in its own graph.

**Intent** (`intent`) is required when the kind is directive and is never derivable. `pending` demands follow-up (the default posture). `guiding` is standing context that shapes later decisions without ever completing. `settled` is born terminal; the body must justify why no follow-up is needed. Dialogue states no intent for the directive? Ask the user before drafting; never supply one.

**Attachments** (`attachments`). The description is the summary; the attachment is the record. Dialogue produced design trade-offs, evaluation findings, exploration synthesis or research? Stage the full record (`stage_attachment`) and list the handles here. A compressed summary without the record loses the reasoning permanently. Skip only when the description alone carries the full substance. Link each staged record from the body as `[label]({{"{{attachments}}"}}/filename.md)`; it resolves to the entry's attachment directory at write. Keep that link in plain prose. Inside a code span, fence or indented block it reads as documentation of the syntax, not a live link. Every other file path the body mentions takes the reverse: set it in code formatting. Otherwise it reads as a claim to an attachment the entry does not carry and draws warnings at the write gate.
